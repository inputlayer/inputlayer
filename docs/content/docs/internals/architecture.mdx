# InputLayer Architecture

**Status**: Describes the engine as it runs today. Persistent rules are evaluated on every read; they are not materialized or incrementally maintained. Section 16 describes the planned live-views design ([#305](https://github.com/inputlayer/inputlayer/issues/305)), which is not yet shipped.

---

## Overview

InputLayer is a Datalog engine that executes each query as a Differential Dataflow (DD) dataflow over a snapshot of the knowledge graph's facts. The architecture provides:

- **Recompute on read**: every query evaluates the persistent rules it depends on from the base facts, in a dataflow built for that query and torn down afterwards
- **Lock-free concurrent reads** via an ArcSwap snapshot system
- **Standing queries (subscriptions)** that re-evaluate their query after each relevant commit and send the diff against the previous result
- **Session isolation** for ephemeral facts and rules
- **Durability** through a WAL and Parquet batch files

```
+-----------------------------------------------------------------------------+
|                              StorageEngine                                    |
|                    DashMap<String, Arc<RwLock<KnowledgeGraph>>>              |

|  |  +--------------------+  +--------------------+  +-------------------+  | |

|  |  |  dedup indexes     |  |  stratification    |  |  base relations   |  | |
|  |  +--------------------+  +--------------------+  +-------------------+  | |
|  |                                                                          | |
|  |  +--------------------------------------------+                          | |
|  |  |        ArcSwap<KnowledgeGraphSnapshot>      |                          | |
|  |  |  revision                                   |                          | |

+-----------------------------------------------------------------------------+

 Each query: snapshot -> fresh IQLEngine -> one DD dataflow per rule -> rows -> dataflow dropped
```

No component keeps rule results between queries. Derived relations exist only inside the evaluation of the query that reads them.

## 2. Core Components

### 2.1 StorageEngine

**Purpose**: Multi-knowledge-graph storage with concurrent access.

**Key Features**:
- **DashMap** enables concurrent access to different KGs without global locking
- **Revisions** from one counter shared by every knowledge graph of the engine run; each published snapshot gets the next one
- **Per-KG locking** allows parallel queries to different knowledge graphs

### 2.2 KnowledgeGraph

**Purpose**: Single knowledge graph: base facts, rules, schemas, vector indexes and the current snapshot (`src/storage_engine/mod.rs`).

```rust
pub struct KnowledgeGraph {
    name: String,
    store: RelationStore,              // base relations with dedup indexes
    rule_catalog: RuleCatalog,         // persistent rules (rules/catalog.json)
    schema_catalog: SchemaCatalog,     // per-KG schema isolation
    snapshot: ArcSwap<KnowledgeGraphSnapshot>,
    incremental: Option<IncrementalEngine>, // None in production, see 2.4
    auto_materialize: bool,                 // false in production, see 2.4
    indexes: IndexManager,             // vector indexes on base relations
    num_workers: usize,
    // query limits: max_result_rows, max_query_cost, max_recursion_iterations, ...
}
```

### 2.3 KnowledgeGraphSnapshot

**Purpose**: Immutable point-in-time view for lock-free reads (`src/storage_engine/snapshot.rs`).

**Key Features**:
- **revision** names the state a query read and is returned to clients
- **input_tuples** holds the base relations (Arc-shared with the store, O(1) clone per relation)
- **rules** holds the persistent rules; **persistent** holds their formatted program prefix and a plan cache, shared with the previous snapshot while the rules are unchanged
- **materialized_relations** is always empty on the server path (it is filled only when the test-only auto-materialization of 2.4 is on)

### 2.4 IncrementalEngine and DerivedRelationsManager (test-only)

`src/incremental.rs` and `src/derived_relations.rs` contain an `IncrementalEngine` (a long-lived timely worker with one DD `InputSession` and arrangement per **base** relation) and a `DerivedRelationsManager` (rule bookkeeping whose compiled rule clauses are always empty). Neither is used by the server:

- `KnowledgeGraph.incremental` is `None` in both production constructors; `enable_incremental()` and `set_auto_materialize()` are called only from tests.
- There is no configuration key that turns either on.
- When a test enables auto-materialization, each publish recomputes every rule from the base facts in a temporary engine and copies the results in; nothing is maintained incrementally.
- No rule is compiled into a DD dataflow that outlives a query.

The live-views milestone replaces this code (Section 16).

## 3. Data Flow Paths

### 3.1 Write Path

```
WS/REST write program (+fact, -fact, +rule, ...)
    |
    v
commit_program (KG write lock)                     src/storage_engine/program_commit.rs
    |
    +-> expect_revision precondition check
    +-> resolve and validate facts (schema, refuse writes into rule heads)
    +-> FilePersist: WAL append + fsync ----------> Durability
    +-> apply_delta:
    |     store insert/delete
    |     vector index upsert/delete
    |     shadow_write -> returns at once (incremental is None)
    v
publish_snapshot() -------------------------------> new revision, ArcSwap.store(new_snapshot)
    |
    v
notifications: one PersistentUpdate per changed relation
    -> subscription hub re-evaluates affected standing queries (3.3)
```

A fact commit does nothing to persistent rules: no rule result exists to update. Rule definitions are written to the catalog (`rules/catalog.json`) and logged in the WAL.

### 3.2 Read Path (Query)

```
?path(X, Y)
    |
    +-> query shorthand: __query__(X, Y) <- path(X, Y)
    +-> parse session facts and session rules
    v
KnowledgeGraphSnapshot (pinned at the current revision)
    |
    +-> combine: dependency closure of the query over the persistent rules;
    |            keep only those rules and only the relations they read
    +-> add session facts (isolated copy of the touched relations) and session rules
    +-> new_engine(): a fresh IQLEngine for this query
    v
IQLEngine
    +-> load: safety, stratification
    +-> compile: constant specialization, SIP, Magic Sets, IR, optimizer
    |     (standing queries reuse a cached plan while the rules are unchanged;
    |      ad-hoc queries compile every time)
    +-> execute: per rule, a fresh CodeGenerator and timely worker; inputs streamed in,
    |            results collected, dataflow torn down
    v
Rows (sorted, paginated, capped by the handler), tagged with the snapshot revision
```

Every read of a persistent rule re-derives it from the base facts. Magic Sets restrict the work when the query binds a constant in a position the rule's recursion can use; otherwise the whole derived relation is computed.

### 3.3 Subscriptions (Standing Queries)

```
commit on KG -> PersistentUpdate{relation} -> hub
  for each view of the KG whose dependency closure contains the relation:
     re-evaluate the query on the KG's current snapshot (same path as 3.2, cached plan)
     diff the new full result against the previous one
     publish the delta to every subscriber of the view
```

- Code: `src/protocol/subscription/` (`hub.rs`, `views.rs`, `reevaluate.rs`, `result_set.rs`).
- Subscribers of the same query share one view and one evaluation per change. Changes that arrive while an evaluation runs are merged into one pending change, so a view has at most one evaluation running and one pending.
- **Parameterized families** (`parameterized.rs`): views that differ only in bound constants lift the constants to parameters and may share one evaluation per revision, partitioning its rows by binding. Whether a family shares is decided by measuring shared cost against each member's own cost (config `subscriptions.share_parameterized`, on by default). Shared evaluations run one at a time, with at most one more pending.
- A view that reads a vector index re-evaluates on every commit of its graph.
- The delta is computed by re-evaluation and diff; no support counts or derived state are kept between evaluations.

## 4. Consistency Guarantees

### 4.1 Snapshot Consistency

**Guarantee**: Point-in-time consistent views via immutable Arc-wrapped data.

- Readers get consistent snapshots without holding locks
- Snapshot cloning is O(1) due to Arc sharing
- Each query evaluates everything it reads (base facts and rules) against one snapshot revision

### 4.2 Write Consistency

**Guarantee**: All writes are durable before acknowledgment.

- WAL append and fsync before the in-memory update
- The new snapshot is published under the KG write lock, so revisions of one KG increase with every commit
- `expect_revision` preconditions are checked against the snapshot the commit applies to

### 4.3 Read-After-Write Consistency

A write is acknowledged with the revision it committed at. A query on the same knowledge graph issued after the acknowledgement reads that revision or a later one, and recomputes every rule it reads from those facts.

A subscription's delta for a commit comes from a re-evaluation on the KG's current snapshot when the evaluation starts, which may already include later commits.

### 4.4 Session Isolation

**Guarantee**: Session facts and rules don't affect concurrent queries. Session facts are added to an isolated copy of the relations the query touches; session rules are compiled into that query's program only.

## 5. Rule System

### 5.1 Persistent Rules (`+` prefix)

```iql
+path(X, Y) <- edge(X, Y)
+path(X, Z) <- path(X, Y), edge(Y, Z)
```

**Characteristics**:
- Stored in the RuleCatalog (`rules/catalog.json`), validated at registration (safety, stratification, arity, aggregates)
- Evaluated from the base facts on every query that reads them; no results are stored
- A rule change invalidates the KG's cached plans and the affected subscription views

### 5.2 Session Rules (no prefix)

```iql
reachable_from(Y) <- path(1, Y)
?reachable_from(X)
```

**Characteristics**:
- Ephemeral (per-session lifecycle), compiled into each query of the session
- Validated for stratification before execution
- Can reference persistent rules, which are evaluated in the same query
- Computed fresh each time (not cached), like persistent rules

### 5.3 Rule Validation

```rust
/// Validate single rule (self-negation, head safety, range restriction)
pub fn validate_rule(rule: &Rule, name: &str) -> Result<(), String>;

/// Validate rule set for stratification (negation cycles)
pub fn validate_rules_stratification(rules: &[Rule]) -> Result<(), String>;
```

**Checks**:
- **Self-negation**: Can't negate own head
- **Head variable safety**: All head variables must be bound by positive atoms
- **Range restriction**: Variables in negated atoms must be bound by positive atoms
- **Stratification**: No mutual negation cycles

## 7. Execution Model

### 7.1 Batch Execution (CodeGenerator)

```rust
pub struct CodeGenerator {
    input_data: HashMap<String, Vec<Tuple>>,
}

pub struct ExecutionConfig {
    num_workers: usize,
}
```

**Execution Paths**:
1. **Non-recursive**: Single `execute_directly` call
2. **Transitive closure**: DD iterative scope with `SemigroupVariable`
3. **General recursive**: DD `.iterative()` scope with live collections

**Parallelization**:
- Rayon-based parallel execution for scan/filter/map
- Join queries use single-worker DD for correctness
- Configurable via `num_workers`

### 7.2 No Incremental Execution Path

Every query, ad-hoc or standing, runs through the batch path of 7.1. There is no long-lived dataflow on the server path; see 2.4 for the test-only `IncrementalEngine`.

## 8. Persistence Layer

### 8.1 WAL (Write-Ahead Log)

```rust
pub struct Update {
    pub data: Tuple,
    pub time: u64,
    pub diff: i64,  // +1 for insert, -1 for delete
}

/// All changes of one commit, applied atomically at one revision.
pub struct Transaction {
    revision: u64,     // Logical time of every change in the commit
    ops: Vec<TxnOp>,   // Changes in commit order
}

pub enum TxnOp {
    Facts { shard: String, changes: Vec<(Tuple, i64)> },
}
```

Each transaction is one WAL record, `<crc32>:<json>\n`, and the trailing
newline is its commit boundary. Recovery replays the longest intact prefix of
records, so a crash recovers whole transactions only (see the persistence
guide).

### 8.2 Batch Files (Parquet)

```rust
pub struct ShardMeta {
    pub shard: String,
    pub batches: Vec<BatchMeta>,
    pub since: u64,   // Compaction frontier
    pub upper: u64,   // Write frontier
}
```

### 8.3 Recovery Sequence

```
1. Load shard metadata, rule catalog, schemas and index definitions
2. Load batch files into the relation store
3. Replay WAL transactions since the last batch
4. Rebuild vector indexes from the facts
5. Publish the first snapshot; rules are evaluated on the first query that reads them
```

Nothing derived is persisted or recovered: after a restart every rule is recomputed on every read, as before the restart.

## 10. HNSW Indexing

Vector indexes are maintained on **base** relations by the commit path (`apply_delta`), synchronously under the KG write lock. Queries resolve `hnsw_nearest` right before the rule that uses it runs. An index on a rule's head relation is not maintained today (it is built from stored facts only, and a rule's rows are never stored); the live-views milestone covers vectors inside maintained rules (Section 16).

## 12. Query Optimization

InputLayer includes query optimization infrastructure for improving join performance.

### 12.1 Optimization Modules

| Module | File | Purpose |
|--------|------|---------|
| **Bloom Filter** | `src/bloom_filter.rs` | Probabilistic set membership testing |
| **Hash Index** | `src/hash_index.rs` | O(1) join key lookups with Bloom acceleration |
| **Statistics** | `src/statistics.rs` | Cardinality and selectivity estimation |
| **Join Planning** | `src/join_planning/mod.rs` | Join ordering via MST algorithm |
| **SIP Rewriting** | `src/sip_rewriting/mod.rs` | Sideways Information Passing |
| **Subplan Sharing** | `src/subplan_sharing/mod.rs` | Common subexpression elimination within one evaluation |

### 12.2 Bloom Filter

Space-efficient probabilistic data structure for fast set membership testing.

```rust
use inputlayer::bloom_filter::{BloomFilter, BloomFilterBuilder};

// Create filter for 10K elements with 1% false positive rate
let mut filter = BloomFilter::new(10_000, 0.01);
filter.insert(&"key1");
filter.insert(&"key2");

// Check membership (no false negatives, possible false positives)
if filter.might_contain(&"key1") {
    // Definitely present or false positive
}
```

**Properties:**
- No false negatives: if `might_contain()` returns `false`, the element is definitely not present
- Possible false positives: if `might_contain()` returns `true`, element might or might not be present
- Space efficient: ~10 bits per element for 1% false positive rate

### 12.3 Hash Index

Accelerates join key lookups with Bloom filter pre-filtering.

```rust
use inputlayer::hash_index::{HashIndex, HashIndexManager, JoinKeySpec};

// Create index for edge(src, dst) on column 0
let spec = JoinKeySpec::new("edge", vec![0]);
let mut index = HashIndex::new(spec);

// Build from tuples
index.build_from_tuples(&edge_tuples);

// Lookup with Bloom filter check first
if let Some(matching) = index.lookup(&key) {
    for tuple in matching {
        // Process matching tuples
    }
}
```

### 12.4 Statistics Manager

Collects and maintains relation statistics for query optimization.

```rust
use inputlayer::statistics::{StatisticsManager, RelationStats};

let mut stats_manager = StatisticsManager::new();

// Update statistics for a relation
stats_manager.update_stats("edge", &edge_tuples);

// Get cardinality estimate
if let Some(stats) = stats_manager.get_stats("edge") {
    println!("Cardinality: {}", stats.cardinality);
    println!("Distinct values in col 0: {}", stats.column_stats[0].distinct_count);
}

// Estimate join selectivity
let selectivity = stats_manager.estimate_join_selectivity("edge", 0, "node", 0);
```

### 12.5 BloomSemijoin IR Node

The IR includes a `BloomSemijoin` node for semijoin reduction:

```rust
IRNode::BloomSemijoin {
    input: Box<IRNode>,           // Relation to filter
    filter_source: Box<IRNode>,   // Relation providing filter keys
    input_key_columns: Vec<usize>,
    filter_key_columns: Vec<usize>,
    output_schema: Vec<String>,
}
```

This node filters `input` to keep only tuples whose key columns exist in `filter_source`, implemented via Differential Dataflow's `semijoin()` operator.

## 14. Architectural Patterns

### 14.1 Arc-Wrapped Data for Sharing

Base relations and rules in a snapshot are Arc-wrapped for O(1) cloning:
```rust
input_tuples: Arc<RelationMap>
rules: Arc<Vec<Rule>>
```

### 14.2 ArcSwap for Atomic Publishing

```rust
self.snapshot.store(Arc::new(new_snapshot));  // O(1) atomic swap
```

### 14.3 Recompute on Read

```rust
let snapshot = kg.snapshot();          // pinned revision
let engine = snapshot.new_engine();    // fresh IQLEngine per query
// combine persistent-rule closure + session rules + query, compile, execute, drop
```

### 14.4 Session Isolation via Copy-on-Touch

```rust
// Only the relations that receive session facts are copied
isolated.entry(relation).or_default().push(session_fact);
// Execute against the isolated copy
```

| Capability | Implementation today |
|-----------|----------------|
| **Rule evaluation** | Recomputed from base facts on every query, one DD dataflow per rule per query |
| **Subscriptions** | Re-evaluate after each relevant commit, diff with the previous result |
| **Lock-free reads** | ArcSwap snapshot system |
| **Concurrent writes** | DashMap + per-KG locking |
| **Schema isolation** | Per-KG SchemaCatalog |
| **Session isolation** | Isolated copies for ephemeral data |
| **Durability** | WAL + Parquet batch files; only base facts and definitions are stored |
| **Consistency** | One snapshot revision per query; revision returned on writes and reads |

## 16. Planned: Live Views (Milestone 9, #305)

> Status: planned, not yet shipped. Tracked in [#305](https://github.com/inputlayer/inputlayer/issues/305). Nothing in this section describes today's behaviour.

The live-views milestone makes every deployed (persistent) rule an incrementally maintained view; everything else is a query.

- **One view maintainer per knowledge graph**: a long-lived Differential Dataflow worker fed from the commit path (the `shadow_write` hook) at each commit's revision. It replaces `IncrementalEngine` and `DerivedRelationsManager`.
- **Persistent rules as arrangements**: each rule compiles into the maintainer's dataflow (joins, recursion with `iterate`, negation with `antijoin`, aggregates with `reduce`); its rows live only in its arrangements.
- **Queries never re-derive deployed rules**: ad-hoc queries, session rules and proofs import the view arrangements at a stated revision and run only their own operators.
- **Writes confirmed once views include them**: a write is acknowledged after the maintainer has applied it, so the acknowledged revision is the revision views and queries show.
- **Subscriptions only on deployed rules**: a subscription is a keyed diff of a view between two revisions, read from the view's update history. Subscribing to a body that is not a deployed rule is refused with a request to deploy it first.
- **Query batching kept, simplified**: many subscribers that bind different constants become subscribers of one view with different keys; the cost probe that decides whether to share goes away.
- **Non-maintainable constructs refused in deployed rules**: constructs that cannot be maintained (for example time-dependent or non-deterministic functions) are rejected at registration and stay available in queries and session rules.
- **Vectors inside live rules**: vector predicates and indexes over rule outputs are maintained with the views.
