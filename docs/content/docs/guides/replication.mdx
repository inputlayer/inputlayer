# Replication (Warm Standby)

A **follower** is a second server that keeps a live copy of a **primary**. The
primary streams every committed change to it. The follower applies the
changes in commit order and serves queries and subscriptions on the copy. It
refuses every write.

This release ships the stream and the follower. Shipping is
**asynchronous** by default: the primary acknowledges a write once it is
durable on the primary, then sends it on. With **synchronous** shipping the
primary acknowledges a write only once a follower holds it, so no
acknowledged write is lost with the primary (see
[Synchronous Shipping](#synchronous-shipping)). Promotion (turning a follower
into the primary) and automatic failover are not part of this release.

## Setting Up

Both servers need the same shared secret. On the primary:

```toml
[replication]
role = "primary"
token = "a-long-random-secret"   # or INPUTLAYER_REPLICATION__TOKEN
```

On the follower, which has its own, empty data directory:

```toml
[replication]
role = "follower"
token = "a-long-random-secret"
primary_url = "http://primary:8080"
```

The follower connects to `GET /v1/replication/stream` on the primary's HTTP
port. The follower's client speaks plain HTTP only. Keep the connection on a
private network, or put a proxy that handles TLS in front of the primary. It copies the primary's whole state, then applies changes as they
commit. Users and API keys live in the replicated `_internal` graph, so the
primary's API keys work on the follower too. The follower creates no admin
user of its own.

## What Replicates

Every durable change, in the order it committed:

- fact inserts and deletes
- persistent rules and schemas
- knowledge graph creation and drops
- relation drops
- vector index creation and drops (the follower builds each index from its
  own copy of the facts)

Session rules, session facts and session schemas stay on the server that holds
the session. API key "last used" times are not saved on a follower.

Each change applies on the follower as one transaction, exactly as it
committed on the primary. A query on the follower therefore sees the
primary's state as of some earlier commit, never half of a commit.
Subscriptions on the follower get deltas for replicated commits. Revisions
on the follower are the follower's own: they increase, but they are not the
primary's numbers.

## Recovery Point (RPO)

With asynchronous shipping, a write the primary acknowledged can be lost if
the primary is lost before the follower applied it. The window is the
follower's lag, which the status endpoint and the metrics report at any time
(`primary.lag_events` and `primary.lag_ms`: the writes that losing the
primary now would lose, and the age of the oldest).

Measured with primary and follower on one 32-core host (release build,
`immediate` durability):

- a subscription on the follower receives a write's delta 2.1 ms after the
  primary acknowledges the write (median; p99 7.4 ms). The same subscription
  on the primary takes 0.5 ms.
- with 4 writers at full speed (about 520 commits per second) the follower
  stays within one event of the primary
- across 5 trials of killing the primary (`SIGKILL`) under a steady writer,
  no acknowledged write was missing from the follower

A follower that cannot hear the primary (the primary died, or the network is
cut) notices after `timeout_ms`. Writes the primary accepts in that time reach
the follower only once the connection is back.

With synchronous shipping the RPO is zero for every acknowledged write while
a follower keeps up: see below.

## Synchronous Shipping

```toml
[replication]
role = "primary"
token = "a-long-random-secret"
mode = "sync"
sync_timeout_ms = 5000        # how long a write's reply waits for a follower
on_follower_loss = "block"    # or "degrade"
```

In `sync` mode the primary answers a request that changed state (facts,
rules, schemas, graphs, indexes, users, API keys, access grants) only once a
follower has applied its changes and synced them to its WAL. If the primary
is then lost, the follower holds every write a client was told succeeded.
Reads never wait. Nothing changes on the follower: it acknowledges every
applied batch after its WAL fsync in both modes.

**What it costs.** Each write's reply waits one round trip to the follower
plus the follower's fsync. Measured with primary and follower on one 32-core
host (release build, `immediate` durability, the measurement lab in
`tests/replication_tests.rs`):

| Writes | Async (median / p99) | Sync (median / p99) |
|---|---|---|
| 1 writer, one commit at a time | 1.46 ms / 5.6 ms | 2.69 ms / 8.5 ms |
| 4 writers at full speed | 4.7 ms / 13.2 ms, 766 commits/s | 5.2 ms / 14.6 ms, 770 commits/s |

Async mode costs the same as before synchronous shipping existed (1.44 ms
median for 1 writer, 763 commits/s for 4, on the previous release in the same
runs). A standalone server takes 1.33 ms per commit.

The follower applies every batch it has received with one fsync, so
concurrent writers share the wait: throughput with several writers is close
to async.

**Kill-the-primary test.** Across 10 trials of killing the primary
(`SIGKILL`) under 4 writers in `sync` mode, every write a client was told
succeeded (about 2,000 per trial) was on the follower. The test runs on every
change (`in_sync_mode_killing_the_primary_loses_no_acknowledged_write`).
The same 10 trials in `async` mode also lost nothing on that host, but there
the primary held 1 or 2 unconfirmed writes at each kill: a slower network or
follower turns those into lost writes, and `sync` mode never does.

### When No Follower Confirms

The commit itself is already durable on the primary when the wait ends, so a
timeout is never reported as a failed write. What happens is set by
`on_follower_loss`:

| `on_follower_loss` | A write no follower confirms within `sync_timeout_ms` | Later writes |
|---|---|---|
| `block` (default) | fails with code `replica_unconfirmed`: committed on the primary, not confirmed on a replica | keep waiting, then fail the same way, until a follower confirms again. RPO stays zero for every write reported as succeeded; availability of writes drops. |
| `degrade` | succeeds after the wait; the primary logs `replication_sync_degraded` and falls back to asynchronous shipping | do not wait. Once a follower has caught up (it applied everything it was sent, including every change from before the fall back), the primary logs `replication_sync_rearmed` and waits again. |

A client that gets `replica_unconfirmed` must not resend the write as if it
had failed: it is applied on the primary and reaches the follower once one
catches up. It could be lost only if the primary is lost first.

Choose `block` when losing an acknowledged write is worse than refusing
writes for a while, and `degrade` when writes must keep flowing. In both
modes, alert on `inputlayer_replication_sync_state`.

A follower that resyncs (it is new, or fell further behind than
`retain_bytes`) confirms nothing until the copy is applied, so writes made
meanwhile wait for it. Size `sync_timeout_ms` above the follower's usual
reconnect time (a few seconds), not above a resync.

## When Things Go Wrong

| Event | What the follower does |
|---|---|
| The primary is killed | Keeps exactly the changes it applied: a prefix of the primary's commits. It reconnects with backoff (100 ms up to 2 s). |
| The primary restarts | Copies the primary's state again (a *resync*), then streams. |
| Network partition | Notices the silence after `timeout_ms`, keeps reconnecting, and catches up from where it stopped once the network is back. |
| The follower restarts | Resumes from its saved position (`replication/follower.json` in its data directory). |
| The follower falls further behind than `retain_bytes` | Resyncs. |
| A change fails to apply | Clears its position and resyncs. |

A resync brings the follower's whole state to a consistent copy of the
primary. On the same host, a fresh follower copied a primary holding 1,000,000
facts in 3.7 s. A restarted follower caught up on 20,000 missed commits in
2.4 s. Facts, rules, schemas, graphs and indexes the primary no longer has
are removed. A partly applied or stale follower is repaired the same way as
an empty one.

While a checkpoint is sent, the primary keeps every change committed after
it, even past `retain_bytes`, so the follower can catch up once the copy is
applied. That backlog may grow to 4 × `retain_bytes`. If writes outgrow it
during the copy, the primary abandons that resync, logs
`replication_resync_pin_overflowed`, and counts it in
`primary.resync_pin_overflows`. The follower counts the attempt in
`resync_failures` and waits longer before each retry: 1 s, doubling up to
60 s. The wait resets once a resync finishes and the follower catches up
with the primary's head. If the counters keep rising, raise `retain_bytes`
to cover the writes made during one resync.

**Known limit.** The follower stops reading the stream while it applies one graph from a
checkpoint. If a single graph takes longer to apply than the primary waits
for a stalled follower (`timeout_ms`, at least 10 s), the primary drops the
connection and the resync starts over. Graphs of a few million facts are
affected. This is tracked in
[#356](https://github.com/inputlayer/inputlayer/issues/356).

## Monitoring

`GET /v1/replication/status` (any valid API key) reports this server's role.

On a primary it reports:

- `primary.stream_id`: this run of the primary
- `primary.head_lsn`: the number of the newest change
- `primary.lag_events` and `primary.lag_ms`: the changes no follower has
  confirmed applying, and how long ago the oldest of them committed (what
  losing the primary now would lose)
- `primary.sync`: `mode`, `state` (`async`, `sync`, `stalled` while `block`
  times out, or `degraded`), `on_follower_loss`, `sync_timeout_ms`,
  `confirmed_lsn` (every change up to it is on a follower), and the counters
  `waits`, `wait_ms_total`, `unconfirmed`, `degrades` and `rearms`
- for each connected follower: `sent_lsn`, `acked_lsn`, `lag_events` and
  `lag_ms`
- `resync_pin_overflows`: resyncs abandoned because writes during the copy
  outgrew 4 × `retain_bytes`

On a follower it reports:

- `follower.state`: `connecting`, `resyncing` or `streaming`
- `applied_lsn` and `primary_head_lsn`
- `lag_events`
- `last_contact_ms`: time since the primary was last heard; absent until
  the follower first hears from it after starting
- `resyncs` (begun), `resync_failures` (ended before the follower caught
  up with the primary's head) and `reconnects`, counted since the follower
  started
- `last_error`

```bash
curl -H "Authorization: Bearer $INPUTLAYER_API_KEY" http://follower:8080/v1/replication/status
```

The same report is the `replication` object of `GET /metrics` on a primary
or follower. `GET /metrics/prometheus` exports it as
`inputlayer_replication_*`:

| Metric | Server | Meaning |
|---|---|---|
| `head_lsn`, `confirmed_lsn` | primary | newest change; newest change a follower confirmed |
| `lag_events`, `lag_seconds` | primary | changes no follower confirmed, and the age of the oldest |
| `followers` | primary | connected followers |
| `sync_state{state="async\|sync\|stalled\|degraded"}` | primary | 1 for the current state |
| `sync_waits_total`, `sync_wait_seconds_total` | primary | replies that waited for a follower, and the time spent |
| `sync_unconfirmed_total` | primary | replies failed with `replica_unconfirmed` |
| `sync_degrades_total`, `sync_rearms_total` | primary | falls back to async, and returns to sync |
| `follower_streaming`, `follower_applied_lsn`, `follower_lag_events` | follower | stream state, position and lag |
| `follower_last_contact_seconds` | follower | time since the primary was last heard |
| `follower_resyncs_total`, `follower_reconnects_total` | follower | resyncs begun, reconnects |

## Settings

| Setting | Role | Default | Meaning |
|---|---|---|---|
| `role` | both | `standalone` | `standalone`, `primary` or `follower` |
| `token` | both | none | shared secret, at least 16 characters |
| `retain_bytes` | primary | 64 MiB | recent changes kept in memory for followers to catch up from |
| `heartbeat_ms` | primary | 500 | heartbeat interval on an idle stream |
| `primary_url` | follower | none | the primary's base URL (`http://` only) |
| `timeout_ms` | follower | 3000 | silence after which the follower reconnects; must exceed `heartbeat_ms` |
| `mode` | primary | `async` | `async`, or `sync` to acknowledge a write only once a follower applied it |
| `sync_timeout_ms` | primary | 5000 | how long a write's reply waits for a follower in `sync` mode |
| `on_follower_loss` | primary | `block` | `block` or `degrade`: what a `sync` primary does when no follower confirms in time |

Keep the primary on `durability_mode = "immediate"` (the default). With
`batched` durability a crash can lose commits that the primary already sent.
The follower would then hold commits that the restarted primary no longer
has. The resync that follows removes them from the follower.

A follower must be durable: it refuses to start with
`durability_mode = "async"`, which writes no WAL, because after a crash it
would resume past changes it lost. Use `immediate` or `batched`.
