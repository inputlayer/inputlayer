# HTTP API Guide

InputLayer is a **WebSocket-first** system. All data operations (queries, inserts, rule definitions, meta commands) go through the WebSocket API. The HTTP REST endpoints provide health checks, metrics, and documentation.

For query execution, see the [WebSocket API](websocket-api) guide.

## Starting the Server

```bash
# Start the HTTP server
./target/release/inputlayer-server

# With custom port
./target/release/inputlayer-server --port 9090

# With config file
./target/release/inputlayer-server --config config.toml
```

Or enable in configuration:

```toml
[http]
enabled = true
host = "127.0.0.1"
port = 8080
```

## Base URL

All endpoints are available at both root and versioned paths:

```
http://localhost:8080/health
http://localhost:8080/v1/health
```

## Health & Monitoring Endpoints

### Health Check

```http
GET /health
```

Returns server health status. Returns HTTP 200 when healthy, 503 when storage is degraded.

**Response (200):**
```json
{
  "success": true,
  "data": {
    "status": "healthy",
    "version": "0.1.0",
    "uptime_secs": 3600
  }
}
```

**Response (503) - Storage lock contended:**
```json
{
  "success": true,
  "data": {
    "status": "degraded",
    "version": "0.1.0",
    "uptime_secs": 3600
  }
}
```

### Liveness Probe

```http
GET /live
```

Always returns HTTP 200 if the process is alive. Does not check storage. Use for Kubernetes liveness probes.

### Readiness Probe

```http
GET /ready
```

Returns HTTP 200 if the server can handle requests (storage accessible). Returns 503 if storage lock is contended. Use for Kubernetes readiness probes.

### Server Statistics

```http
GET /metrics
Authorization: Bearer <admin-api-key>
```

Needs an admin API key: an unscoped key of a user with the `admin` role. The
statistics cover every knowledge graph, so other keys get `403 Forbidden`.

**Response:**
```json
{
  "success": true,
  "data": {
    "knowledge_graphs": 3,
    "relations": 10,
    "views": 5,
    "memory_usage_bytes": 262144000,
    "query_count": 15000,
    "uptime_secs": 3600,
    "sessions": {
      "total": 5,
      "clean": 3,
      "dirty": 2,
      "total_ephemeral_facts": 100,
      "total_ephemeral_rules": 10
    }
  }
}
```

`views` counts persistent rules (derived relations) across knowledge graphs. Their rows are not stored; each is evaluated when a query reads it.

`memory_usage_bytes` is the server process's resident memory (0 on platforms
that do not report it).

### Prometheus Metrics

```http
GET /metrics/prometheus
Authorization: Bearer <admin-api-key>
```

Needs an admin API key, like `/metrics`. Returns metrics in Prometheus text
exposition format:

```
# HELP inputlayer_uptime_seconds Server uptime in seconds.
# TYPE inputlayer_uptime_seconds gauge
inputlayer_uptime_seconds 3600
# HELP inputlayer_queries_total Total queries executed.
# TYPE inputlayer_queries_total counter
inputlayer_queries_total 15000
# HELP inputlayer_kg_tuples Stored tuples, per knowledge graph.
# TYPE inputlayer_kg_tuples gauge
inputlayer_kg_tuples{kg="default"} 50000
# HELP inputlayer_store_read_only 1 once the store refuses writes until restart after a failed WAL write or fsync, else 0.
# TYPE inputlayer_store_read_only gauge
inputlayer_store_read_only 0
# HELP inputlayer_rejections_total Requests and connections refused before they ran, by reason.
# TYPE inputlayer_rejections_total counter
inputlayer_rejections_total{reason="http_rate_limit"} 0
...
```

See [Monitoring](deployment#monitoring) for every metric, a scrape
configuration and recommended alerts.

## Authentication

REST endpoints (except health/live/ready) require an API key in the Authorization header:

```http
Authorization: Bearer <api-key>
```

`/metrics` and `/metrics/prometheus` need an admin API key and answer other
keys with `403 Forbidden`.

API keys are managed via meta commands in the WebSocket session:

```iql
.apikey create my-service-key 90d
.apikey list
.apikey expire my-service-key 24h
.apikey revoke my-service-key
```

See [Authentication](authentication) for details.

## Error Responses

All errors use a consistent format:

```json
{
  "success": false,
  "error": {
    "code": "NOT_FOUND",
    "message": "Resource not found"
  }
}
```

**Error Codes:**

| Code | HTTP Status | Description |
|------|-------------|-------------|
| `NOT_FOUND` | 404 | Resource not found |
| `BAD_REQUEST` | 400 | Invalid request |
| `INTERNAL_ERROR` | 500 | Server error |
| `SERVICE_UNAVAILABLE` | 503 | Server not ready |

## Client Examples

### cURL - Health Check

```bash
# Check server health
curl http://localhost:8080/health

# Get server stats (admin API key)
curl -H "Authorization: Bearer $ADMIN_API_KEY" http://localhost:8080/metrics

# Get Prometheus metrics (admin API key)
curl -H "Authorization: Bearer $ADMIN_API_KEY" http://localhost:8080/metrics/prometheus
```

### cURL - With Authentication

```bash
# Authenticated request (metrics need an admin API key)
curl -H "Authorization: Bearer your-api-key" http://localhost:8080/metrics
```

### Kubernetes Probes

`deploy/kubernetes/base/statefulset.yaml` wires these up. It adds a startup
probe on `/live` that covers the WAL replay before the HTTP server starts:

```yaml
startupProbe:
  httpGet:
    path: /live
    port: http
  periodSeconds: 5
  failureThreshold: 120
livenessProbe:
  httpGet:
    path: /live
    port: http
  periodSeconds: 10
  timeoutSeconds: 3
  failureThreshold: 3
readinessProbe:
  httpGet:
    path: /ready
    port: http
  periodSeconds: 5
  timeoutSeconds: 3
  failureThreshold: 3
```
