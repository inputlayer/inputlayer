# WebSocket API

The WebSocket API provides live, bidirectional communication with InputLayer. It supports authentication, query execution, streaming results, session rules, and push notifications.

## Connection

Connect to the global WebSocket endpoint:

```
ws://host:port/ws
```

With TLS (via reverse proxy):

```
wss://host:port/ws
```

Optionally specify a knowledge graph via query parameter:

```
ws://host:port/ws?kg=mydb
```

## Authentication

The first message after connection must authenticate. There are two methods:

### Username/Password

```json
{
  "type": "login",
  "username": "admin",
  "password": "<the admin password>"
}
```

### API Key

```json
{
  "type": "authenticate",
  "api_key": "your-api-key"
}
```

### Auth Response

On success:

```json
{
  "type": "authenticated",
  "session_id": "a1b2c3d4",
  "knowledge_graph": "default",
  "version": "0.1.0",
  "role": "admin",
  "protocol_version": 3,
  "stream_epoch": "3f9c2a7e01b4d865"
}
```

`protocol_version` is the version of this protocol the server speaks (currently 3). `stream_epoch` identifies this run of the engine: notification `seq` numbers and knowledge graph revisions belong to it, and a restarted engine has a new one (see [Reconnection](#reconnection)).

On failure:

```json
{
  "type": "auth_error",
  "message": "Invalid credentials"
}
```

The server allows 30 seconds for authentication before closing the connection.

The connection stays bound to the credential it authenticated with. See [Authentication: Revocation](authentication#revocation) for which credential changes and key expiries end a session and how they affect in-flight results and writes.

## Executing Statements

Send any InputLayer statement or meta command:

```json
{
  "type": "execute",
  "program": "?edge(X, Y)"
}
```

The `program` field accepts any valid InputLayer statement: queries, inserts, rule definitions, meta commands, etc.

### Request IDs

Any request (`login`, `authenticate`, `execute`, `ping`) may carry an `id`, a non-empty string of at most 64 bytes:

```json
{"type": "execute", "id": "42", "program": "?edge(X, Y)"}
```

Every frame answering it echoes the `id`: `authenticated`, `auth_error`, `result`, `result_start`, `result_chunk`, `result_end`, `error` and `pong`. A request without an `id` gets replies without one. An `id` must be unique among your requests still awaiting a reply; it can be reused once answered. A request reusing an `id` that is still awaiting its reply gets an `invalid_request` error and does not run.

Frames you did not ask for never carry an `id` and have their own types, so they cannot be read as a reply: [notifications](#notifications), [standing-query pushes](#standing-queries) and [notices](#notices).

A request that is not a valid frame (bad JSON, unknown `type`, a missing field, or an `id` that is not a 1-64 byte string or appears twice) gets exactly one `error` with code `invalid_request`, carrying the `id` when it could be read. Nothing runs and the connection stays usable.

### Pipelining

A client may send several requests without waiting for each reply:

- **Replies come back in request order**, one reply (or one streamed `result_start` ... `result_end` sequence) per request, even when a later request finishes first.
- **Queries overlap.** A program made only of queries (`?...`) runs concurrently with the connection's other queries.
- **Everything else runs alone, in order**: inserts, deletes, rules, session rules and facts, meta commands such as `.kg use`, `.session clear`, `.subscribe` and `.unsubscribe`. Such a request starts only after every earlier request has replied, and no later request starts before it replies. A query sent after `.kg use other` therefore always reads `other`, and an insert sent after it always writes there.
- **Pushes are not held up by requests.** Notifications and subscription deltas are delivered while the connection's own requests run, between replies (never inside a streamed result).
- At most `http.rate_limit.ws_max_in_flight_requests` requests (default 16) are admitted and not yet answered; at that bound the server stops reading the connection until a reply goes out.
- Closing the connection abandons its running queries and stops their computation; a running write finishes before the session is closed.

### Deadlines and Cancellation

Every `execute` runs under **one deadline**, counted from when the server reads it: waiting behind earlier requests, waiting for a compute slot and computing all count against it. The deadline is `storage.performance.query_timeout_ms` (default 30 s), or the request's own `timeout_ms` when that is sooner:

```json
{"type": "execute", "id": "q1", "program": "?path(X, Y)", "timeout_ms": 2000}
```

`cancel` stops an unanswered request named by its `id`, wherever it is (still waiting behind other requests, or computing). It acts as soon as the server reads it, and is answered by `cancel_ack`, released in request order like any reply, so after the target's own reply:

```json
{"type": "cancel", "id": "c1", "target": "q1"}
{"type": "cancel_ack", "id": "c1", "target": "q1", "outcome": "cancelled"}
```

| `outcome` | Meaning |
|---|---|
| `cancelled` | The target stopped before it began committing. Nothing it would have changed is applied, it never runs later, and it replies with an `error` of code `cancelled`. |
| `too_late` | The target already finished or began committing. A commit is never interrupted; the target's reply reports what it committed. |
| `not_found` | No unanswered request on this connection has that `id` (already answered, never sent, or a `.subscribe`). |

A `cancel` is read like any other frame: while `http.rate_limit.ws_max_in_flight_requests` requests are unanswered the server reads nothing, so keep a slot free if you may need to cancel.

A request whose deadline passes is stopped the same way and fails with code `deadline_exceeded`; a write that already began committing completes and returns its result. Code `outcome_unknown` means the commit itself failed in a way that may have left the changes applied: read the state back before retrying.

Writes of facts are idempotent: inserting a fact that is present, or deleting one that is absent, changes nothing. After `cancelled`, `deadline_exceeded`, `outcome_unknown` or a lost connection, a client can resend the same write without duplicating it.

### Result Response

```json
{
  "type": "result",
  "columns": ["X", "Y"],
  "rows": [[1, 2], [2, 3], [3, 4]],
  "row_count": 3,
  "total_count": 3,
  "truncated": false,
  "execution_time_ms": 2,
  "errors": []
}
```

### Error Response

```json
{
  "type": "error",
  "message": "String value too long: 70000 bytes (max 65536)",
  "code": "validation"
}
```

A program of one statement that fails gets an `error`. `code` says why: `validation`, `not_found`, `conflict`, `unsupported` or `internal`; `invalid_request` and `rate_limited` reject a request before it runs; `deadline_exceeded`, `cancelled` and `outcome_unknown` are described in [Deadlines and Cancellation](#deadlines-and-cancellation); `store_read_only` refuses a write while the store is read-only after an unknown outcome; `resource_exhausted` refuses a query that went over `storage.performance.max_query_memory_bytes`, or a write that would grow its knowledge graph past `storage.performance.max_graph_memory_bytes`, and nothing was applied. It is absent for auth and other engine failures. For write outcomes and restart recovery, see [Persistence](persistence#wal-record-format).

### Statement Failures

A multi-statement program replies with a `result` (or `result_start`) whose `errors` lists each failure by 0-based statement index.

A program that changes facts, schemas or rules commits all of those changes as one transaction (see [Programs Commit Together](core-concepts#programs-commit-together)). An ordinary statement failure rolls back the program: it stops at that statement, `errors` names it, its message ends with `(rolled back: none of the program's N write statements A-B was applied)` when the program had other writes, no statement reports success, and the program's query does not run. An unknown commit outcome omits the rollback claim; follow the [persistence recovery guidance](persistence#wal-record-format). For example, an ordinary failure returns:

```json
{
  "type": "result",
  "columns": ["message"],
  "rows": [["Rule 'missing' not found: Failed to drop rule: Rule 'missing' does not exist (rolled back: none of the program's 2 write statements 0-1 was applied)"]],
  "errors": [{"index": 1, "code": "not_found", "message": "Rule 'missing' not found: Failed to drop rule: Rule 'missing' does not exist (rolled back: none of the program's 2 write statements 0-1 was applied)"}]
}
```

A program that writes may end with a `.why`, `.why full` or `.why_not`: its `result` keeps the statements' message rows and carries the proof in `proof_trees`, evaluated on the snapshot the writes committed against (see [Proofs of a Guarded Write](explainability#proofs-of-a-guarded-write)). A command that cannot join the transaction (`.kg use`, `.rel drop`, `.index`, `.compact`, inspection commands and the like), or a proof that is not the program's last statement, in a program that writes fails the program with code `unsupported` before any statement runs. A program without writes runs every statement and keeps going past a failure:

```json
{
  "type": "result",
  "columns": ["message"],
  "rows": [["Error: Failed to drop relation: Relation 'x' not found."], ["Relation 'y' dropped."]],
  "errors": [{"index": 0, "code": "not_found", "message": "Error: Failed to drop relation: Relation 'x' not found."}]
}
```

An empty `errors` means every statement succeeded. Do not match message text to detect failures.

### Statement Counts

A program that commits fact statements lists them in `statements`, in program order, with the tuples each one changed. The list rides on the reply even when the program ends with a query, whose rows are the `rows`:

```json
{
  "type": "result",
  "columns": ["message"],
  "rows": [["Inserted 1 fact(s) into 'task'."], ["Update: 0 deleted, 1 inserted."]],
  "errors": [],
  "statements": [
    {"index": 0, "kind": "insert", "inserted": 1, "deleted": 0},
    {"index": 1, "kind": "update", "inserted": 1, "deleted": 0}
  ]
}
```

`kind` is `insert`, `delete` or `update`. Counts are effective, as of the statements before it: inserting a fact that is present or deleting one that is absent is listed with zero counts. A conditional write that matched nothing is listed with zero counts too, so `inserted` of a guarded update says whether it landed. Schema and rule statements are not listed. `statements` is absent when the program committed no fact statement, including a program that failed and rolled back. Read counts from `statements`, not from the message rows.

## Knowledge Graph Operations

Use meta commands via execute:

```json
{"type": "execute", "program": ".kg create mydb"}
{"type": "execute", "program": ".kg use mydb"}
{"type": "execute", "program": ".kg list"}
{"type": "execute", "program": ".kg drop mydb"}
```

When `.kg use` switches knowledge graphs, the result includes a `switched_kg` field.

## Streaming Results

For large result sets (> 1MB serialized), the server automatically streams results in chunks:

### Stream Start

```json
{
  "type": "result_start",
  "columns": ["X", "Y"],
  "total_count": 50000,
  "truncated": false,
  "execution_time_ms": 245
}
```

### Stream Chunk

```json
{
  "type": "result_chunk",
  "rows": [[1, 2], [2, 3]],
  "chunk_index": 0
}
```

Each chunk contains at most 500 rows and about 1 MiB; a row bigger than that gets a chunk of its own. Chunks are sent in order of `chunk_index`, from 0.

### Stream End

```json
{
  "type": "result_end",
  "row_count": 50000,
  "chunk_count": 100
}
```

Small results (< 1MB) use the single `result` message, maintaining backward compatibility.

A streamed result is complete only at `result_end`: check that the chunks arrived in order and add up to its `row_count` and `chunk_count` before using it. If an `error` with the request's `id` arrives instead, the request failed: discard the rows received. A connection that closes mid-stream delivered no result.

No frame exceeds the 16 MiB message limit. A result with a single row larger than that cannot be delivered; the server answers with an `error` before sending any part of it.

## Session Rules

Session rules are ephemeral rules scoped to the current WebSocket connection. They are automatically cleared when the connection closes.

### Define Session Rule

Session rules omit the `+` prefix:

```json
{
  "type": "execute",
  "program": "temp(X, Y) <- edge(X, Y), X < Y"
}
```

### Session Facts

Insert transient facts scoped to the session:

```json
{
  "type": "execute",
  "program": "context(\"user\", \"alice\")"
}
```

### Query with Session Rules

Session rules are automatically included when querying:

```json
{
  "type": "execute",
  "program": "?temp(X, Y)"
}
```

### Clear Session

```json
{
  "type": "execute",
  "program": ".session clear"
}
```

## Notifications

The server pushes notifications when persistent data changes in the session's knowledge graph. `kg_change` notifications for other knowledge graphs go to admin sessions only, and changes to the internal `_internal` knowledge graph are never sent. Replay on reconnect (`last_seq` with `epoch`) applies the same rules. Revoking a user's access to the knowledge graph (`.kg acl revoke`) stops its notifications and subscription deltas on live connections at once; a delta withheld this way is replaced by a `subscription_error`. The subscription keeps the last result it received, so once access is restored its next delta is relative to that result and its `seq` continues without a gap.

### Persistent Update

Sent when base facts in a relation change, once per changed relation for each committed transaction, after the change is visible to queries. `operation` is `insert` or `delete` when the transaction only added or only removed facts of the relation, and `update` when it did both; `count` is the number of facts added plus removed. A transaction that changes nothing (only duplicates, or changes that cancel out) and a failed one send nothing.

```json
{
  "type": "persistent_update",
  "knowledge_graph": "default",
  "relation": "edge",
  "operation": "insert",
  "count": 5,
  "timestamp_ms": 1700000000000,
  "seq": 42
}
```

### Rule Change

Sent when a rule is registered, removed, or dropped:

```json
{
  "type": "rule_change",
  "knowledge_graph": "default",
  "rule_name": "reachable",
  "operation": "registered",
  "timestamp_ms": 1700000000000,
  "seq": 43
}
```

### KG Change

Sent when a knowledge graph is created or dropped:

```json
{
  "type": "kg_change",
  "knowledge_graph": "mydb",
  "operation": "created",
  "timestamp_ms": 1700000000000,
  "seq": 44
}
```

### Schema Change

Sent when a relation is dropped:

```json
{
  "type": "schema_change",
  "knowledge_graph": "default",
  "entity": "edge",
  "operation": "dropped",
  "timestamp_ms": 1700000000000,
  "seq": 45
}
```

The `seq` field is the notification's position in the engine's notification stream: strictly increasing in the order notifications are delivered, from 1, within one `stream_epoch`. Each connection sees the notifications visible to it, so the numbers it sees increase but may skip. Notification `seq` is unrelated to a subscription delta's `seq`.

## Standing Queries

A standing query keeps a query's result current: after each committed change that can affect it, the server pushes the rows that entered and left the result. Use it to react to *derived* conclusions without polling.

### Subscribe

```json
{"type": "execute", "program": ".subscribe late_orders ?late(Order, Customer)"}
```

The reply is a normal [result](#result-response) holding the initial snapshot, plus `subscribed`:

```json
{"type": "result", "columns": ["Order", "Customer"], "rows": [[1007, "globex"]],
 "subscribed": {"subscription": "late_orders", "generation": 3, "revision": 16},
 "errors": [], "...": "..."}
```

The subscription is bound to the connection and to its current knowledge graph. Its `generation` is unique per connection and is carried by every push for it, so after `.unsubscribe` and a new `.subscribe` with the same name, a push with the old generation is recognizably stale.

`revision` is the knowledge graph revision the snapshot is the exact answer at. Every commit published after it reaches the subscription, even one that lands while the snapshot is being taken, so the snapshot plus the deltas that follow always ends at the current result. Revisions are comparable only within one knowledge graph and one `stream_epoch`.

`<id>` is client-chosen: 1-128 characters from `[A-Za-z0-9_.:-]`, unique per connection.

A large snapshot is [streamed](#streaming-results) like any result, with `subscribed` on its `result_start`; it counts only once its `result_end` arrives. A snapshot that cannot be delivered whole (a row larger than the 16 MiB message limit) fails the `.subscribe` with an `error`, and nothing is registered.

### Delta

```json
{
  "type": "subscription_delta",
  "subscription": "late_orders",
  "generation": 3,
  "knowledge_graph": "default",
  "seq": 1,
  "revision": 17,
  "columns": ["Order", "Customer"],
  "inserted": [[1042, "acme"]],
  "retracted": [[1007, "globex"]]
}
```

- Set semantics: `inserted` and `retracted` are the difference between consecutive result sets, each sorted. Applying every delta to the snapshot reproduces the current result.
- `seq` starts at 1 per subscription and increases by one per delta. A gap means a delta was lost: resubscribe. Unchanged results push nothing.
- `revision` is the knowledge graph revision the result reaches with this delta; it increases with every delta. Coalesced commits produce one delta at the latest revision.
- Triggers: inserts, deletes, rule add/drop/remove, and relation drop on any relation the query depends on (its body plus, transitively, the bodies of the persistent rules defining them). Writes to other relations cause no evaluation.
- Sharing: subscriptions to the same query on the same knowledge graph share one evaluation and one result in memory, across connections and users, so a hundred agents watching one query cost the server about as much as one. Each subscriber's read access is checked when it subscribes, again before its snapshot is sent, and before every push, so a shared result never reaches a subscriber who may not read the knowledge graph. This is sound because access is granted per knowledge graph: every reader of a query sees the same rows. A rule change that can affect a shared query stops new subscribers from joining it: a `.subscribe` sent after the rule change's reply always gets a fresh evaluation under the new rules, while existing subscribers receive the refresh as a delta. Likewise, a `.subscribe` sent after a write's reply always gets a snapshot that includes that write: a new subscriber shares the current result at once only when no refresh of it is running or due, and otherwise waits for a refresh that has seen the write. The query text is compared exactly (after trimming): a differently spelled query, for example with other variable names, is evaluated separately.
- Bound constants: subscriptions whose queries differ only in string or integer constants of positive atoms, such as one per session (`?speech("s-1", G, T)` and `?speech("s-2", G, T)`), share one evaluation per commit. The server evaluates the query once with the constants as variables and gives each subscription exactly the rows of its own constants, matched as the engine matches a constant. The deltas, revisions, errors and access checks are those of the subscription's own query. A subscription evaluates its own query when it starts, after a rule change, and whenever the shared evaluation fails or holds more rows for it than `max_result_rows`. Negated atoms, comparisons and float or boolean constants are not shared in this way: queries that differ in them are evaluated separately. A shape never shares while its subscriptions are no more than the server's query threads: their own evaluations then all run at once, and the shared one is no faster. Once a subscription's own evaluation has been timed and the shape has more subscriptions than query threads, the server tries the shared evaluation in the background, one try at a time and without taking a query thread, so no delta waits for it, and starts sharing only if it is no slower than the subscriptions' own evaluations run in parallel on the server's query threads. Sharing lasts while that holds on average over recent shared evaluations: when they are slower (the constants restrict the work a lot), the server evaluates the subscriptions separately and tries sharing again later, waiting longer after each failed try. A server with fewer than three query threads makes no such tries: it shares at once, and still stops sharing when shared evaluations are slower. A shape whose constant binds a relation that reads a recursive relation is never evaluated shared, whatever the server: the constant restricts the work a lot, and the shared evaluation could compute the whole closure. A rule change stops sharing and starts the comparison over under the new rules, including whether a constant binds a recursive relation. `subscriptions.share_parameterized = false` turns this off.
- Plans: a standing query is compiled once and its plan is reused on every re-evaluation until the persistent rules change.
- Coalescing: at most one evaluation runs per shared query. Commits that land meanwhile trigger one follow-up evaluation, so a burst produces few deltas and the last one always reflects the final state. With `http.rate_limit.subscription_coalesce_ms` above 0 (default 0, at most 100), a query also waits that long after the first relevant commit before evaluating, so commits inside the window share one evaluation; each delta is then delayed by up to the window. A connection that reads slowly gets one combined delta for the commits it fell behind on, not a queue of them.
- Evaluation runs off the connection's read loop and off the write path.

### Streamed Deltas

A delta whose frame would exceed 1 MiB arrives as one logical delta in several frames: a `subscription_delta_start` with everything but the rows, `subscription_delta_chunk`s of at most 500 rows and about 1 MiB, and a `subscription_delta_end` with the counts the chunks must add up to:

```json
{"type": "subscription_delta_start", "subscription": "late_orders", "generation": 3,
 "knowledge_graph": "default", "seq": 2, "revision": 18, "columns": ["Order", "Customer"]}
{"type": "subscription_delta_chunk", "subscription": "late_orders", "generation": 3, "seq": 2,
 "chunk_index": 0, "inserted": [[1043, "initech"]], "retracted": []}
{"type": "subscription_delta_end", "subscription": "late_orders", "generation": 3, "seq": 2,
 "chunk_count": 1, "inserted_count": 1, "retracted_count": 0}
```

- Buffer the chunks and apply the delta only at its end, after checking that `chunk_index` ran from 0 without gaps or repeats and that the rows match `inserted_count` and `retracted_count`. Until then the result stays at its previous revision.
- The stream's frames arrive in order; replies, notifications and other subscriptions' pushes may arrive between them.
- A stream that breaks those rules leaves the result unknown: unsubscribe and subscribe again. If the connection closes mid-stream, nothing of that delta applied.

### Errors

If re-evaluation fails, or the subscriber may no longer read the knowledge graph (`.kg acl revoke`), the server pushes:

```json
{"type": "subscription_error", "subscription": "late_orders", "generation": 3, "message": "Access denied"}
```

The subscription stays registered; its next delta is relative to the last result it received. A subscriber that had not yet received the last complete result before the failure (it was reading slowly) first gets that result as a delta, then the error.

A result cut at `storage.performance.max_result_rows` is incomplete, so it is never delivered as a snapshot or diffed into a delta. When a re-evaluation's result grows past the cap, the server pushes a `subscription_error` naming the cap and keeps the last complete result. Once the result fits again, the next delta is relative to that last complete result, so applying it restores the current set.

`.subscribe` replies with an `error` when the id is taken, the per-connection limit is reached, the query uses `limit`/`offset`, the result exceeds `max_result_rows`, or the user lacks read access to the knowledge graph (the same check as a query, repeated before the snapshot is sent). When the latest evaluation of a shared query failed, a new `.subscribe` re-evaluates it (once for all subscribers arriving meanwhile) instead of repeating the old error; if it fails again with the same error, only the new subscribers are told, and existing subscribers get no duplicate `subscription_error`.

### Reset

When the server cannot deliver a subscription's next change whole (a row larger than the 16 MiB message limit), it removes the subscription and pushes:

```json
{"type": "subscription_reset", "subscription": "late_orders", "generation": 3,
 "message": "Delta 4 has a row of 17000000 bytes, over the 16777216-byte message limit. The subscription was removed; subscribe again."}
```

The rows you hold for that subscription are no longer kept current; discard them, including a streamed delta in progress, and `.subscribe` again for a fresh snapshot. Nothing more is pushed for that generation, and the id is free.

### Unsubscribe

```json
{"type": "execute", "program": ".unsubscribe late_orders"}
```

Subscriptions are also removed when the connection closes and when it switches knowledge graph (`.kg use`, `.kg create`). The switch removes them silently: re-subscribe in the new knowledge graph.

### Scope and limits

- Subscriptions see **persistent data only**: session facts and session rules are excluded, as with `.why`.
- At most `http.rate_limit.ws_max_subscriptions` per connection (default 64, 0 = unlimited).
- No frame exceeds the 16 MiB message limit: large snapshots and deltas are streamed, and a change that still cannot be delivered (a single row over the limit) resets the subscription.
- The server writes one frame at a time. A client that leaves a frame unread for `http.ws_send_timeout_ms` (default 30 seconds) is disconnected, so a client that stops reading holds no server resources and never delays other connections.

## Keep-Alive

Send a ping to keep the connection alive:

```json
{"type": "ping"}
```

Response:

```json
{"type": "pong"}
```

The server also sends WebSocket-level pings every 30 seconds to detect dead connections.

## Connection Lifecycle

1. **Connect** to `ws://host:port/ws`
2. **Authenticate** with `login` or `authenticate`
3. **Execute** statements and queries
4. **Receive** notifications for data changes and subscription deltas
5. **Close** gracefully by sending a WebSocket Close frame

### Graceful Close

Always send a Close frame before disconnecting to avoid server warnings:

```python
# Python
await websocket.close()
```

```javascript
// JavaScript
ws.close(1000, "Normal closure");
```

## Notices

The server announces connection events with a `notice`, never with an `error`:

```json
{"type": "notice", "code": "idle_timeout", "message": "Idle timeout"}
```

| `code` | Meaning |
|---|---|
| `notifications_missed` | The client read too slowly and change notifications were dropped. The connection stays open; subscription deltas are unaffected. |
| `replay_gap` | The reconnect cursor (`last_seq` with `epoch`) could not be honoured: it is from another engine run, names no epoch, or notifications after it are no longer retained. Nothing was replayed; re-read the state you track. The connection stays open. |
| `slow_consumer` | Too many notifications were dropped; the connection closes. |
| `idle_timeout` | No request within `http.ws_idle_timeout_ms`; the connection closes. |
| `lifetime_exceeded` | The connection reached `http.rate_limit.ws_max_lifetime_secs`; it closes. |
| `auth_timeout` | No authentication in time; the connection closes. |
| `credential_revoked` | The connection's credential was revoked; it closes. |
| `credential_expired` | The connection's API key expired; it closes. |
| `server_shutdown` | The server is stopping; the connection closes. |

## Reconnection

If the connection drops:

1. Wait with exponential backoff (1s, 2s, 4s, 8s, max 30s)
2. Reconnect and re-authenticate
3. Session rules, facts, and subscriptions are lost - re-create them after reconnecting. A new `.subscribe` returns a fresh snapshot; subscription state never carries across connections.
4. Persistent data (facts, rules, indexes) is unaffected
5. To catch up on change notifications, connect with the last `seq` you saw and the `stream_epoch` it belongs to:

```
ws://host:port/ws?kg=mydb&last_seq=42&epoch=3f9c2a7e01b4d865
```

The server replays the retained notifications after `seq` 42, then continues live, with nothing skipped or repeated in between. If it cannot (the engine restarted, the cursor names no epoch, or the notifications were evicted from the server's bounded ring of `http.rate_limit.notification_buffer_size`), it sends one `replay_gap` notice and replays nothing: re-read the state you track. Notifications are not a durable history.

## Rate Limiting

The server applies per-connection rate limiting (default: 1000 messages/sec, configurable). Exceeding the limit returns:

```json
{
  "type": "error",
  "id": "42",
  "message": "Rate limit exceeded (1000 msgs/sec)",
  "code": "rate_limited"
}
```

## Example: Python Client

```python
import asyncio
import json
import os
import websockets

async def main():
    async with websockets.connect("ws://localhost:8080/ws") as ws:
        # Authenticate
        await ws.send(json.dumps({
            "type": "authenticate",
            "api_key": os.environ["INPUTLAYER_API_KEY"]
        }))
        auth_resp = json.loads(await ws.recv())
        assert auth_resp["type"] == "authenticated"
        print(f"Session: {auth_resp['session_id']}")

        # Insert data
        await ws.send(json.dumps({
            "type": "execute",
            "program": "+edge[(1, 2), (2, 3), (3, 4)]"
        }))
        result = json.loads(await ws.recv())

        # Query
        await ws.send(json.dumps({
            "type": "execute",
            "program": "?edge(X, Y)"
        }))
        result = json.loads(await ws.recv())
        print(f"Got {result['row_count']} rows")

        # Close gracefully
        await ws.close()

asyncio.run(main())
```

## Example: JavaScript Client

```javascript
const ws = new WebSocket("ws://localhost:8080/ws");

ws.onopen = () => {
  ws.send(JSON.stringify({
    type: "authenticate",
    api_key: process.env.INPUTLAYER_API_KEY
  }));
};

ws.onmessage = (event) => {
  const msg = JSON.parse(event.data);

  if (msg.type === "authenticated") {
    // Authenticated - start querying
    ws.send(JSON.stringify({
      type: "execute",
      program: "?edge(X, Y)"
    }));
  }

  if (msg.type === "result") {
    console.log(`Query returned ${msg.row_count} rows`);
  }

  // Handle streaming results
  if (msg.type === "result_start") {
    console.log(`Streaming ${msg.total_count} rows...`);
  }
  if (msg.type === "result_chunk") {
    console.log(`Received chunk ${msg.chunk_index}`);
  }
  if (msg.type === "result_end") {
    console.log(`Stream complete: ${msg.row_count} rows`);
  }

  // Handle notifications
  if (msg.type === "persistent_update") {
    console.log(`${msg.relation}: ${msg.operation} ${msg.count} rows`);
  }
};
```
