# Deployment

Run InputLayer in production with Docker, systemd, reverse proxies, and Kubernetes.

## Quick Reference

| Setting | Default | CLI Flag | Env Variable | Config Key |
|---|---|---|---|---|
| Host | `127.0.0.1` | `--host` | `INPUTLAYER_HTTP__HOST` | `http.host` |
| Port | `8080` | `--port` | `INPUTLAYER_HTTP__PORT` | `http.port` |
| Data directory | `./data` | `--data-dir` | `INPUTLAYER_STORAGE__DATA_DIR` | `storage.data_dir` |
| Log level | `info` | -- | `INPUTLAYER_TRACE_LEVEL` | `logging.level` |
| Log format | `text` | -- | `INPUTLAYER_TRACE_JSON=1` | `logging.format` |
| Admin password (12+ characters) | generated | -- | `INPUTLAYER_ADMIN_PASSWORD` | `http.auth.bootstrap_admin_password` |
| Config file | `config.toml` | `--config` | -- | -- |

## Environment Variables

InputLayer uses the `INPUTLAYER_` prefix with double-underscore separators for nested keys.
Environment variables override values from config files.

```bash
# Server binding
export INPUTLAYER_HTTP__HOST=0.0.0.0
export INPUTLAYER_HTTP__PORT=8080

# Storage
export INPUTLAYER_STORAGE__DATA_DIR=/var/lib/inputlayer/data
export INPUTLAYER_STORAGE__AUTO_CREATE_KNOWLEDGE_GRAPHS=true

# Persistence
export INPUTLAYER_STORAGE__PERSIST__ENABLED=true
export INPUTLAYER_STORAGE__PERSIST__DURABILITY_MODE=immediate

# Logging (via tracing)
export INPUTLAYER_TRACE_LEVEL=info          # trace, debug, info, warn, error
export INPUTLAYER_TRACE_JSON=1              # JSON structured logging
export INPUTLAYER_TRACE_FILE=/var/log/inputlayer/server.log  # Log to file instead of stderr

# Authentication
export INPUTLAYER_ADMIN_PASSWORD=your-secure-password

# Performance
export INPUTLAYER_STORAGE__PERFORMANCE__NUM_THREADS=4
export INPUTLAYER_STORAGE__PERFORMANCE__QUERY_TIMEOUT_MS=30000
```

## Configuration File

Create a `config.toml` for persistent configuration. Pass a custom path with `--config`:

```bash
inputlayer-server --config /etc/inputlayer/config.toml
```

Example production configuration:

```toml
[storage]
data_dir = "/var/lib/inputlayer/data"
default_knowledge_graph = "default"
auto_create_knowledge_graphs = false
max_knowledge_graphs = 100

[storage.persist]
enabled = true
durability_mode = "immediate"
buffer_size = 10000
max_wal_size_bytes = 67108864       # 64 MB

[storage.performance]
num_threads = 0                     # 0 = all available CPU cores
query_timeout_ms = 30000            # 30 seconds
max_query_size_bytes = 1048576      # 1 MB
max_insert_tuples = 10000
max_result_rows = 100000
slow_query_log_ms = 5000
max_query_memory_bytes = 8589934592 # 8 GiB per query; refused past it
max_graph_memory_bytes = 4294967296 # 4 GiB of facts per graph
max_total_query_memory_bytes = 12884901888 # 12 GiB for all queries at once (32 GB host)

[logging]
level = "info"
format = "json"

[http]
host = "0.0.0.0"
port = 8080
shutdown_timeout_secs = 30

[http.auth]
session_timeout_secs = 86400        # 24 hours

[http.rate_limit]
max_connections = 10000
max_ws_connections = 5000
ws_max_messages_per_sec = 1000
per_ip_max_rps = 100

[http.gui]
enabled = true
static_dir = "/var/lib/inputlayer/gui/dist"
```

## Health Checks

InputLayer exposes three probe endpoints. All bypass authentication.

| Endpoint | Method | Purpose | Healthy Response |
|---|---|---|---|
| `/health` | GET | General health check | `200 OK` |
| `/live` | GET | Kubernetes liveness probe | `200 OK` |
| `/ready` | GET | Kubernetes readiness probe | `200 OK` (or `503` if storage is unavailable) |

All endpoints are also available under the `/v1/` prefix (e.g., `/v1/health`).

Example health check:

```bash
curl -sf http://localhost:8080/health
```

## Monitoring

The server exports Prometheus metrics at `/metrics/prometheus` (also
`/v1/metrics/prometheus`) and the same headline numbers as JSON at `/metrics`.

### Authentication

Both endpoints need an **admin API key**: an unscoped key of a user with the
`admin` role. The metrics count every knowledge graph on the server, so keys
of editors and viewers, and keys scoped to one knowledge graph (even an
admin's), get `403 Forbidden`. A missing or invalid key gets `401`.

Give the scraper its own admin user and key, so you can revoke its access
without touching anyone else's:

```iql
.user create monitoring <a-password-of-12-or-more-characters> admin
```

Log in as `monitoring`, then create the key and store it where only
Prometheus can read it:

```iql
.apikey create prometheus-scrape
```

### Scrape Configuration

```yaml
scrape_configs:
  - job_name: inputlayer
    metrics_path: /metrics/prometheus
    scrape_interval: 30s
    scrape_timeout: 10s
    authorization:
      type: Bearer
      credentials_file: /etc/prometheus/secrets/inputlayer-api-key
    static_configs:
      - targets: ["inputlayer.internal:8080"]
```

A scrape reads every knowledge graph's counts without loading any from disk.
It gives up with a `500` after `http.stats_timeout_secs` (default 5), for
example while a long write holds the storage lock. Counters start at zero
when the server starts.

Metrics without labels are one value for the whole server. `kg` labels carry

| `inputlayer_kg_relations{kg}`, `inputlayer_kg_views{kg}`, `inputlayer_kg_tuples{kg}` | gauge | The same, per knowledge graph. |
| `inputlayer_kg_loaded{kg}` | gauge | 1 while the knowledge graph is in memory. |
| `inputlayer_kg_sessions{kg}` | gauge | Open sessions bound to the knowledge graph. |
| `inputlayer_sessions_total`, `_clean`, `_dirty` | gauge | Open sessions; dirty ones hold session facts or rules. |

| Metric | Type | Meaning |
|---|---|---|
| `inputlayer_memory_usage_bytes` | gauge | Resident memory (RSS) of the server process. Linux only. |
| `inputlayer_memory_limit_bytes` | gauge | The memory limit of the server's cgroup (container or systemd `MemoryMax=`). Absent without one. |
| `inputlayer_query_memory_bytes` | gauge | Memory the queries running now hold. |
| `inputlayer_query_memory_budget_bytes` | gauge | `max_total_query_memory_bytes` in effect (0: no limit). |
| `inputlayer_compute_permits` | gauge | Computations that run at once over every lane; more wait for a permit on their lane. |
| `inputlayer_compute_permits_in_use` | gauge | Computations holding a permit now. |
| `inputlayer_admission_running{lane}`, `inputlayer_admission_queued{lane}` | gauge | Computations holding a permit, and requests waiting for one, on each lane (`interactive`, `write`, `background`, `probe`; see [Admission and lanes](#admission-and-lanes)). |
| `inputlayer_admission_admitted_total{lane}` | counter | Requests admitted to compute, by lane. |
| `inputlayer_admission_refused_total{lane,reason}` | counter | Requests refused with `overloaded`: `queue_full` (the lane's `max_queued`) or `timeout` (no permit within `max_wait_ms`). |
| `inputlayer_admission_stopped_waiting_total{lane}` | counter | Requests whose deadline passed, or that were cancelled, while they waited for a permit. |
| `inputlayer_admission_wait_seconds_total{lane}`, `inputlayer_admission_held_seconds_total{lane}` | counter | Time requests spent waiting for a permit, and time computations held one, summed by lane. `rate(wait)/rate(admitted)` is a lane's mean queueing delay. |
| `inputlayer_query_{parse,optimize,execute,total}_seconds` | histogram | Query latency by phase (see [Query Profiling](query-profiling)). |
| `inputlayer_rule_evaluations_total`, `inputlayer_view_reads_total`, `inputlayer_view_maintenance_us_total` | counter | How reads of persistent rules were answered: by evaluating the rules, or from a view, and the microseconds spent keeping views current (see [Query Profiling](query-profiling#prometheus-metrics)). |

| Metric | Type | Meaning |
|---|---|---|
| `inputlayer_wal_size_bytes` | gauge | Size of the write-ahead log. |
| `inputlayer_wal_size_limit_bytes` | gauge | `max_wal_size_bytes`: past it, the next commit flushes every shard (0: no limit). |
| `inputlayer_persist_dirty_shards` | gauge | Relations with committed changes not yet flushed to batch files. |

### Recommended Alerts

Starting points; tune the thresholds to your traffic.

| Alert | Expression | For | Severity |
|---|---|---|---|
| Server down | `up{job="inputlayer"} == 0` | 2m | page |
| Store read-only | `inputlayer_store_read_only == 1` | 0m | page |
| Engine faults | `sum(rate(inputlayer_ws_errors_total{code=~"internal\|outcome_unknown\|store_read_only"}[5m])) > 0` | 5m | page |
| Flushes failing | `increase(inputlayer_persist_flush_failures_total[15m]) > 0` | 0m | ticket |
| WAL not draining | `inputlayer_wal_size_limit_bytes > 0 and inputlayer_wal_size_bytes > 2 * inputlayer_wal_size_limit_bytes` | 15m | ticket |
| Memory near limit | `inputlayer_memory_usage_bytes / inputlayer_memory_limit_bytes > 0.85` | 10m | ticket (page above 0.95) |
| Query memory saturated | `inputlayer_query_memory_budget_bytes > 0 and inputlayer_query_memory_bytes / inputlayer_query_memory_budget_bytes > 0.9` | 5m | ticket |
| Queries refused for memory | `rate(inputlayer_ws_errors_total{code="resource_exhausted"}[5m]) > 0` | 15m | ticket |
| Compute saturated | `inputlayer_compute_permits_in_use >= inputlayer_compute_permits` | 10m | ticket |
| Requests refused as overloaded | `rate(inputlayer_admission_refused_total[5m]) > 0` | 5m | page |
| A lane queueing | `rate(inputlayer_admission_wait_seconds_total{lane="interactive"}[5m]) / rate(inputlayer_admission_admitted_total{lane="interactive"}[5m]) > 0.5` | 10m | ticket |
| Deadlines missed | `rate(inputlayer_ws_errors_total{code="deadline_exceeded"}[5m]) / rate(inputlayer_queries_total[5m]) > 0.01` | 10m | ticket |
| Connections near limit | `inputlayer_ws_connections_limit > 0 and inputlayer_ws_connections / inputlayer_ws_connections_limit > 0.8` | 10m | ticket |
| Connections refused | `sum(rate(inputlayer_rejections_total{reason=~"http_connection_limit\|ws_connection_limit"}[5m])) > 0` | 5m | ticket |
| Authentication attack or broken client | `sum(rate(inputlayer_auth_failures_total[5m])) > 1` or `increase(inputlayer_rejections_total{reason="login_throttled"}[15m]) > 10` | 10m | ticket |
| Slow consumers | `increase(inputlayer_ws_notices_total{code="slow_consumer"}[15m]) + increase(inputlayer_ws_send_timeouts_total[15m]) > 0` | 0m | info |
| Server errors | `sum(rate(inputlayer_http_responses_total{code=~"5.."}[5m])) > 0` | 10m | ticket |
| Restarted | `inputlayer_uptime_seconds < 600` | 0m | info |

## Docker

InputLayer provides a multi-stage Dockerfile that produces a minimal Debian-based image.

### Build the Image

```bash
docker build -t inputlayer:latest .
```

### Run a Container

```bash
docker run -d \
  --name inputlayer \
  -p 8080:8080 \
  -v inputlayer-data:/var/lib/inputlayer/data \
  -e INPUTLAYER_ADMIN_PASSWORD \
  inputlayer:latest
```

`-e INPUTLAYER_ADMIN_PASSWORD` passes the admin password from your shell's environment (set it from your secret store, not on the command line). A supplied password needs at least 12 characters or the first boot refuses to start (once the admin exists a short one only draws a warning); an empty one counts as unset. Without it, the first boot generates the password and an admin API key and saves them to `/var/lib/inputlayer/data/credentials.toml` (see [Credentials](installation#credentials)).

The image includes a built-in `HEALTHCHECK` that polls `/health` every 10 seconds:

```dockerfile
HEALTHCHECK --interval=10s --timeout=3s --start-period=5s --retries=3 \
    CMD curl -sf http://localhost:8080/health || exit 1
```

### Image Details

The image runs as a non-root `inputlayer` user with the following defaults:

| Setting | Value |
|---|---|
| Binary | `/usr/local/bin/inputlayer-server` |
| Backup tool | `/usr/local/bin/inputlayer-backup` ([Backup and Restore](backup)) |
| Data volume | `/var/lib/inputlayer/data` |
| GUI assets | `/var/lib/inputlayer/gui/dist/`, served at `/` (`INPUTLAYER_HTTP__GUI__ENABLED=false` turns it off) |
| Exposed port | `8080` |
| User | `inputlayer`, uid/gid `999` (non-root) |

### Custom Configuration in Docker

Mount a config file and pass it via the CLI:

```bash
docker run -d \
  --name inputlayer \
  -p 8080:8080 \
  -v inputlayer-data:/var/lib/inputlayer/data \
  -v ./config.toml:/etc/inputlayer/config.toml:ro \
  inputlayer:latest \
  --config /etc/inputlayer/config.toml
```

## systemd

Create a systemd service for running InputLayer on a bare-metal or VM deployment.

### Create a System User

```bash
sudo useradd -r -s /bin/false -m -d /var/lib/inputlayer inputlayer
sudo mkdir -p /var/lib/inputlayer/data
sudo chown inputlayer:inputlayer /var/lib/inputlayer/data
```

### Install the Binary

```bash
sudo cp target/release/inputlayer-server /usr/local/bin/
sudo chmod 755 /usr/local/bin/inputlayer-server
```

### Create the Service File

Write the following to `/etc/systemd/system/inputlayer.service`:

```ini
[Unit]
Description=InputLayer
After=network-online.target
Wants=network-online.target

[Service]
Type=simple
User=inputlayer
Group=inputlayer
ExecStart=/usr/local/bin/inputlayer-server \
    --host 0.0.0.0 \
    --port 8080 \
    --config /etc/inputlayer/config.toml \
    --data-dir /var/lib/inputlayer/data
Restart=on-failure
RestartSec=5
LimitNOFILE=65536

# Security hardening
ProtectSystem=strict
ProtectHome=true
ReadWritePaths=/var/lib/inputlayer/data
PrivateTmp=true
NoNewPrivileges=true
ProtectKernelTunables=true
ProtectControlGroups=true

# Environment
Environment=INPUTLAYER_TRACE_LEVEL=info
Environment=INPUTLAYER_TRACE_JSON=1
Environment=INPUTLAYER_TRACE_FILE=/var/log/inputlayer/server.log

[Install]
WantedBy=multi-user.target
```

### Enable and Start

```bash
sudo mkdir -p /var/log/inputlayer
sudo chown inputlayer:inputlayer /var/log/inputlayer

sudo systemctl daemon-reload
sudo systemctl enable inputlayer
sudo systemctl start inputlayer

# Check status
sudo systemctl status inputlayer
sudo journalctl -u inputlayer -f
```

## TLS and Reverse Proxies

InputLayer does not terminate TLS natively. Use a reverse proxy for TLS termination in production.

### Nginx

```nginx
server {
    listen 443 ssl;
    server_name inputlayer.example.com;
    ssl_certificate     /etc/ssl/certs/inputlayer.crt;
    ssl_certificate_key /etc/ssl/private/inputlayer.key;
    ssl_protocols       TLSv1.2 TLSv1.3;
    location / {
        proxy_pass http://127.0.0.1:8080;
        proxy_http_version 1.1;
        proxy_set_header Upgrade $http_upgrade;
        proxy_set_header Connection "upgrade";
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
        proxy_read_timeout 300s;
        proxy_send_timeout 300s;
    }
}
```

The `proxy_read_timeout` and `proxy_send_timeout` values of 300 seconds accommodate long-running WebSocket connections. The `Upgrade` and `Connection` headers are required for WebSocket support.

For HTTP-to-HTTPS redirect, add a companion server block:

```nginx
server {
    listen 80;
    server_name inputlayer.example.com;
    return 301 https://$host$request_uri;
}
```

### Caddy

Caddy automatically provisions and renews TLS certificates via Let's Encrypt:

```caddyfile
inputlayer.example.com {
    reverse_proxy 127.0.0.1:8080 {
        header_up X-Real-IP {remote_host}
    }
}
```

No additional TLS configuration is needed. Caddy handles certificates, HTTPS redirect, and WebSocket upgrades automatically.

## Kubernetes

The repository ships Kustomize manifests in `deploy/kubernetes/`. Install one
engine per tenant: each tenant gets its own namespace, volume and engine.

| Path | Contents |
|---|---|
| `base/statefulset.yaml` | The engine: one replica, non-root, probes, graceful shutdown |
| `base/pvc.yaml` | `inputlayer-data`, the engine's `ReadWriteOnce` volume |
| `base/service.yaml` | `inputlayer`, a ClusterIP Service on port `8080` |
| `base/configmap.yaml` | `config.toml`, mounted at `/etc/inputlayer/config.toml` |
| `components/ingress/` | Optional ingress-nginx Ingress with TLS |
| `overlays/tenant-example/` | A per-tenant overlay: namespace, image tag, Ingress host |
| `maintenance/maintenance-pod.yaml` | Offline volume access for [backup and restore](#backup-and-restore) |

### Install a Tenant

Copy `overlays/tenant-example` to a directory of your own. Then set the
namespace, pin the image tag and set the Ingress host. If the tenant has no
public endpoint, drop the `components` entry and the Ingress patch. Then:

```bash
kubectl apply -f my-overlays/acme/namespace.yaml
kubectl -n inputlayer-acme create secret generic inputlayer-secrets \
  --from-literal=admin-password='your-secure-password' \
  --from-literal=bootstrap-api-key='your-agent-api-key'   # optional
kubectl apply -k my-overlays/acme
kubectl -n inputlayer-acme rollout status statefulset/inputlayer
```

Both secrets need at least 12 characters; with a shorter one on first boot the engine refuses to start and the pod restarts until you fix the secret. Once the admin exists, a short one is ignored with a warning. If you leave out `bootstrap-api-key`, the engine generates an admin API key on
first boot and stores it in `credentials.toml` on the volume:

```bash
kubectl -n inputlayer-acme exec inputlayer-0 -- cat /var/lib/inputlayer/data/credentials.toml
```

Agents in the cluster connect to `ws://inputlayer.inputlayer-acme.svc:8080/ws`.
Agents outside it connect through the Ingress at `wss://<host>/ws`.

### Single Writer

InputLayer is a single writer per data directory (see
[Persistence](persistence#single-writer)). The manifests stack three
safeguards:

1. **One replica.** `replicas: 1` on a StatefulSet. Never raise it, and never
   point an autoscaler at it.
2. **No overlap on replacement.** With one replica, a StatefulSet rolling
   update deletes `inputlayer-0`, waits for it to terminate, and only then
   creates the replacement. A Deployment's default `RollingUpdate` starts the
   new pod first. If you deploy the engine as a Deployment, use
   `strategy: Recreate`.
3. **The data-dir lock.** `ReadWriteOnce` stops a second node attaching the
   volume. Pods on the same node can still mount it, and there the engine's
   `LOCK` refuses the second writer, which exits with `in use by another
   InputLayer process`.

None of this prevents every duplicate writer. A force-deleted pod
(`kubectl delete pod --force`), or a pod on a partitioned node, can still be
running when its replacement starts. Then only the volume and the lock
remain. They do not hold on storage that attaches read-write to several nodes,
or on a filesystem whose `flock` is not shared between clients (some NFS
setups). Keep the data on block storage. Where the CSI driver supports it,
set `accessModes: [ReadWriteOncePod]` in `pvc.yaml`. Do not force-delete
the engine pod unless you know that its node is down.

### Security Context

The engine runs as uid/gid `999`, the image's `inputlayer` user (pinned in the
`Dockerfile`). `fsGroup: 999` makes a freshly provisioned, root-owned volume
writable. The root filesystem is read-only, all capabilities are dropped,
privilege escalation is off and the seccomp profile is `RuntimeDefault`. The
pod passes the `restricted` Pod Security Standard, which the example overlay
enforces on its namespace. The pod gets no service account token.
`enableServiceLinks: false` keeps Kubernetes from injecting `INPUTLAYER_*`
service variables into the engine's config namespace.

### Configuration

`base/configmap.yaml` holds `config.toml`. Environment variables override it,
and the engine image sets `http.host`, `http.port`, `storage.data_dir`,
`logging.level` and `storage.auto_create_knowledge_graphs` as environment
variables. Change those five keys in `statefulset.yaml`. A ConfigMap change does not
restart the pod, so restart it after applying:

```bash
kubectl -n inputlayer-acme rollout restart statefulset/inputlayer
```

Behind the Ingress, every request comes from the ingress controller. Set
`http.trusted_proxies` to the controller's pod CIDR. Otherwise the per-IP rate
limit and the pre-auth WebSocket cap (`ws_max_preauth_per_ip`) apply to
the controller instead of to each client. The Ingress keeps idle WebSockets
open for an hour, so the engine's `http.ws_idle_timeout_ms` decides when idle
subscriptions close.

### Probes, Shutdown and Upgrades

- The HTTP server starts only after the WAL replay. The startup probe on
  `/live` therefore sets the replay budget: 10 minutes. Raise
  `failureThreshold` for large data sets.
- `/live` drives the liveness probe and `/ready` (storage reachable) drives
  readiness. See [Health Checks](#health-checks).
- `terminationGracePeriodSeconds: 60` exceeds `http.shutdown_timeout_secs: 30`
  so the WAL flush on `SIGTERM` can finish.
- To upgrade, change the image tag in the overlay and `kubectl apply -k` it.
  The engine is down from its shutdown until the new pod finishes replay.
  Take a backup first.

### Backup and Restore

Back up and restore with the engine stopped. The maintenance pod mounts the
volume as the engine's user and holds the engine's `LOCK` while it runs. It
fails to start while an engine owns the volume, and an engine started in the
meantime refuses the volume. Point kubectl at the tenant's namespace first:

```bash
kubectl config set-context --current --namespace=inputlayer-acme
```

**Back up**

```bash
kubectl scale statefulset/inputlayer --replicas=0
kubectl wait --for=delete pod/inputlayer-0 --timeout=120s
kubectl apply -f deploy/kubernetes/maintenance/maintenance-pod.yaml
kubectl wait --for=condition=Ready pod/inputlayer-maintenance --timeout=180s
kubectl exec inputlayer-maintenance -- sh -c 'cd /var/lib/inputlayer/data &&
  find . -mindepth 1 -maxdepth 1 ! -name LOCK ! -name lost+found -print0 |
  tar --null -T - -czf -' > inputlayer-backup.tgz
kubectl delete pod inputlayer-maintenance
kubectl scale statefulset/inputlayer --replicas=1
```

The archive holds every knowledge graph, the WAL and the user and API key
store. If the engine generated its credentials, the archive also holds
`credentials.toml`. Treat the archive as a secret.

**Restore** into a new, empty volume. This step deletes the current volume,
so back it up first if you might need it.

```bash
kubectl scale statefulset/inputlayer --replicas=0
kubectl wait --for=delete pod/inputlayer-0 --timeout=120s
kubectl delete pvc inputlayer-data
kubectl apply -f deploy/kubernetes/base/pvc.yaml   # only the PVC: re-applying the overlay would also restore replicas: 1
kubectl apply -f deploy/kubernetes/maintenance/maintenance-pod.yaml
kubectl wait --for=condition=Ready pod/inputlayer-maintenance --timeout=180s
kubectl exec -i inputlayer-maintenance -- tar -C /var/lib/inputlayer/data -xzf - < inputlayer-backup.tgz
kubectl delete pod inputlayer-maintenance
kubectl scale statefulset/inputlayer --replicas=1
kubectl rollout status statefulset/inputlayer
```

If your overlay changes the PVC (storage class, size), apply your overlay's
rendered PVC instead of `base/pvc.yaml`. CSI `VolumeSnapshot`s also work
as backups. Take them while the StatefulSet is scaled to 0, and restore by
creating `inputlayer-data` from the snapshot (`spec.dataSource`).

## Resource Sizing

### Memory

InputLayer holds the facts of loaded knowledge graphs in memory, in its relation store. Derived data is not kept: each query builds a Differential Dataflow computation over a snapshot of the facts and drops it when it finishes. Memory usage is proportional to the number of facts plus the working memory of the queries and standing queries running at the time.

| Workload | Facts | Rules | Recommended Memory |
|---|---|---|---|
| Development | < 100K | < 50 | 512 MB |
| Small production | 100K - 1M | 50 - 200 | 2 - 4 GB |
| Medium production | 1M - 10M | 200 - 1000 | 8 - 16 GB |
| Large production | 10M+ | 1000+ | 32 GB+ |

Three limits keep the server inside that memory and refuse work with
`resource_exhausted` instead of growing past it:

- `max_graph_memory_bytes` bounds the **stored data**: the facts of one
  knowledge graph, as estimated from their tuples.
- `max_query_memory_bytes` bounds one query's **working set**: everything it
  holds while it evaluates, summed over all the threads evaluating it. A
  query copies the facts it reads into its dataflow, and joins and recursive
  rules hold intermediate results on top, so its working set is a multiple of
  the data it reads. Keep the per-query limit at least twice the graph
  budget, so a query that scans a whole graph inside its budget still runs;
  raise it further for joins and recursion over large relations.
- `max_total_query_memory_bytes` bounds the working sets of **all queries
  running at once**. Up to about three quarters of the CPUs run queries
  concurrently; a query that grows while they hold this much is stopped, so
  concurrency can never push the server past its memory. A query holding
  next to nothing (under 1/64 of this, at most 16 MiB) is not stopped for
  it: the queries that filled it are. Unset, it is 60% of the container's
  memory limit (the tightest cgroup limit on the process, as a container or
  a systemd unit's `MemoryMax=` sets it), or no limit when the server runs
  without one. That default leaves room only
  for the server and small graphs: set it explicitly whenever graphs hold
  real data, and outside a memory-limited container. The server logs the
  budget it uses at startup (`query_memory_limits`).

The query limits hold while a query computes, not only between its steps:
the evaluator checks them every few thousand rows a join forms, so even a
join pairing millions of rows in one step is stopped a few hundred KB past
its limit. After a query that held a lot of memory, the server returns what
it freed to the operating system.

`max_query_cost` (default 100,000,000) refuses with `validation`, before it
runs, a query whose plan joins relations on no shared variable into a cross
product estimated past it, counting the rows its filters keep of stored
relations. The optional `max_recursion_iterations` (default 0, no limit)
stops recursion that keeps deriving new values after that many iterations,
whatever the deadline; without it, the deadline and memory limits stop it.

Stored graphs and the queries' working memory are separate, so they add up.
The sizing rule that keeps the process inside its memory limit is:

```
(sum of the graphs' max_graph_memory_bytes)
  + max_total_query_memory_bytes
  + server overhead (about 0.5 GB)
  ≤ 0.8 × memory limit

max_query_memory_bytes ≤ max_total_query_memory_bytes
```

The last 20% of the memory limit is margin for allocator overhead: the
allocator holds more resident memory than the bytes it hands out.

For example, a 32 GB host with the configuration above gives 12 GiB to
queries (one whole-graph query at 8 GiB, with room for smaller ones beside
it) and holds up to two graphs at their full 4 GiB budget: 8 + 12 + 0.5 =
20.5 GiB, inside 0.8 × 32 GB. The Kubernetes base manifests follow the same
rule for their 8Gi pod: `max_total_query_memory_bytes` 3 GiB,
`max_query_memory_bytes` 1 GiB and `max_graph_memory_bytes` 512 MiB, so up to
four graphs at their full budget (4 × 0.5 + 3 + 0.5 = 5.5 GiB, inside
6.4 GiB).

### CPU

Each query runs its own Differential Dataflow computation, and concurrent queries and standing-query re-evaluations run on separate workers, so more cores serve more of them at once. The `num_threads` setting (default: `0`, meaning all available cores) controls worker parallelism.

| Workload | Recommended CPU |
|---|---|
| Development | 2 cores |
| Small production | 4 cores |
| Medium production | 8 cores |
| Large production | 16+ cores |

### Admission and Lanes

Every computation holds one **compute permit** while it runs: a query, a program that writes, a proof, a `read`, a subscription refresh or a shared standing-query round. The pool holds `storage.performance.admission.compute_permits` permits (default `0`: the cores not reserved for I/O, about three quarters of them), so the server never runs more dataflows at once than it has cores for.

Requests wait for a permit on one of three **lanes**, which share the pool by the time their computations actually hold permits:

| Lane | What runs on it | Default weight |
|---|---|---|
| `interactive` | Queries, `read`s, proofs, session queries and commands that change no durable state | 4 |
| `write` | Programs that commit: facts, schemas, rules, index builds and the other commands that change durable state | 2 |
| `background` | Subscription refreshes and the shared rounds of standing-query families | 4 |

When a permit frees, the lane that has used the least permit time for its weight gets it, so a lane running cheap work keeps getting through however much another lane queues, and a lane that monopolized the pool yields until the others catch up. Writes **yield to background work** (`yields_to_background`, default on): a write waits while any refresh waits. Every commit refreshes the views that depend on it, so a write admitted while those refreshes still wait only makes the deliveries later and the refreshes repeat; yielding batches writes between sweeps of the views, whose refreshes coalesce, and keeps a delivery within one sweep of its write. Writes cannot starve: the refreshes commits cause are finite, so the background queue drains while writes wait, and against interactive work writes share by weight. Overload may slow writes down, but never the deliveries they cause. Two bounds sit on top of that share: a lane holding fewer than its `min_permits` is served before any other (default 1 for `interactive`, so a cheap query never waits behind a full sweep of refreshes or writes, even on a host with two permits; 0 for the others, whose weights already guarantee their share); and no lane holds more than its `max_permits` (default `0`: every permit). The pool is work-conserving: a free permit never idles while any lane can use it. Sharing probes of standing-query families hold one permit of their own beside the pool.

Waits are bounded. A lane's queue holds at most `max_queued` requests (default 4,096 for `interactive` and `write`; unbounded for `background`, whose queue is bounded by the views that exist); one more is refused at once. No request waits longer than its own deadline or `max_wait_ms` (default 30,000), whichever is sooner. A request refused for either gets code `overloaded` (or `deadline_exceeded` when its own deadline passed), never runs later, and applied nothing; a request cancelled or disconnected while it waits leaves the queue at once. The `inputlayer_admission_*` [metrics](#metrics) show each lane's running and queued requests, refusals and summed wait and hold times.

```toml
[storage.performance.admission]
compute_permits = 0        # 0: cores minus the I/O reserve
max_wait_ms = 30000

[storage.performance.admission.interactive]
weight = 4
min_permits = 1
max_permits = 0            # 0: every permit
max_queued = 4096

[storage.performance.admission.write]
weight = 2
min_permits = 0
max_permits = 0
max_queued = 4096
yields_to_background = true

[storage.performance.admission.background]
weight = 4
min_permits = 0
max_permits = 0
max_queued = 0             # bounded by the views that exist
```

Turn `yields_to_background` off and raise the `write` weight on a server whose write acknowledgements matter more than its deliveries; cap `interactive` with `max_permits` on one whose writes matter more than its reads; cap `write` with `max_permits` on a server where many writers commit to one knowledge graph, since each commit serializes on that graph's write lock and a permit held while waiting for it computes nothing.

### Disk

The data directory stores WAL files and compacted batch files. Disk usage depends on fact volume and the WAL rotation settings.

- WAL files rotate at 64 MB by default (`max_wal_size_bytes`)
- Batch files are compacted when a shard exceeds 10 files (`auto_compact_threshold`)
- Plan for 2-3x the raw data size to account for WAL overhead and compaction headroom

Use fast local storage (SSD/NVMe) for the data directory. Network-attached storage works but increases write latency, which impacts durability mode `immediate`.

### File Descriptors

For production deployments with many concurrent WebSocket connections, increase the file descriptor limit:

```bash
# In systemd service
LimitNOFILE=65536

# Or system-wide in /etc/security/limits.conf
inputlayer    soft    nofile    65536
inputlayer    hard    nofile    65536
```

## Security Recommendations

### Authentication

InputLayer requires WebSocket authentication for all data operations. On first boot, if no admin password is configured (or it is empty), a random password is generated and saved to `credentials.toml` in the data directory. A configured password shorter than 12 characters stops the server on first boot with an error naming the setting; once the admin exists it is ignored with a warning. For production:

1. Set `INPUTLAYER_ADMIN_PASSWORD` explicitly, or keep the generated password and protect `credentials.toml`; in Compose, require it with `${INPUTLAYER_ADMIN_PASSWORD:?...}` so an unset variable fails the deploy instead of passing an empty value
2. Use Kubernetes Secrets or Docker secrets for the password
3. Rotate credentials periodically

### Network

1. Bind the server to `127.0.0.1` when behind a reverse proxy (the default)
2. Use a reverse proxy for TLS termination -- InputLayer does not terminate TLS natively
3. Enable rate limiting via `http.rate_limit.per_ip_max_rps` for public-facing deployments
4. Restrict CORS origins in production (`http.cors_origins` instead of `http.cors_allow_all`)

### Filesystem

1. Run as a dedicated non-root user
2. Use `ProtectSystem=strict` in systemd to prevent writes outside allowed paths
3. Set appropriate permissions on the data directory (`750` or stricter)
4. Back up the data directory regularly with `inputlayer-backup` -- see [Backup and Restore](backup) (Kubernetes: [Backup and Restore](#backup-and-restore))

### Durability

For production, always use `durability_mode = "immediate"`. The server warns on startup if a weaker mode is configured:

```
WARNING: Durability mode is Batched (not Immediate).
Recent writes may be lost on crash.
```

Also ensure `storage.persist.enabled = true` (the "DD-native persist layer" is the WAL + Parquet storage layer). Without it, all data is lost on restart:

```
WARNING: DD-native persist layer is DISABLED.
Data will NOT survive restarts.
```
