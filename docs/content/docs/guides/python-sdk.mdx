# Python SDK

InputLayer's Python SDK is an Object-Logic Mapper (OLM) that lets you work with your knowledge graph using plain Python classes. You define schemas as typed dataclasses, build queries with lambdas and operators, and the SDK compiles everything into InputLayer Query Language (IQL) behind the scenes. You never have to write IQL by hand for normal application code.

The SDK connects over WebSocket, so you get persistent connections, live notifications, and session-scoped state out of the box. For LangChain users, see the dedicated [LangChain Integration](langchain) guide.

## Installation

The SDK is not published to PyPI yet. Install it from a source checkout of the repository:

```bash
git clone https://github.com/inputlayer/inputlayer.git
pip install ./inputlayer/packages/inputlayer-py

# With pandas DataFrame support
pip install "./inputlayer/packages/inputlayer-py[pandas]"
```

Requirements: Python 3.10+ and a running InputLayer server.

The package also installs the `il migration` commands for managing schema migrations. See [Migrations](migrations) for the full guide.

## Connecting

The `InputLayer` client manages a WebSocket connection with automatic reconnection. It authenticates with an API key or a username and password. The examples read secrets from the environment: `INPUTLAYER_API_KEY` holds a key (on first boot the server writes the admin key to `credentials.toml` in its data directory; see [Installation](installation#credentials)), never a literal in code.

```python
import asyncio
import os
from inputlayer import InputLayer

async def main():
    async with InputLayer("ws://localhost:8080/ws", api_key=os.environ["INPUTLAYER_API_KEY"]) as il:
        print(f"Connected to InputLayer {il.server_version}")

asyncio.run(main())
```

To sign in as a user instead:

```python
async with InputLayer(
    "ws://localhost:8080/ws",
    username=os.environ["INPUTLAYER_USER"],
    password=os.environ["INPUTLAYER_PASSWORD"],
) as il:
    ...
```

The client accepts a few optional parameters for connection resilience:

```python
il = InputLayer(
    "ws://localhost:8080/ws",
    api_key=os.environ["INPUTLAYER_API_KEY"],
    auto_reconnect=True,         # reconnect on disconnect (default: True)
    reconnect_delay=1.0,         # first backoff in seconds, doubling to 30 with jitter (default: 1.0)
    max_reconnect_attempts=10,   # give up after N failures (default: 10)
    default_timeout=30.0,        # deadline of each call in seconds (default: 30.0)
    keepalive=20.0,              # ping after this many idle seconds (default: 20.0)
)
await il.connect()
# ... use the client ...
await il.close()
```

### How connections behave

- **One connection per knowledge graph.** `il.knowledge_graph(name)` gets its own connection, bound to that graph when it opens (on first use; a missing graph is created then). Handles never switch a shared connection between graphs, so one graph's subscriptions and session state survive calls on another.
- **Calls are pipelined.** Concurrent calls on one handle are sent without waiting for each other and their replies are matched by request id; at most 15 are unanswered at once, which keeps one of the server's 16 slots free for a cancel.
- **Deadlines.** Every call runs under a deadline (`default_timeout`, or `timeout=` on `kg.execute(iql, timeout=2.0)`) that the engine enforces (time spent waiting for a reconnect or a free request slot counts against it); past it the call raises `DeadlineExceeded` and nothing was applied. If no reply comes at all, the SDK cancels the request on the server: a query then raises `DeadlineExceeded`, but a write raises `OutcomeUnknownError` unless the server confirmed the cancel, because it may have committed, so read back before retrying it. Cancelling the awaiting task cancels the request too.
- **Live while idle.** One reader task per connection always runs, so notifications arrive while no call is in flight, and a ping every `keepalive` idle seconds keeps a listening client under the server's idle timeout.
- **Reconnects.** A dropped connection fails its pending calls with `ConnectionLost` (`may_have_committed` is set for a write that was sent: read back before retrying) and reconnects to the same knowledge graph, resuming notifications after the last `seq` seen (a reconnect with no `seq` to resume from reports a `notification_gap`). Session rules and facts do not survive it. `il.events` reports `disconnected`, `session_reset`, `reconnected`, `notification_gap` and `closed`:

```python
@il.events.on("session_reset")
async def recreate_session_rules(event):
    await il.knowledge_graph(event.knowledge_graph).session.define_rules(MySessionView)
```

### Sync Client

If you're working in a script, notebook, or anywhere async isn't practical, use `InputLayerSync` instead. It wraps the async client and exposes the same API, just without `await`:

```python
import os
from inputlayer import InputLayerSync

with InputLayerSync("ws://localhost:8080/ws", api_key=os.environ["INPUTLAYER_API_KEY"]) as il:
    kg = il.knowledge_graph("myapp")
    kg.define(Employee)
    result = kg.query(Employee)
    for emp in result:
        print(emp.name)
```

Every method shown in this guide works the same way on the sync client - just drop the `await`.

## Knowledge Graphs

Once connected, you work within a knowledge graph. Think of it as a namespace or database that holds your relations, rules, and indexes.

```python
# Get or create a knowledge graph
kg = il.knowledge_graph("myapp")

# List all knowledge graphs on the server
graphs = await il.list_knowledge_graphs()

# Drop a knowledge graph and all its data
await il.drop_knowledge_graph("myapp")
```

## Defining Schemas

Schemas are defined as Python classes that extend `Relation`. Each field becomes a typed column in the knowledge graph.

```python
from inputlayer import Relation, Vector, Timestamp

class Employee(Relation):
    id: int
    name: str
    department: str
    salary: float
    active: bool

class Document(Relation):
    id: int
    title: str
    content: str
    embedding: Vector[384]
    created_at: Timestamp
```

Deploy your schema to the server with `define()`. This is idempotent - calling it multiple times is safe and won't duplicate anything.

```python
kg = il.knowledge_graph("myapp")
await kg.define(Employee, Document)
```

You can inspect what's been deployed:

```python
# List all relations
relations = await kg.relations()
for r in relations:
    print(f"{r.name}: {r.row_count} rows")

# Describe a specific relation's schema
desc = await kg.describe(Employee)
for col in desc.columns:
    print(f"  {col.name}: {col.type}")
```

### Supported Types

| Python Type | InputLayer Type | Description |
|-------------|-----------------|-------------|
| `int` | `int` | 64-bit integer |
| `float` | `float` | 64-bit floating point |
| `str` | `string` | UTF-8 string |
| `bool` | `bool` | Boolean |
| `Vector[N]` | `vector(N)` | N-dimensional float32 vector |
| `VectorInt8[N]` | `vector_int8(N)` | N-dimensional int8 quantized vector |
| `Timestamp`, `datetime` | `int` | Unix epoch milliseconds; a `datetime` is written as milliseconds (a naive one as UTC) and read back as a UTC `datetime` |

### Custom Relation Names

By default, the SDK converts your class name to snake_case (e.g., `SensorReading` becomes `sensor_reading`). You can override this:

```python
class SensorReading(Relation):
    __relation_name__ = "readings"
    sensor_id: int
    value: float
```

## Inserting Data

You can insert data in several ways, depending on what's most convenient.

```python
# A single fact
await kg.insert(Employee(id=1, name="Alice", department="eng", salary=120000.0, active=True))

# A batch of facts
await kg.insert([
    Employee(id=2, name="Bob", department="hr", salary=90000.0, active=True),
    Employee(id=3, name="Charlie", department="eng", salary=110000.0, active=False),
])

# From a dictionary
await kg.insert(Employee, data={"id": 4, "name": "Diana", "department": "eng", "salary": 105000.0, "active": True})

# From a list of dictionaries
await kg.insert(Employee, data=[
    {"id": 5, "name": "Eve", "department": "sales", "salary": 95000.0, "active": True},
    {"id": 6, "name": "Frank", "department": "sales", "salary": 88000.0, "active": True},
])
```

### Inserting from pandas DataFrames

If you installed with the `[pandas]` extra, you can load data directly from DataFrames:

```python
import pandas as pd

df = pd.DataFrame({
    "id": [7, 8, 9],
    "name": ["Grace", "Hank", "Ivy"],
    "department": ["eng", "hr", "eng"],
    "salary": [115000.0, 92000.0, 108000.0],
    "active": [True, True, False],
})
result = await kg.insert(Employee, data=df)
print(f"Inserted {result.count} rows")
```

Every write (inserts, deletes, programs, claims, rules and session facts) sends its values as [parameters](/docs/guides/websocket-api#parameters), beside the program text: the program reads `+employee($p0, $p1, $p2, $p3, $p4)` and the engine binds the values without parsing them, so no value can change what the program does. This needs an engine speaking protocol 4; an older one is refused before anything is sent.

## Deleting Data

Delete specific facts or use a filter to remove matching rows:

```python
# Delete a specific fact
await kg.delete(Employee(id=1, name="Alice", department="eng", salary=120000.0, active=True))

# Delete by condition
result = await kg.delete(Employee, where=lambda e: e.active == False)
print(f"Deleted {result.count} rows")
```

## Querying

Queries are built with Python expressions. The SDK compiles your lambdas, column references, and aggregation calls into the right query language behind the scenes.

### Basic Queries

```python
# All rows from a relation
result = await kg.query(Employee)
for emp in result:
    print(f"{emp.name} - {emp.department}")

# With a filter
engineers = await kg.query(
    Employee,
    where=lambda e: (e.department == "eng") & (e.active == True),
)
```

### Selecting Specific Columns

Instead of fetching full rows, you can select just the columns you need. The result has exactly those columns, in that order, and like every query result it is a set: two employees with the same name and salary give one row.

```python
result = await kg.query(
    Employee.name, Employee.salary,
    join=[Employee],
    where=lambda e: e.department == "eng",
)
for row in result:
    print(f"{row.name}: ${row.salary}")
```

### Joins

When your query spans multiple relations, use `join` and `on` to combine them:

```python
class Department(Relation):
    name: str
    budget: float

result = await kg.query(
    Employee.name, Department.budget,
    join=[Employee, Department],
    on=lambda e, d: e.department == d.name,
)
```

### Self-Joins

For queries that need to compare rows within the same relation, use `refs()` to create aliased references:

```python
e1, e2 = Employee.refs(2)

result = await kg.query(
    e1.name, e2.name,
    join=[e1, e2],
    on=lambda a, b: (a.department == b.department) & (a.id != b.id),
)
```

### Computed Columns

You can define computed values inline using keyword arguments:

```python
result = await kg.query(
    Employee.name,
    join=[Employee],
    bonus=Employee.salary * 0.1,
)
for row in result:
    print(f"{row.name}: bonus = ${row.bonus}")
```

### Ordering and Pagination

Ordering and pagination run in the engine, so the engine sends only the requested page. To page a projection, select the column you order by: ordering a page by a column you do not select is ambiguous, so the SDK raises `CompileError`.

```python
# Top 10 highest paid
result = await kg.query(
    Employee,
    order_by=Employee.salary.desc(),
    limit=10,
)

# Second page
result = await kg.query(
    Employee,
    order_by=Employee.name.asc(),
    limit=10,
    offset=10,
)
```

### Aggregations

The SDK includes standard aggregation functions that you can use in queries:

```python
from inputlayer import count, count_distinct, sum_, avg, min_, max_

# Group by department with stats
result = await kg.query(
    Employee.department,
    count(Employee.id),
    avg(Employee.salary),
    max_(Employee.salary),
    join=[Employee],
)
for row in result:
    print(f"{row.department}: {row.count_id} employees, avg ${row.avg_salary}")
```

Result columns are named after what you select: a column by its name (`row.department`), a computed column by its keyword, and an aggregate as `<function>_<column>` (`count_id`, `avg_salary`, `max_salary`; `count()` without a column is `count`). A repeated name gets a `_2` suffix. Pass an aggregate as a keyword to name it yourself: `kg.query(Employee.department, n=count(Employee.id), join=[Employee])`.

For more specialized aggregation, `top_k` lets you find the top entries per group:

```python
from inputlayer import top_k

# Top 3 highest-paid employees per department
result = await kg.query(
    Employee.department,
    top_k(3, Employee.name, order_by=Employee.salary, desc=True),
    join=[Employee],
)
# columns: department, name, salary
```

The columns you select beside `top_k` are the groups; the columns passed to `top_k` before `order_by` are kept for each of the top rows.

### Working with Results

Every query returns a `ResultSet` with several ways to access the data:

```python
result = await kg.query(Employee)

# Iterate as typed objects
for emp in result:
    print(emp.name)

# Check result metadata
print(f"Rows: {len(result)}, Total: {result.total_count}")
print(f"Execution time: {result.execution_time_ms}ms")

# Get the first row (or None if empty)
first = result.first()

# Get a single scalar value
total = (await kg.query(count(Employee.id), join=[Employee])).scalar()

# Convert to different formats
dicts = result.to_dicts()     # list[dict]
tuples = result.to_tuples()   # list[tuple]
df = result.to_df()           # pandas DataFrame (requires pandas)
```

### Query Plans

To understand how a query will execute without running it, use `debug()`. It takes the same arguments as `query()`, and so does `why()`, which returns the query's rows with a proof tree for each. The engine does not paginate `.why`, so `why()` fetches every row and applies `order_by`, `limit` and `offset` in the SDK:

```python
plan = await kg.debug(
    Employee,
    where=lambda e: e.department == "eng",
)
print(plan.iql)   # compiled IQL string
print(plan.plan)  # execution plan
```

### Raw IQL

If you need to drop down to raw InputLayer Query Language for something the OLM doesn't cover:

```python
result = await kg.execute("?employee(Id, Name, D, Salary, A), Salary > 100000")
```

The query body is whatever follows `?`. Variable names must be capitalized (lowercase identifiers parse as constants). Never build IQL strings with `f"..."` from values you did not write yourself: pass them as parameters, which the engine binds without parsing:

```python
await kg.execute(
    "+employee($id, $name, $dept, $salary, $active)",
    params={"id": 7, "name": user_input, "dept": "eng", "salary": 100000.0, "active": True},
)
```

For agent-style or chain-style use, see also the [LangChain Integration](langchain) guide.

## Derived Relations (Rules)

Derived relations are computed views: InputLayer stores the rule, not its results, and recomputes the rows from the current facts on every query that reads them. There is nothing to refresh by hand: the next query after a change reflects it.

Define them using `Derived` with the `From(...).where(...).select(...)` builder:

```python
from typing import ClassVar
from inputlayer import Derived, From

class HighEarner(Derived):
    name: str
    salary: float
    rules: ClassVar[list] = [
        From(Employee)
            .where(lambda e: e.salary > 100000)
            .select(name=Employee.name, salary=Employee.salary),
    ]
```

### Recursive Rules

One of InputLayer's most powerful features is native support for recursive logic. You define it naturally - a base case and a recursive case:

```python
class Edge(Relation):
    src: int
    dst: int

class Reachable(Derived):
    src: int
    dst: int
    rules: ClassVar[list] = []

Reachable.rules = [
    # Base case: direct edges are reachable
    From(Edge).select(src=Edge.src, dst=Edge.dst),
    # Recursive case: if A reaches B and B reaches C, then A reaches C
    From(Reachable, Edge)
        .where(lambda r, e: r.dst == e.src)
        .select(src=Reachable.src, dst=Edge.dst),
]
```

Deploy and query rules just like regular relations:

```python
# Deploy the rule (persistent - survives restarts)
await kg.define_rules(Reachable)

# Query it
result = await kg.query(Reachable, where=lambda r: r.src == 1)
for row in result:
    print(f"1 can reach {row.dst}")
```

### Managing Rules

```python
# List all deployed rules
rules = await kg.list_rules()
for r in rules:
    print(f"{r.name}: {r.clause_count} clause(s)")

# View a rule's compiled IQL definition
clauses = await kg.rule_definition("reachable")
for clause in clauses:
    print(clause)

# Drop a specific rule
await kg.drop_rule("high_earner")

# Remove every clause of a rule
await kg.clear_rule("reachable")
```

## Guarded writes and claims

### Existence checks

`R.any(**columns)` is true when a row of `R` exists whose columns equal the given values. Columns you leave out match anything, and a value can be a column of another relation in the same condition. `~R.any(...)` is true when no such row exists. You can use both in rule conditions, in the `where=` of queries and conditional deletes, and in guards:

```python
class AutoTool(Derived):
    tool: str
    rules: ClassVar[list] = [
        From(ToolPolicy)
            .where(lambda t: (t.mode == "auto") & ~KillSwitch.any(tool=t.tool))
            .select(tool=ToolPolicy.tool),
    ]

auto = await kg.query(ToolPolicy, where=lambda t: (t.mode == "auto") & ~KillSwitch.any(tool=t.tool))
await kg.delete(Attempt, where=lambda a: AttemptDone.any(attempt=a.attempt))
```

`~R.any()` must bind at least one column. A constant binding works even when no positive relation in the condition carries that value; the SDK supplies the binding through its own `il_const_*` relations.

### Programs

`kg.program()` collects statements and commits them as one request and one transaction. The builder methods chain: `insert(*facts)`, `retract(row)` or `retract(R, **columns)` (every row matching those columns), `define(*relations)`, `define_rules(*derived)` and `clear_rule(name)`. `commit()` returns a `ProgramResult(applied, inserted, deleted, iql)`, where `inserted` and `deleted` count the facts that the program's writes changed. `kg.retract(...)` is a one-statement program.

`.when(*conditions)` makes the whole program conditional. The engine evaluates the guard once at commit, and the program applies whole or not at all. Conditions are `R.any()` / `~R.any()` atoms and comparisons over their columns, such as `Cursor.any(session="s-42"), Cursor.last < 7`.

```python
from inputlayer import PreconditionFailed

try:
    result = await (
        kg.program()
        .retract(CarrierNote, shipment="S-77")
        .insert(CarrierNote(shipment="S-77", reason="weather_delay"))
        .when(Attempt.any(attempt="att-9f3"), ~AttemptDone.any(attempt="att-9f3"))
        .commit()
    )
    print(f"+{result.inserted} -{result.deleted}")
except PreconditionFailed:
    ...  # nothing was applied; re-read the state before retrying
```

A guard comes in two forms:

- **Abort form, `commit()` (`strict=True`, the default).** If the guard does not hold, the engine rolls back the whole program, rules and schema included, and the call raises `PreconditionFailed`. Use this form for a program that holds `define()`, `define_rules()` or `clear_rule()`.
- **Token form, `commit(strict=False)`, for programs that only insert or retract facts.** If the guard does not hold, nothing is applied and the call returns `applied=False` instead of raising. `strict=False` on a program that holds rules or schema raises `CompileError` before anything is sent.

`kg.define()` also declares the SDK's guard relations (`il_txn`, `il_txn_pending` and `il_assert`). A guarded program declares them itself on a graph that was defined elsewhere.

### Claims

`kg.claim(row, when=, unless=, key=)` inserts `row` only if every `when` condition holds and no `unless` row exists at commit. It is one request: of many concurrent claims on one key, exactly one wins, and every caller sees the same holder.

```python
c = await kg.claim(
    Attempt(order="ORD-1", tool="carrier_check", attempt=attempt_id),
    when=[CheckNeeded.any(order="ORD-1")],
    unless=Attempt.any(order="ORD-1", tool="carrier_check"),
)
if c.won:
    run_tool()                 # c.holder is the claimed row
elif c.holder is None:
    ...                        # the when guard did not hold
else:
    ...                        # c.holder is the row that already holds the key
```

It returns a `Claim(won, holder)`. `unless` defaults to a row with the `key` columns of `row`. `key` defaults to the columns that `unless` binds when it checks the claimed relation, otherwise to every column. A claim that loses does not raise.

A guarded program or claim whose guard reads rows that concurrent commits keep changing raises `Conflict`. Nothing was applied, so retry with backoff. On `InputLayerSync`, `program().commit()`, `claim()` and `retract()` block.

## Vector Search

InputLayer supports HNSW indexes for approximate nearest-neighbor search over vector columns.

### Creating an Index

```python
from inputlayer import HnswIndex

index = HnswIndex(
    name="doc_emb_idx",
    relation=Document,
    column="embedding",
    metric="cosine",       # cosine, euclidean, manhattan, dot_product
    m=32,                  # connections per node (higher = more accurate, more memory)
    ef_construction=200,   # build-time search width
    ef_search=50,          # query-time search width
)
await kg.create_index(index)
```

### Searching

```python
query_embedding = [0.1, 0.2, ...]  # your query vector

# Top-k nearest neighbors
result = await kg.vector_search(
    Document,
    query_vec=query_embedding,
    k=10,
    metric="cosine",
)

# Radius-based search (all vectors within distance)
result = await kg.vector_search(
    Document,
    query_vec=query_embedding,
    radius=0.3,
    metric="cosine",
)

# Combined with a filter
result = await kg.vector_search(
    Document,
    query_vec=query_embedding,
    k=10,
    metric="cosine",
    where=lambda d: d.created_at > Timestamp.from_datetime(cutoff_date),
)
```

### Managing Indexes

```python
# List all indexes
indexes = await kg.list_indexes()
for idx in indexes:
    print(f"{idx.name}: {idx.row_count} vectors, metric={idx.metric}")

# Get detailed stats
stats = await kg.index_stats("doc_emb_idx")

```

## Sessions

Sessions let you inject ephemeral facts and rules that exist only for the lifetime of your WebSocket connection. They're useful for user-specific context, A/B testing, or temporary views that shouldn't persist (session rules are evaluated with each query on the connection, like persistent ones).

```python
# Insert session-scoped facts (only visible to this connection)
await kg.session.insert([
    Employee(id=999, name="Temp", department="eng", salary=0.0, active=True),
])

# Define session-scoped rules
await kg.session.define_rules(MyTempView)

# Query as normal - session facts mix with persistent data
result = await kg.query(MyTempView)

# List session rules
session_rules = await kg.session.list_rules()

# Clean up (or just disconnect - session state is automatically cleared)
await kg.session.clear()
```

## Subscriptions

`kg.subscribe()` takes the arguments of `query()` (or raw IQL as `iql="?..."`) and returns an async iterator of `Change` events that keeps the result exact on the client. Every event has the same fields (`kind`, `inserted`, `retracted`, `revision`, `seq`, `verified`), so a loop that applies `retracted` and `inserted` is always correct:

```python
async for change in kg.subscribe(Late):
    for row in change.retracted:
        cancel(row)
    for row in change.inserted:
        start(row)
    if not change.verified:
        pause()
```

- `snapshot`: the first event, the whole result with every row in `inserted`.
- `delta`: the set difference between consecutive results. An unchanged result delivers nothing, and commits that coalesce arrive as one delta, so a row that appears and disappears between two evaluations is never seen.
- `unverified`: the result may no longer be current (`reason` is `connection_lost`, `seq_gap`, `broken_stream`, `subscription_reset`, `subscription_error` or `slow_consumer`). Both lists are empty; act on nothing new until the resync arrives. The SDK subscribes again with backoff.
- `resync`: the exact difference between the rows you hold and the fresh result.

Rows are instances of the relation when one whole relation is selected, otherwise immutable `Row` records (`row.order` or `row["order"]`). A projected subscription reports a row only when the first engine tuple behind it appears or the last one goes away. `queue` (default 1024) bounds the events held for a slow reader: a reader that falls further behind gets `unverified` (`slow_consumer`) and then a `resync`, and the connection never blocks. Leaving the loop or calling `close()` ends the subscription, and `sub.stats` counts dropped stale pushes and resubscribes.

A standing query tracks the whole result of persistent rules, so `subscribe()` raises `SubscriptionRejected` with a `reason`: `limit_offset`, `or_branches` or `session_view` (a session rule, an aggregate or a negated constant) before anything is sent, or the engine's `result_cap`, `access_denied`, `id_taken`, `subscription_limit` or `rejected`. To subscribe to such a query, declare a persistent rule and subscribe to that rule instead.

`kg.watch()` yields the whole current result (`Live`: `rows`, `revision`, `verified`) each time it changes. `kg.on(Late, callback)` calls `callback` with every `Change` and returns a handle; `await handle.close()` stops it. On `InputLayerSync`, `kg.subscribe()` and `kg.watch()` are blocking iterators, and the `on()` callback runs on the client's background thread.

### Several results at one revision

Two subscriptions refresh independently, so an event of one can be ahead of the other. When an agent decides on several results together, read or subscribe to them together. `kg.read()` runs several queries on one snapshot, and `kg.subscribe_group()` keeps several queries current as one subscription. Both take a mapping from a name to a target (a relation, a column, a tuple or dict of `query()` arguments, or raw IQL):

```python
snap = await kg.read({"orders": Order, "eta": Eta})
print(snap.revision, snap.results["orders"], snap.truncated)

async for change in kg.subscribe_group({"orders": Order, "eta": Eta}):
    for name, member in change.members.items():
        if not member.unchanged:
            apply(name, member.retracted, member.inserted)
```

- Every result of a read is its query's exact answer at `snap.revision`, whatever commits meanwhile. After every verified group event (`snapshot`, `delta`, `resync`), every member is its query's exact answer at `change.revision`: a program that changes two members shows up in both in the same event.
- A `delta` lists every member, `unchanged` when its rows did not move; a refresh that changes no member delivers nothing. `unverified` and `resync` cover the whole group.
- Reads and groups see persistent data only and refuse a target that is not one `?` query, with `SubscriptionRejected`. A read keeps `order_by`, `limit` and `offset` and names the results a limit or the result cap cut in `snap.truncated`; a group tracks whole results. Commits coalesce: a row that appears and disappears between two refreshes is never seen.
- On `InputLayerSync`, `kg.read()` blocks and `kg.subscribe_group()` is a blocking iterator. See [Snapshot Reads](/docs/guides/websocket-api#snapshot-reads) and [Subscription Groups](/docs/guides/websocket-api#subscription-groups) for the wire protocol.

## Notifications

Subscribe to live events as data changes in the knowledge graph. This is useful for event-driven pipelines, dashboards, or audit logs. To be told when a rule-derived answer changes, use [subscriptions](#subscriptions).

```python
# Register a callback for a specific relation
@il.on("persistent_update", relation="sensor_reading")
def on_sensor_update(event):
    print(f"[{event.relation}] {event.operation}: {event.count} rows")
    print(f"  sequence: {event.seq}, timestamp: {event.timestamp_ms}")

# Listen for any knowledge graph change
@il.on("kg_change")
def on_kg_change(event):
    print(f"KG {event.knowledge_graph} changed")

# You can also iterate over events
async for event in il.notifications():
    print(f"Event: {event.type} seq={event.seq}")
```

Event types include `persistent_update`, `rule_change`, `kg_change`, and `schema_change`. You can filter by relation or knowledge graph.

## User and Access Management

The SDK provides methods for managing users, API keys, and per-knowledge-graph access control.

### User Management

```python
# Create a new user
await il.create_user("alice", "securepassword", role="editor")

# List users
users = await il.list_users()
for u in users:
    print(f"{u.username}: {u.role}")

# Change a user's role
await il.set_role("alice", "admin")

# Change a user's password
await il.set_password("alice", "newpassword")

# Remove a user
await il.drop_user("alice")
```

### API Keys

```python
# Create an API key that expires in 90 days (omit ttl for no expiry)
key = await il.create_api_key("my-service", ttl="90d")
print(f"Store this key securely: {key}")

# List keys; times are Unix milliseconds, None when unknown/never/unused
keys = await il.list_api_keys()
for k in keys:
    print(f"{k.label} owner={k.owner} {k.status} expires={k.expires_at} last_used={k.last_used_at}")

# Rotate: create the replacement, give the old key a 24h grace period
new_key = await il.create_api_key("my-service-2", ttl="90d")
await il.expire_api_key("my-service", "24h")

# Revoke a key
await il.revoke_api_key("my-service")
```

See [Authentication](authentication#rotate-api-key) for how expiry and rotation work.

### Per-Knowledge-Graph Access Control

```python
# Grant a user access to a specific knowledge graph
await kg.grant_access("alice", "editor")

# List access control entries
acl = await kg.list_acl()
for entry in acl:
    print(f"{entry.username}: {entry.role}")

# Revoke access
await kg.revoke_access("alice")
```

## Error Handling

The SDK uses a hierarchy of typed exceptions so you can handle specific failure modes:

```python
from inputlayer import (
    InputLayerError,           # base class for all errors
    ConnectionError,           # network/connection issues
    AuthenticationError,       # bad credentials
    SchemaConflictError,       # schema mismatch on define()
    ValidationError,           # invalid data
    QueryError,                # base class for program and commit errors
    StatementFailedError,      # some statements of a program failed
    OutcomeUnknownError,       # write outcome unknown; read back before retrying
    StoreReadOnlyError,        # write refused until restart recovery
    CompileError,              # SDK refused to compile a call; nothing sent
    PreconditionFailed,        # strict guarded program's guard did not hold
    Conflict,                  # guarded write found no stable state; retry
    QueryTimeoutError,         # query took too long
    DeadlineExceeded,          # the call's deadline passed; nothing applied
    Cancelled,                 # the call was cancelled; nothing applied
    ConnectionLost,            # connection closed before the reply
    RateLimited,               # refused by the server's rate limit; already retried once
    ProtocolError,             # server could not read the request; an SDK bug
    PermissionError,           # insufficient permissions
    KnowledgeGraphNotFoundError,
    KnowledgeGraphExistsError,
    RelationNotFoundError,
    RuleNotFoundError,
    IndexNotFoundError,
    InternalError,             # unexpected server error
)

try:
    await kg.load("seed.iql")
except AuthenticationError:
    print("Check your credentials")
except StatementFailedError as e:
    # Inspect indexed errors; write-program atomicity is described in
    # Programs Commit Together in the Core Concepts guide.
    for err in e.errors:
        print(f"statement {err.index} [{err.code}]: {err.message}")
except QueryError as e:
    # e.code identifies the cause; e.validation_errors lists parse errors.
    print(f"Program error ({e.code}): {e.message}")
except InputLayerError as e:
    print(f"InputLayer error: {e}")
```

Every SDK call that reaches the engine raises on failure: no failed statement is returned as a result row. `insert()` returns the number of facts the engine newly stored, so re-inserting an existing fact counts 0. This is a behaviour change: earlier SDK versions returned the number of facts sent.

For the typed commit-outcome exceptions and recovery before retrying a write,
see [Persistence](persistence#wal-record-format). These exceptions inherit from
`QueryError` and may carry the server's complete response in `result`.

## Migrations

For production deployments, the SDK includes a Django-style migration system that tracks schema changes, generates versioned migration files, and supports rollbacks. The `il` CLI is installed automatically with the package.

```bash
# Generate a migration from your current models
il migration generate --models myapp.models

# Apply pending migrations to a server
il migration apply --url ws://localhost:8080/ws --kg production

# Check what's applied
il migration status --url ws://localhost:8080/ws --kg production
```

This is a large topic with its own dedicated guide. See [Migrations](migrations) for the full walkthrough covering the CLI, operations, workflows, and CI/CD integration.

## Known Limitations

A few rough edges to be aware of in the current pre-alpha SDK:

- **`kg.relations()` only sees relations after data exists**. The server's `.rel` listing surfaces a relation only after at least one row has been inserted; defining the schema is not enough. If you need a registry of declared schemas that's independent of data, track them in your application code.
