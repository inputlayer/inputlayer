# Why We Built InputLayer on Differential Dataflow

We needed an engine where deleting one fact from a graph with two million derived conclusions would correctly drop exactly the right subset from the answer, every time. Getting this wrong means phantom permissions that should have been revoked, stale compliance flags that miss a sanctions hit, or recommendations pointing to discontinued products. These aren't edge cases. They're the normal state of any system where facts change and derived conclusions are stored somewhere that nobody refreshes.

The choice of computation engine determines whether these bugs are even possible. We chose Differential Dataflow because it makes an entire category of consistency failures structurally impossible. Not caught by tests, not handled by cleanup jobs, but eliminated at the engine level. Here's the story behind that choice.

## The problem that started everything

We wanted to build a knowledge graph engine that could do something deceptively simple: give answers that are correct for the facts as they are right now, including after facts are removed.

That sounds straightforward until you think about scale. Imagine a knowledge graph with 100,000 facts and 50 rules that derive new conclusions from those facts. Some of those rules are recursive, meaning their output feeds back into their input. The initial computation produces millions of derived facts. Fine, that's a one-time cost.

But then a single fact changes. One employee transfers departments. One entity gets added to a sanctions list. One product goes out of stock.

```flow
100K facts + 50 rules -> 2M derived facts [primary] -> 1 fact changes -> ~100 affected [highlight]
```

There are two ways to get this wrong. Store the 2 million derived facts and forget to retract the ones that lost support, and you serve phantom conclusions. Recompute the whole closure for every question, and at 11 seconds per recomputation on a 2,000-node graph you're locked into batch processing.

We needed an engine whose derivations are correct under deletion by construction, and a way to compute only the part of the graph a question actually needs.

## Finding Differential Dataflow

We found it in Frank McSherry's work on [Differential Dataflow](https://github.com/TimelyDataflow/differential-dataflow), built on top of [Timely Dataflow](https://github.com/TimelyDataflow/timely-dataflow). Both are Rust libraries. The performance was a bonus. The computational model was the real discovery.

The core idea is simple enough to explain in a paragraph: data is a collection of weighted records. Adding a fact is a +1. Removing a fact is a -1. Every operator, including recursive iteration, takes weighted records in and produces weighted records out, so a derived record exists exactly as long as its weight is positive. The same model is what lets a long-lived dataflow apply a change without recomputing everything.

How InputLayer uses it today: every query compiles its rules into a fresh Differential Dataflow dataflow, streams the current facts in, collects the result and tears the dataflow down. Nothing derived is stored between queries. A subscription re-runs its query after each relevant commit and pushes the difference from the previous result.

```flow
Today: Query -> Fresh dataflow over current facts [primary] -> Answer
```

```flow
Planned: Changed fact -> Long-lived dataflow applies the diff [success] -> Maintained view
```

The second line is planned work: keeping every persistent rule as a long-lived, incrementally maintained view is [milestone 9](https://github.com/inputlayer/inputlayer/issues/305).

## How it handles the hard part: recursive retraction

The real test of a reasoning engine isn't additions. It's deletions. And specifically, deletions through recursive chains of reasoning.

Here's the scenario that breaks naive systems that store and patch derived results. Alice has authority over Charlie through two independent paths:

```graph
Alice --manages-> Bob --manages-> Charlie [primary]
Alice --manages-> Diana --manages-> Charlie [primary]
```

Remove Bob's management of Charlie. Does Alice lose authority over Charlie? *No*, the path through Diana still supports it. Now remove Diana's management of Charlie too. Does Alice lose authority over Charlie? *Yes*, there are no remaining paths.

Differential Dataflow's weight-based model makes this precise. Within an evaluation, each derived fact carries a weight representing the support it has. Removing a path decreases the weight, and the fact only disappears when the weight hits zero. In InputLayer today, the deletion takes effect on the next evaluation: the query is recomputed from the remaining facts, and Alice keeps or loses Charlie exactly as the remaining paths dictate.

```steps
Both paths: weight = 2 :: via Bob + Diana
Remove Bob path: weight = 1 :: survives [success]
Remove Diana path: weight = 0 :: retracted [highlight]
```

This sounds simple in theory. In practice, getting it right through multiple levels of recursive reasoning, where intermediate conclusions can also have multiple support paths, is extraordinarily difficult. Differential Dataflow solves it at the engine level, which means we didn't have to, and it is the same machinery the planned maintained views will use to apply deletions without a full re-evaluation.

## What this gives you

Building on Differential Dataflow gave us three properties that show up directly in what you can build with InputLayer.

**Answers that match the current facts:** Every query is evaluated against the facts as they are when it runs, so there is no stored derived state to drift out of date. Subscriptions get the same guarantee by re-evaluating after each relevant commit.

**Correct retraction:** Delete a fact, and everything derived through it disappears, but only if there's no alternative reasoning path. Phantom permissions, stale recommendations, lingering compliance flags. These bugs simply don't exist when the engine handles retraction correctly.

**On-demand computation:** We combined Differential Dataflow with an optimization called Magic Sets, which rewrites recursive rules so the engine only computes what's needed for a specific query. Ask "who does Alice have authority over?" and the engine starts from Alice and follows only her paths. It doesn't compute authority for the entire organization. On a 2,000-node graph with 400,000 derived relationships, the bound query `?reach(1, Y)` takes 6.83ms against 11.3 seconds for computing the full closure, a 1,652x difference. That is a demand-driven query computing only the slice it needs, not incremental maintenance.

## The tradeoffs

No engineering decision is free. Here's what we trade.

**Recomputation on read:** Because nothing derived is stored, every read re-derives its answer. Bound recursive queries stay cheap through Magic Sets, but unbound reads of large recursive rules, and subscriptions that re-run them after every commit, pay the full cost each time. That is the gap milestone 9 closes by maintaining persistent rules as views.

**Memory:** Facts live in memory, backed by persistent storage (Parquet files plus a write-ahead log) for recovery. Each query's dataflow holds its working set in RAM while it runs, which is a real consideration for very large knowledge graphs.

**Complexity floor:** The Timely/Differential Dataflow programming model is powerful but has a steep learning curve. We invested significant engineering time building the abstraction layer that compiles high-level rules into efficient computation pipelines. You never touch the dataflow layer directly, but we do, and it required deep expertise to get right.

**Single-node:** Currently, InputLayer runs on a single node. Timely Dataflow supports distributed computation, and that's on our roadmap. But today, the engine is bounded by what a single machine can handle. For most knowledge graph workloads, that's millions of facts and derived relationships, but it's a real limit for truly massive datasets.

## Where the choice matters most

The Differential Dataflow foundation matters most for use cases where data changes frequently and derived conclusions need to stay current. Access control hierarchies where people change roles regularly. Supply chain graphs where supplier status changes daily. Compliance systems where entity relationships and sanctions lists are updated constantly. Agent memory systems where new observations arrive continuously.

For batch-once-query-many workloads with no updates, a simpler engine would be fine. But the moment your facts change and you need derived conclusions to stay correct, including under deletion, the weighted model pays for itself immediately.
