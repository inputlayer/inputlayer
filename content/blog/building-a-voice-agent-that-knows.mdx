# Building a Voice Agent That Knows

This is a reference architecture for a production voice agent built on InputLayer, the live rules engine for AI agents, and the InputLayer voicestack runtime. It specifies the demo-ready system end to end: the cascade of models, the knowledge graph beside it, the rules that derive what the agent says and does, the subscriptions that deliver those derivations, the agenda that turns them into speech, the executor that turns them into tool calls, and the failure and concurrency semantics of every hop.

The positioning is one sentence: **Models think. InputLayer knows.** Every model in the cascade stays. Speech-to-text, the intent model, the language model and text-to-speech do what only models can do. InputLayer holds what the system has accepted and concluded: runtime data from your systems, the session's goals, the rules that connect them, the policy for every tool, and the state of every piece of work in flight. The cascade orchestrates around that graph instead of around a transcript.

It is written for engineers who have shipped voice agents and will hold it to that standard. Each section states a mechanism, its invariants, and what happens when it fails. The complete rule pack is in Appendix A; it was executed against the engine, and the state transitions in Appendix B are its output.

## 1. The strongest turn-based agent, and what changes

Be fair to the alternative, because it is good. A well-built voice agent in 2026 streams everything: VAD brackets each utterance, STT streams partials with a stable prefix, the LLM is prefilled speculatively, TTS is sentence-chunked so the first sentence plays while the second is generated. Barge-in interrupts generation and synthesis and keeps the new utterance intact. Tools run concurrently; long tasks go through a durable workflow engine with retries and idempotency. A vector store and structured lookups feed retrieval. A graph-structured agent framework with a checkpointer holds explicit conversation state and resumes after a crash. Webhooks wake the agent. Validators check tool arguments and outputs, and allow-lists gate tools.

That system can be made to exhibit every behaviour this article describes. A competent team can write the code that invalidates a spoken claim when the ETA changes, evaluates a tool policy deterministically, records why a call was allowed, and cancels tasks when the user changes goals. No single behaviour here is exclusive to an engine. What the bespoke system does not have is the thing the behaviours are made of.

An agent's decisive state changes constantly, whether or not the world does. Every user turn adds or replaces a goal. Every tool result, every piece of parallel work started or finished, every policy that becomes satisfied or violated, every guardrail condition, every sentence already said and every promise already made aloud: all of these are facts that change while the agent talks, in every non-trivial agent, and every decision the agent takes is a function of them. In the bespoke system that function is implemented piecemeal, where each consequence is consumed: the invalidation of "due Thursday" lives in the speech code, the policy join lives in the tool wrapper, the cancellation lives in the workflow definition, the "have I already said this" check lives in the dialogue manager, and each of them re-derives, from the same underlying facts, a conclusion the others also need. Those implementations drift, they are tested separately, nobody can ask the running system why it did what it did, and when a new fact type arrives every one of them has to learn about it.

What InputLayer provides is the four things the team that runs such a system wants and cannot get piecemeal: a clean orchestration of **runtime data, knowledge and workflows embedded in the agent**, as one declarative representation the engine evaluates against the current facts; **tool calls and their policies modelled explicitly** as facts and rules, so eligibility and authorization are derived, not coded; **general rules and guardrails of behaviour enforced deterministically, with provenance**, so every action and every claim has a proof; and a **clean cascade implementation that enables multitasking dispatch**, where work starts, continues and is cancelled by rows entering and leaving a standing result rather than by task ids in a context window. Correcting a sentence mid-utterance when the carrier revises an ETA is one consequence of those four, and the running example of this article; it is not the definition of the value.

The components keep their jobs. The speech models stay. The LLM stays for open-ended language. The durable workflow engine can stay as the backend that executes effects. The vector store stays for documents. InputLayer is not a workflow engine, a vector database or a message bus; it is the place where the system's current conclusions are computed, kept current and watched.

**The trade-off, stated plainly.** You add a stateful component to the decision path. It must be deployed, backed up and monitored. Domain state has to be modelled as relations, and the rules have to be written, tested and versioned like code. Every decision gains a network hop to the engine, and the engine's availability becomes part of the speech lane's failure model (section 13). The boundary of where this is worth it is narrow and specific: the architecture is unnecessary only for a stateless, single-shot assistant with no tools, no policies, no concurrent work and no session state worth keeping, where retrieval plus one model call is the whole product. Production agents are almost never that, and voice agents never are: a voice agent holds a floor, has already said things it may have to correct, has work finishing while it speaks, and is bound by policies that decide whether it may act at all. Its decisive state changes on every turn whether or not the world does.

## 2. "Models think. InputLayer knows," operationally

A model output is a **proposal**: a transcript, an interpreted intent, a phrasing, a plan. Proposals are fallible by construction, so the architecture never lets one become system state without a validation gate, and never lets one authorize an action by itself.

The engine holds **accepted facts** and **rule-derived conclusions** at a known **revision**. "Knows" is explicitly relative to those two things: what the adapters accepted from your systems and what the authored rules derive from it. It is not a claim about the world. The order is late in the graph because the accepted ETA is later than the accepted promise date; if the carrier feed is behind, the graph is behind too, and section 4 shows how that lag is itself a fact the rules consume.

| Model | Role | Output is | Enters the graph through |
|---|---|---|---|
| VAD and streaming STT | Audio to text with stable prefixes | A proposal | The intent stage; never written as a fact itself |
| Intent model (small, non-thinking) | Transcript to goals and slots | A proposal | The write gate: typed, scoped, allow-listed, guarded facts |
| LLM (realizer, open-ended reasoning) | Word a selected claim; answer open questions over a fresh snapshot | A proposal | Never; its text is best-effort language, sanitized, and carries no claim |
| TTS | Approved phrase to audio | Audio | Never; playout writes a receipt of what the device actually consumed |

Deterministic components in between: the engine, the write gate, the agenda, the executor, the playout receipts. Each is specified below.

## 3. The target architecture

![The cascade as one pipeline around the graph](/blog/voice-agent/cascade.svg)

The runtime is **one pipeline** from microphone to loudspeaker. Its data lane carries audio, transcripts, voice edges and claim markers downstream through VAD, STT, the barge-in stage, the intent stage, the agenda, the realizer, TTS and the pump. Its system lane carries `Interrupt` downstream from the barge-in stage and, for supersession, from the agenda. The graph sits beside the lane: the intent gate, the agenda and the pump exchange programs and deltas with it; the adapters and the watchdog write world facts into it; a separate executor process consumes work deltas from it and calls tools.

Ownership is split three ways, and the split is a contract:

| Owner | Provides |
|---|---|
| **InputLayer engine** | Typed relations; persistent rules with stratified negation and aggregates; multi-statement programs committed as one transaction at one revision with one write-ahead-log record; compare-and-set through conditional updates, including one update over several relations, and, as a target extension, guards; standing queries with a snapshot and `inserted`/`retracted` deltas; `.why` and `.why_not` proofs; per-knowledge-graph access control; request deadlines and cancellation; crash recovery; an engine clock usable in queries and guards (`time_now()`). |
| **voicestack runtime** | Stages with a synchronous state-owning `decide` and an asynchronous cancellable `perform`; two lanes (data, system) with a causal interrupt flush; barge-in; off-thread work; the model capability traits (`VoiceActivityDetector`, `Transcriber`, `LanguageModel`, `Synthesizer`); dispatch frames for long-running tasks; the active-stage pattern that lets external events enter an idle pipeline. |
| **Application (the pack and the glue)** | The schema and rule pack; the observation adapters and the watchdog; the intent stage and its write gate; the agenda stage, which is the session's speech owner; the playout pump with receipts; the executor. Specified here with their invariants. They are the part you own. |

Four extensions are specified in this article and marked where they appear: the guard statement `.require` (section 8.2); queries and `.why` evaluated inside a write program at that program's snapshot, with the committed revision in the reply (section 12); the dispatch `Cancel` command with its `Cancelled` event (section 10.5); and a status lookup by idempotency key on the dispatch transport (section 10.6).

Baseline models, pluggable behind the voicestack traits: Silero VAD; Voxtral-Mini-4B-Realtime for streaming transcription; Qwen3.5-35B-A3B in non-thinking mode for intent interpretation and rich realization, with separate inference capacity for background reasoning so a long tool-side generation never competes with the speech lane; Fun-CosyVoice3-0.5B for streaming synthesis. Swapping any of them changes an adapter, not the architecture.

Everything below uses one running example: a support agent for deliveries. User `u-1` in session `s-42` owns order `ORD-4821`, shipment `S-77`, promised by `2026-10-09`. The carrier's ETA is first `2026-10-08`, then revised to `2026-10-10` while the agent is speaking. One knowledge graph per tenant, named `support_acme`. Calendar dates are ISO-8601 strings, and string comparison in IQL is lexicographic, so for zero-padded dates `D > P` means "later than". Instants (observation times, lease expiries, backoff deadlines) are Unix milliseconds as integers, the unit of the engine clock.

## 4. Knowledge: facts, provenance, freshness

### 4.1 World facts come from adapters, never from models

Every world relation carries the **source revision** of the record it came from, and the relations that drive episode logic carry the **observation time** too:

```iql
+shipment(order: string, shipment: string, src_rev: int)
+promised(order: string, due: string, src_rev: int)
+customer_order(user: string, order: string, src_rev: int)
+eta(shipment: string, due: string, src_rev: int, observed: int)
+carrier_note(shipment: string, reason: string, src_rev: int, observed: int)
+source(source: string)
+source_cursor(source: string, partition: string, rev: int)
+source_health(source: string, status: string, until: int)
```

**The adapter owns** source identity, the source revision (a CDC log position, a webhook sequence number, an API response version), observation time, deletion (a source delete becomes a retraction), duplicate delivery and out-of-order delivery. The engine owns none of that; it accepts or rejects a program. `observed` is the adapter's own receipt time, from one clock domain for every source that feeds a relation; the executor stamps its tool results the same way (section 10.4), so the comparisons in section 6.4 compare like with like.

**Exact replacement, guarded.** The carrier revises the ETA. The adapter commits one program, which is one transaction at one knowledge-graph revision:

```iql
.require ?source_cursor("carrier", "p3", 1803)
.require ?eta(S, Dcur, R, _), S = "S-77", Dcur != "2026-10-10"
-eta("S-77", D, R, At) <- eta("S-77", D, R, At)
+eta("S-77", "2026-10-10", 1804, 1791068625059)
-source_cursor("carrier", "p3", R) <- source_cursor("carrier", "p3", R)
+source_cursor("carrier", "p3", 1804)
```

The first two lines are guards (section 8.2), one per condition so that a failure names the condition by statement index. The first says: for an ordered partition, commit only if the partition's cursor is exactly the previous record, so a gap in the feed is never skipped over; it is also the resume point, because after a restart the adapter reads its cursor from the graph and the guard names the record it must have seen. The second says: commit only if the value changes. **An unchanged value is a renewal of health, not an observation**: a polling adapter that re-reads the same ETA renews `source_health` and writes nothing, and the engine enforces it, because the guard refuses the replacement. The old row leaves and the new row arrives at the same revision, so no subscriber ever sees zero or two ETAs for `S-77`, and the cursor commits with the data.

**Two kinds of idempotence.** Inserting a fact that is present, or deleting one that is absent, changes nothing: that is *literal* idempotence, and it makes resending the same insert harmless. It does not make resending a *replacement* harmless: a blind replay of the program above after revision 1805 was applied would reinstall 1804. That is what the guard is for: a replayed replacement fails its guard with `precondition_failed` and applies nothing. Request deduplication is a property of guarded programs, not of the fact store.

**Ordered and unordered feeds.** A replayable ordered feed uses the exact-predecessor cursor guard above. An unordered feed (webhooks, retries from a queue) has no global cursor, and a global maximum would skip records that arrived late. For those the guard is per entity, on the entity's own revision, and it must share a variable with a positive literal (section 6): `.require ?eta(S, _, R, _), S = "S-77", R < 1804` for an update, and `.require ?shipment(S, _, _), S = "S-77", !eta(S, _, _, _)` for a first observation. Either way the engine, not the adapter's memory, decides whether the write is stale.

**Writer ownership.** One adapter instance owns a source partition at a time, held as a lease in the graph with the same owner and expiry relations the executor uses (section 10.2), so that two instances during a failover cannot interleave replacements. The guard still protects against a slow instance that lost the lease.

**Source revision versus graph revision.** `src_rev` is the source's clock and lives in the row. The knowledge-graph `revision` is the engine's token: every committed change advances it, every standing-query push names the revision it brings the result to, and revisions are comparable only within one knowledge graph and one engine run. A commit that changes nothing publishes nothing. A delta at revision 1731 says "the result after the change the engine numbered 1731", not "the carrier is at 1731". Rules can read `src_rev`; nothing lets a rule read the graph revision, which is deliberate.

### 4.2 Consistency, freshness and time

The graph is a **replica at a known lag**, never a distributed transaction with the carrier, the CRM or payments. The design does not pretend otherwise; it makes the lag a fact and makes rules consume it, and it keeps wall-clock time out of the rules.

**Freshness is a lease the adapter holds and a watchdog revokes.** The adapter asserts `source_health("carrier", "ok", until)` with an expiry in engine-clock milliseconds and renews it while its feed is current. A **watchdog**, a small redundant process that reads `source_health` and the engine clock, flips the status to `"expired"` with a compare-and-set when the expiry has passed; the adapter flips it back to `"ok"` when it renews. Freshness is then a function of status alone, and a missing row is stale by construction, because the pack registers every source it depends on:

```iql
+fresh(Src) <- source_health(Src, "ok", _)
+stale(Src) <- source_health(Src, St, _), St != "ok"
+stale(Src) <- source(Src), !source_health(Src, _, _)
```

Which topics depend on which source is itself a policy fact, `topic_source(topic, source)`, read by the claim rules and by the reservation guard, and which tools depend on which source is `tool_requires(tool, source)`, read by `tool_ready` and by the claim guard; each dependency is written once (sections 6.2, 6.4, 9.3, 10.3).

Why status flips and not a clock relation: a clock fact that every rule compares against would sit in the dependency closure of every subscription and re-evaluate all of them on every tick, and if its writer died the clock would freeze with every lease "unexpired" and every claim confident. With status flips, subscriptions re-evaluate only when something changed, and the direction of failure is right: a dead adapter stops renewing, the watchdog flips the status, and every claim that requires `fresh("carrier")` is withdrawn. The remaining single point is the watchdog itself, and section 13.1 says what happens when it dies: the rules stay optimistic for at most one lease period, but no action and no firm reservation passes its guard, because **every guard that depends on time compares the lease expiry with the engine clock** (`Now = time_now(), Now < Until`), not with a fact. Time enters guards from the engine; it never enters rules.

**Missing data is absence**, and absence derives nothing. There is no `eta` row for a shipment the carrier has not reported, so `late` and `on_time` are both underived; a rule derives "no estimate on record" from `!eta(S, _, _, _)`, and the realizer words that as not knowing, never as a negative fact about the world. Section 6.2 states the invariant: an open delivery question on an authorized order derives at least one claim in every freshness state, so misconfiguration produces a spoken "I can't reach my carrier feed", never silence.

**Conflicts between authoritative sources** are not resolved by the engine. Two systems that disagree about a promise date produce rows in two relations, and a rule states which wins; the precedence is readable, testable and provable with `.why`.

**Uniqueness is enforced, not assumed.** A typed relation does not impose one value per entity. The replacement protocol keeps world relations single-valued per key, and the pack makes a violation fail closed rather than fail silently: `eta_conflict(S)` and `note_conflict(S)` derive when two values coexist, every firm claim requires their absence, and an operations standing query on the conflict relations raises the alarm. The same pattern guards policy (section 6.4).

### 4.3 Session facts are persistent and session-keyed

The engine has connection-local "session facts" (a fact written without `+`) that live only on one connection and are excluded from standing queries and from `.why`. This design does not use them for anything a subscription must see. Everything about a conversation is written as **persistent facts keyed by the session**:

```iql
+session(session: string, user: string, status: string)
+utterance_cursor(session: string, last: int)
+goal(session: string, goal: string, kind: string, subject: string)
+requested_date(session: string, goal: string, due: string)
+consent(session: string, goal: string, tool: string, arg: string, utterance: int)
+declined(session: string, goal: string, tool: string, arg: string)
+speech_owner(session: string, owner: string, epoch: int)
+speech_until(session: string, until: int)
+playback(session: string, pb: int, goal: string, topic: string, subject: string,
          value: string, epoch: int, status: string)
+playback_time(session: string, pb: int, completed_at: int)
+playback_text(session: string, pb: int, text: string)
+lease_owner(session: string, executor: string, epoch: int)
+lease_until(session: string, until: int)
```

A reconnecting speech lane re-subscribes and gets the session's current state back as a snapshot; the executor's attempts survive its restart; `.why` can explain a session-derived row. Closing a session is a program that flips `session` to `"closed"`; every claim requires an open session, so all of the session's speech and work rows leave at one revision, and the session's rows are garbage-collected later by a separate program. A late worker cannot revive a closed session: its program's guard requires `session("s-42", _, "open")`.

## 5. The intent boundary: proposals become facts through a gate

The intent stage consumes final user transcripts. In its synchronous `decide_data` it assigns the utterance the next ordinal for the session and appends it to the interpreter's in-process queue. The queue is unbounded and its depth is bounded by how fast a human can speak; a backlog is reported, never dropped. A barge-in that drops the stage's in-flight `perform` therefore never loses an utterance that was already final. The interpreter worker processes a session's utterances **strictly in order**, and commits each proposal before it interprets the next, so a slow interpretation of utterance 6 cannot land after utterance 7's.

The worker runs the intent model over the utterance and the session's recent transcript and produces a **proposal**: goals with kinds and slots, a clarification, a confirmation, or a retraction. The **write gate** turns a proposal into one guarded program or rejects it:

1. **Allow-listed relations.** The intent path may write only `goal`, `requested_date`, `consent`, `declined`, `utterance_cursor` and goal retractions. It can never write a world relation, a policy relation, a playback or an attempt.
2. **Kinds and slot formats.** `kind` is one of the pack's declared kinds (`delivery_status`, `reschedule`, `clarify_order`, `open_question`). An order id matches the tenant's id grammar. A date parses.
3. **Scope.** Every row carries the session constant of the connection that produced it. A proposal naming another session is rejected.
4. **Order and liveness, in the guard.** The program requires the session to be open and the utterance cursor to be older than this utterance, and advances the cursor in the same transaction. A duplicate or late proposal fails its guard and applies nothing.
5. **Schema.** The engine validates types on commit. A statement that violates the declared schema fails, and the whole program is rolled back with the statement index in the error.

Replacing a goal names the goal it replaces; it does not clear the session:

```iql
.require ?session(S, _, "open"), S = "s-42", utterance_cursor(S, N), N < 7
-utterance_cursor("s-42", N) <- utterance_cursor("s-42", N)
+utterance_cursor("s-42", 7)
-goal("s-42", "g-7", K, O) <- goal("s-42", "g-7", K, O)
+goal("s-42", "g-8", "delivery_status", "ORD-5000")
```

Atomic replacement is what makes cancellation clean (section 10.5): every work and speech row derived from `g-7` leaves at the revision `g-8` arrives.

**What the gate does not establish, and what does.** The gate validates shape, scope and order. It does not establish that the user may ask about this order, that a confirmation was real, or that the model understood the utterance. Those are handled where they can be:

- **Entity authorization is a derived relation.** `authorized(Sess, O) <- session(Sess, U, "open"), customer_order(U, O, _)` holds when the session's authenticated user owns the order according to the order system's facts. Every claim and every work intent about an order joins `authorized`. A misheard id that happens to be another customer's order derives nothing except the `unknown_order` claim, "I can't find that order on your account", because that rule is the one that requires `!authorized` (Appendix B, step 12).
- **Consent is bound to the latest delivered question.** A consent-mode tool first derives a `confirm` claim carrying the exact tool and argument ("Shall I reschedule ORD-4821 to Monday, October 12th?"). `asked(Sess, G, Tool, Arg, Pb)` holds only for the **latest completed** playback of a confirm claim in that goal, by playback ordinal; an earlier question is not askable any more. The gate accepts a confirmation only through a guard on `asked` for the same tool and argument, within a window measured by the engine clock against the playback's completion time:

```iql
.require ?asked(S, G, T, A, Pb), S = "s-42", G = "g-9", T = "reschedule_delivery",
         A = "2026-10-12", playback_time(S, Pb, At), Now = time_now(),
         Lim = At + 120000, Now < Lim
+consent("s-42", "g-9", "reschedule_delivery", "2026-10-12", 9)
```

  The work intent joins `consent` on the same argument, so a later change of date derives a new confirm question and a new consent, with a fresh attempt budget (Appendix B, step 13). The chain of trust is: a question the device finished playing, the user's next utterance, the intent model's reading of it, and the guard that binds that reading to the latest pending question.
- **Semantic misinterpretation remains possible**, and the design says so. The user may have said "yes" to something else. Mitigation is policy, not magic: the window above; for irreversible tools the confirmation must repeat the slot ("yes, Monday"), which the gate checks against `requested_date`; anything else is a clarification.
- **Ambiguity** becomes `goal("s-42", "g-8", "clarify_order", "")`. No tool rule matches that kind, so nothing can be executed from it; a speech rule derives the clarifying question. At no point does model text reach a tool: the only path to an external operation is an `eligible` row, derived from facts.

## 6. The rule pack: claims, speech, work and policy

Rules are persistent (`+head <- body`), stored in the knowledge graph's rule catalog, and evaluated by the engine. Negation is stratified: a relation may not depend negatively on itself. Negation is also **range-restricted**: a negated literal must share a variable with a positive literal, in rules and in queries alike, and the engine enforces it at evaluation time. A rule that breaks it registers and then fails on every query, which is why section 11 insists that registration is not validity. Constant-only conditions are therefore written as positive literals on a complementary relation (`stale("carrier")`, not `!fresh("carrier")`), and every guard in this article binds a shared variable before negating. Aggregates are grouped by the head's other columns. The derived result is a deterministic function of the base facts, and it is **not monotone** in them: adding a fact can withdraw a conclusion. That is exactly what corrections need, and it is what the differential oracle in the engine's test suite checks. The complete pack is in Appendix A; the sections below explain it.

### 6.1 Knowledge and integrity

```iql
+late(O)    <- shipment(O, S, _), eta(S, D, _, _), promised(O, P, _), D > P
+on_time(O) <- shipment(O, S, _), eta(S, D, _, _), promised(O, P, _), D <= P
+eta_conflict(S)    <- eta(S, D1, R1, A1), eta(S, D2, R2, A2), D1 != D2
+note_conflict(S)   <- carrier_note(S, A, R1, T1), carrier_note(S, B, R2, T2), A != B
+policy_conflict(T) <- tool_policy(T, M1), tool_policy(T, M2), M1 != M2
+authorized(Sess, O) <- session(Sess, U, "open"), customer_order(U, O, _)
+latest_note_at(S, max<At>) <- carrier_note(S, _, _, At)
+note_covers(S) <- latest_note_at(S, NoteAt), eta(S, _, _, EtaAt), NoteAt >= EtaAt
```

The conflict rules name every column of their two atoms on purpose. Each `_` in a rule body is a fresh anonymous variable in the engine the article tree builds on; engines before that fix joined two `_` placeholders at the same position of one relation, which would have made `eta(S, D1, _, _), eta(S, D2, _, _)` match only rows with equal revisions and times, and the conflict rule silent. Named variables hold on both, and Appendix B, step 10b, shows the rule firing: a second ETA value for `S-77` withdraws the firm claim and derives `eta_conflict("S-77")`.

### 6.2 Claims: what is true, supported and allowed to be said

A **claim** is a row `claim(Session, Goal, Topic, Subject, Value)`: the current value the session may assert about a subject under a topic. Claims carry their support in their bodies: the goal, the authorization, the freshness of the source, the absence of conflicts.

```iql
+topic_source[("eta", "carrier")]
+claim(Sess, G, "eta", O, D) <-
    goal(Sess, G, "delivery_status", O), authorized(Sess, O), shipment(O, S, _),
    eta(S, D, _, _), !eta_conflict(S), topic_source("eta", Src), fresh(Src)
+claim(Sess, G, "eta", O, "unknown") <-
    goal(Sess, G, "delivery_status", O), authorized(Sess, O), shipment(O, S, _),
    !eta(S, _, _, _), topic_source("eta", Src), fresh(Src)
+claim(Sess, G, "eta_last_known", O, D) <-
    goal(Sess, G, "delivery_status", O), authorized(Sess, O), shipment(O, S, _),
    eta(S, D, _, _), !eta_conflict(S), topic_source("eta", Src), stale(Src)
+claim(Sess, G, "eta_last_known", O, "unknown") <-
    goal(Sess, G, "delivery_status", O), authorized(Sess, O), shipment(O, S, _),
    !eta(S, _, _, _), topic_source("eta", Src), stale(Src)
+claim(Sess, G, "carrier_reason", O, Why) <-
    goal(Sess, G, "delivery_status", O), authorized(Sess, O), shipment(O, S, _),
    late(O), carrier_note(S, Why, _, _), !note_conflict(S)
+claim(Sess, G, "unknown_order", O, O) <-
    goal(Sess, G, "delivery_status", O), session(Sess, _, "open"), !authorized(Sess, O)
+claim(Sess, G, "clarify", "order", "which") <-
    goal(Sess, G, "clarify_order", _), session(Sess, _, "open")
+claim(Sess, G, "confirm", "reschedule_delivery", D) <-
    goal(Sess, G, "reschedule", O), authorized(Sess, O), requested_date(Sess, G, D),
    tool_policy("reschedule_delivery", "confirm"),
    !consent(Sess, G, "reschedule_delivery", D, _), !declined(Sess, G, "reschedule_delivery", D)
+claim(Sess, G, "answer", Q, "") <-
    goal(Sess, G, "open_question", Q), session(Sess, _, "open")
+unconfirmed_need(Sess, G, T, Subj, Arg, Ep) <-
    attempt(Sess, G, T, Subj, Arg, Ep, Id, _, _, _), attempt_unconfirmed(Id)
+claim(Sess, G, "action_pending", T, Subj) <-
    work_intent(Sess, G, T, Subj, Arg, Ep), satisfied(Sess, G, T, Subj, Arg, Ep),
    !unconfirmed_need(Sess, G, T, Subj, Arg, Ep)
+claim(Sess, G, "action_unconfirmed", T, Subj) <-
    work_intent(Sess, G, T, Subj, Arg, Ep), unconfirmed_need(Sess, G, T, Subj, Arg, Ep)
+claim(Sess, G, "action_failed", T, Subj) <-
    work_intent(Sess, G, T, Subj, Arg, Ep), exhausted(Sess, G, T, Subj, Arg, Ep)
+claim(Sess, G, "cannot_run", T, Subj) <-
    work_intent(Sess, G, T, Subj, Arg, Ep), !tool_ready(T)
```

The source a topic depends on is registered once, in `topic_source`; the firm `eta` claims require that source `fresh`, and the "last known" claims are its stale counterpart, which is why they read the same registration.

Four properties of this shape matter. A claim's **value transitions are complete** for its topic: the ETA topic moves between a date, `"unknown"`, a stale "last known" date and a stale "unknown", and every move is a value change the speech rules turn into the right utterance. A claim **disappears when its support disappears**, which is a different event from being heard: the goal retracted, access revoked, a conflict detected. **Absence is worded as not knowing**: `"unknown"` is a value the realizer renders as "I don't have a delivery estimate yet", never as "there is no delivery". And **work is never silent**: a consented action that cannot run, is waiting for its record, has waited longer than the confirmation bound, or has failed derives a claim of its own, so the user is told rather than left waiting.

The invariant the pack test asserts: for every open `delivery_status` goal on an authorized order, in every freshness state and with or without an `eta` row, at least one `eta` or `eta_last_known` claim derives. Appendix B, step 11, drives it through `"ok"`, `"expired"` and no health row at all.

### 6.3 Speech: pending versus supported

Speech is level-triggered. What the user has heard is reconstructed from **playbacks**, the receipts of section 9.5, and reduced to the latest audible value per topic. A playback counts as heard once any of its audio was consumed by the device.

```iql
+audible[("playing"), ("completed"), ("interrupted"), ("superseded"), ("uncertain")]
+partial[("interrupted"), ("uncertain")]
+heard_pb(Sess, G, T, Subj, max<Pb>) <- playback(Sess, Pb, G, T, Subj, _, _, St), audible(St)
+heard(Sess, G, T, Subj, V) <- playback(Sess, Pb, G, T, Subj, V, _, _), heard_pb(Sess, G, T, Subj, Pb)
+incomplete(Sess, G, T, Subj) <- playback(Sess, Pb, G, T, Subj, _, _, St),
                                heard_pb(Sess, G, T, Subj, Pb), partial(St)
+asked_latest(Sess, G, max<Pb>) <- playback(Sess, Pb, G, "confirm", _, _, _, "completed")
+asked(Sess, G, T, A, Pb) <- playback(Sess, Pb, G, "confirm", T, A, _, "completed"),
                            asked_latest(Sess, G, Pb)
```

The `speech` relation is what the speech loop subscribes to. It carries **two kinds of rows**: `supported` rows, one per claim, which say a claim is still valid, and pending rows, which say what should be said and how. Priorities come from a per-topic table so that best-effort answers rank below facts and corrections rank above statements:

```iql
+topic_priority[("eta", 2), ("eta_last_known", 2), ("carrier_reason", 2), ("unknown_order", 2),
                ("clarify", 2), ("confirm", 2), ("action_pending", 3), ("action_unconfirmed", 2),
                ("action_failed", 2), ("cannot_run", 2), ("answer", 5)]
+speech(Sess, G, T, Subj, V, "supported", 9) <- claim(Sess, G, T, Subj, V)
+speech(Sess, G, T, Subj, V, "state", P) <- claim(Sess, G, T, Subj, V),
                                          !heard(Sess, G, T, Subj, _), topic_priority(T, P)
+speech(Sess, G, T, Subj, V, "correction", P1) <- claim(Sess, G, T, Subj, V),
                                                heard(Sess, G, T, Subj, H), H != V,
                                                topic_priority(T, P), P1 = P - 1
+speech(Sess, G, T, Subj, V, "restate", P2) <- claim(Sess, G, T, Subj, V),
                                             heard(Sess, G, T, Subj, V), incomplete(Sess, G, T, Subj),
                                             topic_priority(T, P), P2 = P + 1
```

`(Goal, Topic, Subject)` is the **claim key**. The rules are generic over topics, so every transition is covered by the same three rules: a date the user heard that is no longer the current date yields a `correction`; a heard date that becomes `"unknown"` yields a correction whose value is `"unknown"` ("I no longer have an estimate"); a heard carrier reason replaced by another yields a correction; a value heard only partially, because playback was interrupted or the speech owner died, yields a `restate` once per interruption, and nothing while the sentence is still playing.

**Open questions** are rows like any other: the `answer` claim carries the utterance id as its subject and an empty value, so it is re-realized once per interruption and never corrected, because its value cannot change; the text that was actually spoken is recorded by the pump in `playback_text`, and `heard` withdraws the row. No correction logic applies to best-effort language by construction.

**Invariants, enforced.** At most one pending row exists per claim key, because the `state`, `correction` and `restate` guards are mutually exclusive; a pack test asserts it over generated states (section 15). Selection order is the total order `(Priority, Goal, Topic, Subject)`; pending rows of distinct keys are independent, so a tie between them is a choice of sequence, not a choice between truths. Two claims with the same key and different values cannot both exist: they would need two `eta` rows, and `eta_conflict` withdraws both.

### 6.4 Work: needs, attempts, and the right to continue

A **work item** is a need: `work_intent(Session, Goal, Tool, Subject, Arg, Episode)`. `Subject` and `Arg` are what the tool acts on; `Episode` identifies the need, so that retries of one need share a budget and a new need gets a fresh one. For a carrier check the episode is the source revision of the ETA being explained, which changes only when the value changes (section 4.1); for a reschedule it is the consent that authorized the date:

```iql
+work_intent(Sess, G, "carrier_check", S, "", Rev) <-
    goal(Sess, G, "delivery_status", O), authorized(Sess, O), shipment(O, S, _),
    late(O), eta(S, _, Rev, _), !eta_conflict(S), !note_covers(S)
+work_intent(Sess, G, "reschedule_delivery", O, D, Utt) <-
    goal(Sess, G, "reschedule", O), authorized(Sess, O), requested_date(Sess, G, D),
    consent(Sess, G, "reschedule_delivery", D, Utt), promised(O, P, _), P != D
```

A carrier check is wanted while the order is late, the ETA is not in conflict, and no carrier note was observed at or after the current ETA was observed: a note from an earlier episode does not suppress a new check, and a note that explains the current ETA does. A new ETA value is a new episode with a fresh budget, so two successful checks never exhaust a third (Appendix B, step 10), and a re-observed unchanged value is no episode at all, because it is never written (step 4b). A reschedule is wanted while the consented date differs from the promise on record, so the intent withdraws itself when the order system's own update arrives; a second date in the same goal is a new episode, carried in the row the executor receives (step 13).

Policy and attempts are facts; eligibility, continued authorization and cancellation are derived:

```iql
+tool_policy(tool: string, mode: string)        // "auto" | "confirm" | "disabled"
+max_attempts(tool: string, n: int)
+kill_switch(tool: string)
+tool_requires(tool: string, source: string)
+attempt(session: string, goal: string, tool: string, subject: string, arg: string,
         episode: int, attempt: string, executor: string, epoch: int, ordinal: int)
+attempt_task(attempt: string, task: string)
+attempt_done(attempt: string, status: string, retryable: string, ready_at: int, detail: string)
+attempt_unknown(attempt: string, revisit_at: int)

+tool_enabled(T) <- tool_policy(T, M), M != "disabled", !tool_policy(T, "disabled"),
                    !kill_switch(T), !policy_conflict(T)
+tool_ready(T) <- tool_enabled(T), !tool_requires(T, _)
+tool_ready(T) <- tool_enabled(T), tool_requires(T, Src), fresh(Src)
+unresolved(Sess, G, T, Subj, Arg, Ep, Id) <- attempt(Sess, G, T, Subj, Arg, Ep, Id, _, _, _),
                                             !attempt_done(Id, _, _, _, _)
+satisfied(Sess, G, T, Subj, Arg, Ep) <- attempt(Sess, G, T, Subj, Arg, Ep, Id, _, _, _),
                                        attempt_done(Id, "ok", _, _, _)
+failures(Sess, G, T, Subj, Arg, Ep, count<Id>) <- attempt(Sess, G, T, Subj, Arg, Ep, Id, _, _, _),
                                                  attempt_done(Id, "failed", _, _, _)
+exhausted(Sess, G, T, Subj, Arg, Ep) <- failures(Sess, G, T, Subj, Arg, Ep, N), max_attempts(T, M), N >= M
+exhausted(Sess, G, T, Subj, Arg, Ep) <- attempt(Sess, G, T, Subj, Arg, Ep, Id, _, _, _),
                                        attempt_done(Id, "failed", "no", _, _)
+eligible(Sess, G, T, Subj, Arg, Ep) <- work_intent(Sess, G, T, Subj, Arg, Ep), tool_ready(T),
                                       !unresolved(Sess, G, T, Subj, Arg, Ep, _),
                                       !satisfied(Sess, G, T, Subj, Arg, Ep),
                                       !exhausted(Sess, G, T, Subj, Arg, Ep)
+run_ok(Id) <- attempt(Sess, G, T, Subj, Arg, Ep, Id, _, _, _), unresolved(Sess, G, T, Subj, Arg, Ep, Id),
               work_intent(Sess, G, T, Subj, Arg, Ep), tool_enabled(T)
+cancel_due(Id) <- unresolved(_, _, _, _, _, _, Id), !run_ok(Id)
+work("start", Sess, G, T, Subj, Arg, Ep, "") <- eligible(Sess, G, T, Subj, Arg, Ep)
+work("cancel", Sess, G, T, Subj, Arg, Ep, Id) <- attempt(Sess, G, T, Subj, Arg, Ep, Id, _, _, _), cancel_due(Id)
+work("reconcile", Sess, G, T, Subj, Arg, Ep, Id) <- attempt(Sess, G, T, Subj, Arg, Ep, Id, _, Epoch, _),
                                                     unresolved(Sess, G, T, Subj, Arg, Ep, Id),
                                                     lease_owner(Sess, _, Cur), Epoch < Cur
+work("reconcile", Sess, G, T, Subj, Arg, Ep, Id) <- attempt(Sess, G, T, Subj, Arg, Ep, Id, _, _, _),
                                                     attempt_unknown(Id, _), !attempt_done(Id, _, _, _, _)
+work("reconcile", Sess, G, T, Subj, Arg, Ep, Id) <- attempt(Sess, G, T, Subj, Arg, Ep, Id, _, _, _),
                                                     attempt_done(Id, "ok", _, _, _),
                                                     work_intent(Sess, G, T, Subj, Arg, Ep), !attempt_unconfirmed(Id)
```

The properties follow from the shape of the rules, not from discipline:

- **Default deny, fail closed.** `eligible` needs `tool_ready`, which needs `tool_enabled`, which needs a positive policy row and is withdrawn by a `disabled` row, a `kill_switch` row or a `policy_conflict`. A tool with no policy, or with two contradictory policies, can never be executed, whatever the intent model proposes. A tool that depends on a source's freshness declares it in `tool_requires`; a carrier check declares none, because a direct call to the carrier is the remedy for a stale feed, not something to block on it.
- **"May start" is not "may continue".** `eligible` says a new attempt may be started: the need holds, the tool is ready, nothing is unresolved, no success awaits its observation, the budget is not exhausted. `run_ok` says an existing attempt is still wanted and allowed: the need still holds and the tool is still enabled. Claiming an attempt withdraws `eligible` and does not withdraw `run_ok`, so a successful claim never cancels itself (Appendix B, step 5). A goal retraction, a kill switch, a disabled policy or a withdrawn consent withdraw `run_ok`, and `cancel_due` tells the executor which attempt to stop (step 6).
- **Success blocks a second effect, and has an exit.** `satisfied` holds from the `ok` outcome until the need withdraws itself. Normally that is immediate, because the executor is the adapter for the tool's own API and writes the observation the API returned in the same transaction as the outcome (section 10.4). When the API confirms but returns no record, `action_pending` tells the user the request went through, a `reconcile` row keeps the owner re-reading the order by key, and when the confirmation bound passes the owner writes `attempt_unconfirmed`, which turns the claim into `action_unconfirmed`: "I requested it, but I have not been able to confirm it." No second ordinal is ever allocated for a satisfied need.
- **Failure is typed and budgets count failures only.** `attempt_done` carries the status, whether it is retryable, and the earliest engine-clock time a retry may run. A permanent failure exhausts the need at once; a retryable one leaves it eligible, with the backoff enforced in the claim guard (section 10.3). Cancelled, not-started and unknown outcomes never count.
- **Unknown is not terminal.** An inconclusive lookup is recorded in `attempt_unknown`, not in `attempt_done`, so the attempt stays unresolved and protected by `run_ok`, no second ordinal is allocated, and a `reconcile` row tells the owner to look again; the executor revisits at `revisit_at` by its own timer. When the lookup resolves, the terminal program deletes the `attempt_unknown` row in the same transaction, and the `reconcile` clause also requires `!attempt_done`, so a resolved attempt is never reconciled again (step 16).
- **Unknown is not negative.** `work_intent` requires `late(O)`, which requires an accepted ETA. A missing ETA derives no work.

### 6.5 Where guardrails are enforced

A model being shown rules is not enforcement. Enforcement here is validation that does not involve a model's judgement:

1. **The write gate** (section 5): what the intent path may assert, typed by schema, scoped by session, ordered by the utterance cursor, rolled back atomically on any violation.
2. **The action gate**: the executor subscribes to `work` and to nothing else, and its claim program is guarded on `eligible` at commit (section 10.3). Tool arguments are the row's columns, which came from facts, never from the model's text.
3. **The speech gate**: a sentence that carries a claim is rendered from a template over the claim's values; the agenda reserves it only if the claim's `supported` row is present with the same value at commit, and the pump re-checks before each chunk (section 9.4).
4. **Best-effort language is separated from claims.** Open questions and small talk go to the LLM over a bounded snapshot of the session's current claims. Its output carries no claim, is never the source of a receipt a rule would treat as a heard fact, and passes a **sanitizer**, not a validator: any date, order id, amount or tool name in the text that is not in the snapshot it was given is replaced by a safe phrase, and output that fails the pattern check falls back to a fixed holding sentence. The sanitizer cannot detect "it will not arrive on October 8th"; the design does not claim it can. What it guarantees is that every sentence the system treats as a claim was produced by a template over accepted facts, and every sentence produced by the model is spoken as the model's language, framed as such ("as far as I can tell"), while the view is fresh.

Behavioural rules that only shape tone or verbosity ride in the realizer prompt and are advisory. The architecture is explicit about which is which.

## 7. Standing subscriptions: the delivery contract

### 7.1 Snapshot, then deltas

The speech loop subscribes once per session, bound to the session constant and to its own ownership:

```json
{"type": "execute", "id": "sub-1",
 "program": ".subscribe speech ?speech(\"s-42\", G, Topic, Subj, Value, Kind, Prio), speech_owner(\"s-42\", \"sp-1\", 1)"}
```

The reply is an ordinary result holding the **initial snapshot**, plus a `subscribed` block:

```json
{"type": "result", "id": "sub-1",
 "columns": ["s-42", "G", "Topic", "Subj", "Value", "Kind", "Prio"],
 "rows": [["s-42", "g-7", "eta", "ORD-4821", "2026-10-08", "state", 2],
          ["s-42", "g-7", "eta", "ORD-4821", "2026-10-08", "supported", 9]],
 "subscribed": {"subscription": "speech", "generation": 1, "revision": 1711}}
```

The snapshot is the query's exact answer at revision 1711. Every position of the goal atom is a column, the bound session constant included, so each row repeats `"s-42"` in its first position; the trailing `speech_owner` literal only filters and is not projected. It is there so that the moment this owner loses the session, its whole result empties (section 9.2). From then on, after each committed change that can affect the result, the server pushes a delta. This is the one the carrier revision produces while the first ETA is playing (Appendix B, step 4):

```json
{"type": "subscription_delta", "subscription": "speech", "generation": 1,
 "knowledge_graph": "support_acme", "seq": 2, "revision": 1731,
 "columns": ["s-42", "G", "Topic", "Subj", "Value", "Kind", "Prio"],
 "inserted": [["s-42", "g-7", "eta", "ORD-4821", "2026-10-10", "correction", 1],
              ["s-42", "g-7", "eta", "ORD-4821", "2026-10-10", "supported", 9]],
 "retracted": [["s-42", "g-7", "eta", "ORD-4821", "2026-10-08", "supported", 9]]}
```

The `state` row had already left at the earlier revision where the `playing` receipt was committed; this push withdraws the old value's `supported` row and inserts the new value's `supported` and `correction` rows, at one revision.

- `inserted` and `retracted` are rows that entered and left the result since the previous push. Set semantics: a row is in or out; an unchanged result pushes nothing.
- `seq` starts at 1 per subscription and increases by one per push. A gap means a push was lost.
- `revision` is the knowledge-graph revision the push brings the result to: previous result plus this delta equals the query's exact answer at `revision`. It strictly increases.
- `generation` identifies this registration; after `.unsubscribe` and a new `.subscribe` with the same name, a push with the old generation is recognisably stale.
- A snapshot or delta whose frame would exceed 1 MiB is streamed as one logical payload (`subscription_delta_start`, `subscription_delta_chunk`s of at most 500 rows, `subscription_delta_end` with the counts the chunks must add up to) and applied only at its end; until then the previous result stands. No frame exceeds the 16 MiB message limit.

The engine also pushes change notifications (`persistent_update`, `rule_change`, `kg_change`) naming a relation and an operation count. They are a separate stream, and this architecture's consumers do not act on them: a notification says a relation changed; a delta says which derived rows changed.

### 7.2 What the engine does per commit

![The fact, rule and subscription loop](/blog/voice-agent/loop.svg)

A subscription records the **dependency closure** of its query: the relations in the body plus, transitively, the bodies of the persistent rules defining them. A commit to a relation outside that closure costs the subscription nothing. A commit inside it schedules a re-evaluation; at most one evaluation runs per subscription, and commits that land meanwhile are coalesced into one follow-up evaluation, so a burst produces few pushes and the last one reflects the final state. Filtering is by relation, not by row: a renewal of any lease expiry would re-evaluate every query whose closure contains that relation, which is why the executor's query joins `lease_owner`, which changes only on takeover, and never `lease_until`, which is renewed constantly and read only by guards (section 13.3).

Today's evaluation strategy re-runs the query against a pinned snapshot and diffs with the previous result; a differential strategy can replace it behind the same trait and wire protocol. The query is bound by the session constant, so the engine's demand-driven rewrite (Magic Sets) evaluates the slice of the graph the bindings reach. That is an optimization, not a bound: a session whose subject joins a broad relation, a deep recursion or many open goals still pays for what it reaches (section 13.3).

Two things this contract does **not** promise, and the design does not rely on:

- **Not one delta per commit.** Coalescing means an intermediate state can be skipped. A `work_intent` that appears and disappears between two evaluations is never seen by anyone, and that is correct for desired state: if the need vanished before anyone acted, no action was needed. What must not be lost is **durable as a fact**: the `goal` persists until the user changes it, so `work_intent` is stable until it is satisfied or withdrawn, and every consumer reconciles desired state against recorded state (`attempt`, `playback`) the way a controller reconciles a declared spec. A standing result is a level, not an event log.
- **No barrier across subscriptions.** Two subscriptions on the same graph receive pushes independently; their revisions are not a common snapshot, and an unchanged result never pushes, so "wait until both views reach R" neither aligns them nor terminates. The design therefore never joins streams. Each consumer holds **one composite subscription** that already carries everything it decides on: the speech loop's `speech` relation holds validity, pending rows and ownership together; the executor's `work` relation holds start, cancel and reconcile rows together, joined on its lease ownership. And no decision is taken on a view alone: every action commits through a guarded program that the engine evaluates against one snapshot (section 8.2).

### 7.3 Recovery

| Signal | Meaning | Consumer action |
|---|---|---|
| Connection lost | Subscriptions never survive a connection | Mark the view unverified, stop acting on it, reconnect, `.subscribe` again, rebuild from the new snapshot |
| `seq` gap | A push was lost | Same: resubscribe |
| `subscription_error` | Re-evaluation failed (access revoked, result over the row cap) | The server keeps the last complete result as the base for the next delta, but a later evaluation with an unchanged result pushes nothing, so recovery would be unobservable. The consumer resubscribes; the fresh snapshot is the verification. If the cause is size, narrow the query |
| `notice: notifications_missed` | The connection read too slowly; server-side broadcast lag | The engine re-evaluates every standing query itself. The consumer treats its view as unverified until the next push or a resubscribe, whichever comes first |
| Push with an old `generation` | From a previous registration | Ignore |
| `subscription_reset` | The server ended the subscription: a change it could not deliver whole (a single row larger than any frame) or read access revoked | Resubscribe once the cause is cleared; the fresh snapshot is the verification |
| Connection closed after an unread frame | The client left a frame unread for `http.ws_send_timeout_ms` (default 30 s) | Same as a lost connection; a consumer that stops reading is disconnected rather than allowed to stall the server |
| Result empties on an ownership join | This consumer lost the session's lease | Stop; mark its in-flight playback or attempt as the successor will expect (sections 9.2, 10.6) |

"Unverified" has a precise meaning for each consumer. The agenda keeps playing the sentence in flight, selects nothing new, and the realizer's best-effort path is suspended (section 13.1). The executor stops claiming. Neither invents state, and neither needs the view to be verified to stay safe, because every action it would take is guarded at commit.

**The registration race.** A commit that lands after the snapshot's revision but before the subscription exists would reach nobody. The engine closes this itself: at registration it compares the graph's current revision with the snapshot's, and if the graph moved on it re-evaluates at once and pushes the difference. The consumer sees snapshot, then delta, with no gap, and the delta may of course be followed by more.

## 8. Programs, guards and the write-ahead log

### 8.1 One program, one transaction, one revision

Every write in this architecture is a **program**: one `execute` request carrying one or more statements. A program that changes persistent state commits all of its changes as one transaction on its knowledge graph: facts, deletes, conditional updates, schema declarations, rules and rule removals. They take effect at one revision, with one write-ahead-log record and one snapshot publish, or none does. Subscribers are notified after the publish, so no standing query ever observes part of a program. Within a program, a statement that reads state sees the changes staged by the statements before it.

| Outcome | Meaning | Writer's response |
|---|---|---|
| success, `errors` empty | Every statement applied | Proceed |
| statement error (`validation`, `not_found`, …) | That statement failed; nothing in the program was applied; the message names the index | Fix or drop the proposal |
| `precondition_failed` (target) | A guard found no row at a committed snapshot; nothing applied | Definitive: the writer's intent is stale. Re-read the state; do not retry blindly |
| `conflict` | A state-reading program kept going stale under concurrent writes after eight re-stagings | Not an answer: nobody could evaluate it. Retry with backoff |
| `deadline_exceeded`, `cancelled` | Stopped before committing; nothing applied | Retry if still wanted |
| `outcome_unknown` | The commit itself failed in a way that may have applied the changes; restart recovery may include or discard the transaction | Read the state back before retrying |
| `store_read_only` | After an `outcome_unknown` the store refuses every later write, across all knowledge graphs, until restart recovery | Treat the engine as unavailable for writes (section 13.1); page the operator |

Guarded programs can be resent safely after any of these, because the guard decides at commit whether the write still applies. What the engine does **not** provide is an exactly-once external effect; section 10 does that with idempotency keys at the effect.

### 8.2 Guards: compare-and-set over any condition

The engine already treats a conditional delete or update as compare-and-set: the statement is staged against a snapshot, its **read set** is recorded as the relation names in its query's dependency closure through rules, and at commit, under the write lock, the engine refuses the program if any relation in that set changed since staging. A refused program is re-staged, with its conditions evaluated again against the new state, up to eight times, and then fails with `conflict`. This design generalizes the mechanism with one target statement, and states its contract completely:

> **`.require <query>`** inside a program (target extension).
> **Evaluation.** The query is evaluated against the snapshot taken when the program's first state-reading statement stages, plus the changes staged by the statements before the guard, so a guard placed after a conditional delete sees that delete. Its final evaluation runs under the write lock at commit, where the stale check runs, so it is linearizable with the commit.
> **Outcome.** No row at that committed snapshot: the program fails with `precondition_failed` and nothing is applied; this is a definitive answer. A concurrent commit to a relation in the guard's read set before the lock: the program is re-staged and the guard re-evaluated, as for conditional updates; after eight re-stagings it fails with `conflict`, which is not an answer.
> **Read set.** The relation names in the query's dependency closure through rules. A guard over `eligible` therefore conflicts with every commit, by any session of the tenant, to any relation in the closure of `eligible`: goals, sessions, orders, ETAs, notes, policy, attempts and outcomes. That footprint is the price of guarding on a derived relation, and the executor's retry competes with the same traffic. Guards are therefore written to check what the writer must be sure of and no more; the refinement this extension should carry is a tuple-level read set for base relations, with the relation-level set as the fallback.
> **Validity.** The query is range-restricted like any other: a negated literal must share a variable with a positive literal, so `attempt(..., Id, ...), !attempt_done(Id, ...)` is valid and `!attempt_done("att-9f3", ...)` alone is not.

The executor's lease takeover needs no guard either, because an update statement may delete and insert in **several relations at once**, under one body. The owner and expiry of a lease are separate relations (section 7.2); the takeover is one compare-and-set over both:

```iql
-lease_until("s-42", U), -lease_owner("s-42", Old, E),
+lease_until("s-42", 1791069285000), +lease_owner("s-42", "exec-2", E1) <-
    lease_until("s-42", U), lease_owner("s-42", Old, E), Now = time_now(), U < Now, E1 = E + 1
```

Two executors racing for an expired lease both send their version, with the same new expiry if their clocks agree. The first to commit replaces both rows and increments the epoch. The second is re-staged against the new state, its body matches nothing (the lease is no longer expired), and its program commits as a no-op; its reply reports zero rows changed, which is how the loser learns it lost. Renewal is one compare-and-set on `lease_until` that **joins the owner and the epoch the renewer holds**, `lease_owner("s-42", "exec-1", 4)`, with `Now < U`: an owner that let its lease expire cannot renew it, a replaced owner that is still running cannot extend its successor's lease, and a renewal never touches `lease_owner`, so it re-evaluates no `work` subscription. Appendix B, step 18, is this race on the engine, together with a zombie's refused renewal.

### 8.3 What the WAL recovers, and what it cannot

Each transaction is one WAL record with a checksum, and the trailing newline is the commit boundary. On restart the engine replays the intact prefix of committed transactions; a record torn by a crash holds no committed data and is dropped. A program is recovered completely or not at all, and the rules and schemas it changed are in the same record as its facts.

The WAL recovers **graph state**. It knows nothing about audio and nothing about external systems. Whether the user heard a sentence is reconstructed from playback receipts (section 9.5). Whether a carrier API call happened is reconstructed by the executor from attempt facts and the backend's idempotency key (section 10.6). No write to the graph is atomic with a sound wave or an HTTP call, and the design never assumes one is.

## 9. The active speech loop

### 9.1 The runtime contract this builds on

![Data flow and control flow in the runtime](/blog/voice-agent/lanes.svg)

A voicestack stage is a `Processor` with a synchronous, state-owning `decide_data` / `decide_system` and an asynchronous, cancellable `perform` that may do I/O but never mutates state. Frames travel on two typed lanes: the data lane (audio, transcripts, voice edges, model and dispatch protocol frames, application frames) in FIFO order downstream, and the system lane, which is drained first and carries `Start`, `Stop` and `Interrupt` downstream and `Error` upstream. While a stage's `perform` runs, the run loop races it against the system lane; an `Interrupt` drops the in-flight future, and because only `decide_*` ever mutated state, **stage state is not torn**. That is the whole guarantee: a dropped future does not undo a request already sent to a remote synthesizer or a generation already streaming, which is why the pipeline's own flush and the pump's own checks, not the dropped future, decide what reaches the loudspeaker (section 9.4).

Every frame carries a per-link sequence stamp shared by both lanes, which makes the interrupt flush **causal**: on `Interrupt`, a stage drops queued data frames stamped before the interrupt unless they survive flush, and keeps everything stamped after it. The barge-in stage sends the `Interrupt` and then re-emits the `SpeechStarted` edge behind it, so the user's new utterance is never destroyed by the interrupt it caused. What survives a flush is durable state: `Model(Input)`, completed `ToolCall`s, every `Dispatch` frame. What is dropped is the interrupted turn's output: audio, generated transcripts, voice edges, claim markers.

### 9.2 The agenda is an active stage and the session's speech owner

An ordinary stage wakes only when a frame arrives. The agenda must also wake when the graph changes, with no user turn and no pending task, so it is an **active stage**: it overrides `run` and polls, as one future, the inbound lanes, the engine connection and the realizer's completions. The system lane preempts everything; the data lane, the engine channel and completions are polled **fairly** (round-robin after the system lane), so a continuously busy data lane cannot starve a delta. Forwarding a frame downstream is a bounded send raced against the system lane, so a blocked downstream never makes the stage deaf to an `Interrupt`. An `Interrupt` is forwarded and does not stop engine polling.

The stage is the **speech owner** of its session. Ownership is `speech_owner(session, owner, epoch)` with its expiry in `speech_until`, taken over with the same one-statement compare-and-set over both relations and renewed with the same owner-joined renewal as the executor's lease (section 8.2), and every playback it creates carries its epoch. Its subscription joins `speech_owner` for its own name and epoch, so the moment another owner takes the session, its result empties in one push and it stops; the pump reads the same view, so it stops too. A partitioned owner that never receives that push is bounded by its lease: the agenda checks the expiry it last renewed against its own clock before every reservation, and the pump before every chunk, so double speech lasts at most one lease period, and the fault suite asserts it (section 15). On takeover, the new owner marks every `reserved` playback of the old epoch `abandoned` and every `playing` one `uncertain`, with compare-and-sets on the exact previous status, before it selects anything.

It owns the **view**: the current `speech` rows with their revision, published through an atomically swapped pointer so the playout pump reads the same view without a lane hop. The agenda state is: the view, the floor (from `SpeechStarted` / `SpeechStopped`), and the playback in flight, if any. Selection runs after every change:

- If the user holds the floor, hold.
- Otherwise pick the pending row with the smallest `(Priority, Goal, Topic, Subject)` whose key has no playback in flight.
- If a playback is in flight and its key's `supported` row is present with the same value, let it finish.
- If its key's `supported` row is present with a **different value**, it is superseded: the agenda sends an `Interrupt` down the system lane, which drops the realizer's and the synthesizer's in-flight work and flushes their queued output exactly as a barge-in would, and then reselects. The pump distinguishes the two interrupts by the view (section 9.4).
- If its key's `supported` row is **absent**, the claim lost its support: the goal is gone, access was revoked, the feed went stale, a conflict appeared, the owner lost the session, or the view itself is unverified (section 7.3). The agenda interrupts the same way; the pump marks the playback `interrupted` if audio had played and the agenda marks it `abandoned` otherwise. Absence is never assumed benign; validity and pending-to-say are separate rows precisely so that this check has the information it needs.

This is why the agenda is **semantic state and not a FIFO of audio**: it replaces, cancels or defers by claim key, with no task ids, because the engine already resolved coalescing (one pending row per key), relevance (only supported claims exist), supersession (retract plus insert at one revision) and already-delivered (pending rows leave when heard).

### 9.3 Playback: the state machine of one sentence

A **playback** is one attempt to say one claim value. Its row is `playback(session, pb, goal, topic, subject, value, epoch, status)`, where `pb` is a per-session ordinal the owner allocates under a guard, and its lifecycle is a set of compare-and-set transitions on the exact previous status:

| From | To | Written by | When |
|---|---|---|---|
| — | `reserved` | agenda | the claim is selected; the guard requires its `supported` row with this value, the owner's unexpired lease by the engine clock, and that this ordinal is unallocated |
| `reserved` | `playing` | pump | the first chunk after `ClaimStart` was consumed by the device |
| `reserved` | `abandoned` | agenda, or the successor owner | superseded, lost support, or owner changed before any audio |
| `playing` | `completed` | pump | `ClaimEnd` reached and the ring drained past the last chunk; `playback_time` records the engine-clock completion time, `playback_text` the text |
| `playing` | `interrupted` | pump (barge-in, lost support) | audio had played when the Interrupt arrived |
| `playing` | `superseded` | pump | the pre-chunk check found the same key with a different value |
| `playing` | `uncertain` | successor owner | the old owner's lease expired with the playback still `playing` |

```iql
.require ?speech_owner(S, "sp-1", 1), S = "s-42", speech(S, G, T, Subj, V, "supported", _),
         G = "g-7", T = "eta", Subj = "ORD-4821", V = "2026-10-08",
         speech_until(S, U), Now = time_now(), Now < U, !playback(S, 1, _, _, _, _, _, _)
.require ?topic_source(T, Src), T = "eta", source_health(Src, "ok", U2), Now = time_now(), Now < U2
+playback("s-42", 1, "g-7", "eta", "ORD-4821", "2026-10-08", 1, "reserved")
```

The second guard is present for every topic that has a `topic_source` row and absent for the others (`confirm`, `clarify`, `answer`, the "last known" claims): it is the health-lease check the dead-watchdog argument of section 13.1 relies on, and it is a separate statement so that its failure is distinguishable by index.

`heard` reads the **latest audible playback per key** by ordinal, not by query revision, so the user's current belief is the last thing the device actually played for that key, whether it completed or was cut. `reserved` and `abandoned` are not audible: a selection that never reached the device leaves no trace in what the user heard, and the pending row stays until something does.

### 9.4 Realization, reservation and the last check

The selected row becomes a **claim token** `(Session, Goal, Topic, Subject, Value, Kind, Pb, Epoch)`. Templates render `state`, `correction` and `restate` kinds for known topics with controlled wording: "It's due Thursday, October 8th." "Correction: it's now due Saturday, October 10th." "To confirm: it's due Thursday, October 8th." "I don't have a delivery estimate yet." "My carrier feed is behind; the last estimate I had was Saturday, October 10th." "I've requested the reschedule and I'm waiting for the confirmation." Open questions are realized by the LLM over a bounded snapshot of the session's current claims and sanitized as in section 6.5.

**Reservation** is the check at the moment the phrase is handed to synthesis, and it is a guarded program, not a local test: the engine confirms, at commit, that the `supported` row with this value still exists, that this owner's lease is unexpired by the engine clock, and that the ordinal is free (section 9.3). For topics with a `topic_source` row the reservation program also requires that source's `source_health` lease to be unexpired by the engine clock (section 9.3), so a dead watchdog cannot leave a confident sentence reservable (section 13.1); the agenda learns which topics those are from the graph, not from a table of its own. A stale local view loses at commit, with `precondition_failed`, and the selection is dropped.

The approved phrase is emitted as `ClaimStart(token)`, the agent `Transcript`, and `ClaimEnd(token)` on the data lane. The TTS stage replaces the transcript with audio chunks and forwards the markers, so downstream the order is marker, chunks, marker, and the pump attributes every chunk between two markers to that playback. Audio chunks carry no tag of their own; the attribution rests on lane order and on the flush: an `Interrupt` drops the realizer's and the synthesizer's in-flight work and every queued chunk stamped before it, so a cancelled generation cannot deliver a late chunk past the marker of the next one.

The **pump** at the pipeline's tail owns the device. Before pushing each chunk it reads the shared view, checks its own lease expiry against its clock, and applies the same rule as the agenda: a `supported` row with this key and a different value means superseded, so it stops, cancels the device ring, and commits `superseded`; an absent `supported` row means support lost, so it stops and commits `interrupted`; an expired lease means a successor exists, so it stops. It pushes each chunk while racing the tail's system lane, so an `Interrupt` from the barge-in stage or from the agenda is seen even mid-chunk, cancels the sink, clears the device ring, and flushes queued audio and markers stamped before the interrupt.

**The propagation window is stated, not hidden.** From a commit in the engine to the pump's view there is a delivery latency; from the pump's last check to the loudspeaker there is the device ring, which is short and bounded, and the OS buffer behind it, which is the floor. A revision that lands inside that window is spoken as if it had not happened, and the next delta turns it into a correction. No design recalls sound, and this one does not claim to. Interrupt responsiveness is a designed bound, VAD onset detection plus one await point plus the device buffer, to be measured on the deployed stack, not a number this article asserts.

### 9.5 Receipts: what was played, not what was generated

The pump writes `playing` when the device consumed the first chunk of a playback and `completed` when it drained the last one, with the completion time and the text. Those are receipts of **device consumption**, not of a human's hearing, and the design is conservative on purpose: anything audible counts as heard, so a cut sentence yields a confirming restatement rather than a silent omission, and a changed value yields a correction rather than a bare repeat.

Crash windows have legal outcomes, and each is a repeat or a restatement, never a lost claim and never a claim the rules believe was heard when nothing played:

| Crash point | Playback row | What the rules derive next |
|---|---|---|
| after selection, before `reserved` committed | none | the pending row is still there; it is said |
| `reserved`, no audio, owner dies | `abandoned` by the successor | pending row still there; it is said |
| audio played, before `playing` committed | none | pending row still there; it is said again (the one window that repeats) |
| `playing`, owner dies | `uncertain` by the successor | `restate` if the value is unchanged, `correction` if it changed |
| `playing`, barge-in | `interrupted` | same as above, after the floor is free |

Ask a confirm question and the same machinery answers "was it asked": `asked` holds only for the latest `completed` playback of a `confirm` claim, with its completion time, which is why consent (section 5) can be bound to it and to a window.

### 9.6 A fact changes mid-utterance

![A fact changes mid-utterance](/blog/voice-agent/correction-timeline.svg)

| Where the old value is | What happens | Mechanism |
|---|---|---|
| Selected, not yet reserved | Replaced silently | the reservation guard fails; the agenda reselects |
| Reserved or synthesizing, nothing played | Replaced silently | the agenda interrupts downstream and marks the playback `abandoned` |
| Chunks queued or in the ring | Remaining chunks dropped, ring cancelled, playback `superseded` | the pump's pre-chunk check sees the same key with a different value |
| Partly or fully heard | A correction is derived and spoken | the audible playback makes the old value `heard`; the new value derives `correction` at priority 1 |
| User is speaking | Nothing is said yet | the agenda holds on floor state; the correction row stays in the view, level-triggered, and is selected when the floor is free |

Only the claim whose key changed is affected. An unrelated revision touches no sentence.

## 10. Multitasking dispatch

![Multitasking dispatch sequence](/blog/voice-agent/dispatch-sequence.svg)

### 10.1 Identities

| Identity | Minted by | Stable for |
|---|---|---|
| Work item `(Session, Goal, Tool, Subject, Arg, Episode)` | Derived by rules | As long as the need holds |
| Attempt id and ordinal | The executor, allocated by a guarded program | One concrete try; the ordinal is unique per work item |
| Idempotency key | A hash of the work item and the ordinal | All retries of the same ordinal, by any executor |
| External task id | The backend, on acceptance (`DispatchEvent::Accepted`) | The backend's task |
| Lease epoch | Incremented by every takeover | The owner's term; carried as a fence on every command |

The dispatch frames already distinguish the model's `tool_call_id` from the backend's `task_id`. This design adds the work-item identity above both, so correlation does not depend on there being a pending tool call: an unsolicited world update that derives a new `work_intent` has a complete identity before any task exists.

### 10.2 Ownership

Each session is owned by one executor at a time through `lease_owner(session, executor, epoch)` and `lease_until(session, until)`: taken over with the one-statement compare-and-set over both relations of section 8.2 when expired, renewed only while unexpired, with the epoch incremented on every takeover. The owner runs one claim loop per session, so within an epoch claims are serialized in process. An executor subscribes once, for all the sessions it owns:

```iql
.subscribe work ?work(K, S, G, T, Subj, Arg, Ep, Id), lease_owner(S, "exec-1", _)
```

The `work` relation is the executor's whole input: `start` rows (eligible needs, with every argument the tool acts on), `cancel` rows (attempts whose `run_ok` was withdrawn), and `reconcile` rows (unresolved attempts from an earlier epoch, and attempts whose outcome is unknown). One subscription per executor; one per session for the speech loop.

### 10.3 The claim is one guarded program

```iql
.require ?work_intent(S, G, T, Subj, Arg, Ep), S = "s-42", G = "g-7", T = "carrier_check",
         eligible(S, G, T, Subj, Arg, Ep), lease_owner(S, "exec-1", 4),
         lease_until(S, U), Now = time_now(), Now < U,
         !attempt(S, G, T, Subj, Arg, Ep, _, _, _, 1)
+attempt("s-42", "g-7", "carrier_check", "S-77", "", 1791068625059, "att-9f3", "exec-1", 4, 1)
```

The guard checks, at commit, the current desired state (`eligible`, which already folds policy, readiness, budget and the absence of unresolved or satisfied attempts), the owner's lease and epoch, the lease expiry against the engine clock, and that ordinal 1 is unallocated. Zero matches apply nothing. For a tool with a `tool_requires` row the program adds a second guard, `.require ?tool_requires(T, Src), T = "reschedule_delivery", source_health(Src, "ok", U2), Now = time_now(), Now < U2`, so the order feed's health lease is checked against the engine clock at the moment the tool starts, whatever `fresh` currently says (section 13.1). A retry adds the backoff: `attempt(S, G, T, Subj, Arg, Ep, Prev, _, _, _), Prev = "att-c1", attempt_done(Prev, "failed", "yes", Ready, _), Ready <= Now`, so an executor whose timer fired early is refused by the engine. The **linearization point** of the claim is this commit: before it, the need is unclaimed and any owner may claim it; after it, `unresolved` holds, `eligible` is withdrawn for everyone, and `run_ok` holds for this attempt. The ordinal is allocated durably by the same commit, so the idempotency key `h(work item, ordinal)` is stable across any later owner.

Then, and only then, the executor sends `DispatchCommand::Create` with the task, the idempotency key and the epoch as a fence. The **revocation boundary** is the backend's acceptance: until `Accepted` arrives the attempt can be finalized as `not_started` with nothing having happened; after it, the effect may be under way and only the backend's cancellation semantics apply. A `Rejected` event, the backend refusing the command before any task exists, is recorded as `failed` with the retryable flag taken from the reason: a quota refusal is retryable with a backoff, an invalid request is not.

**Requirements on the effect provider**, stated as requirements because the engine cannot supply them: the backend deduplicates `Create` by idempotency key within a retention window longer than any attempt's lifetime, returns the existing task for a duplicate key, rejects commands whose fence is lower than the highest it has seen for the session, and answers a status lookup by key. A durable workflow engine meets these; a bare HTTP API needs a thin service in front of it. Exactly-once effects come from the key at the effect; the engine gives atomic, serialized records of what was decided.

### 10.4 Results are observations

Results re-enter through the observation protocol of section 4.1, with the executor acting as the adapter for the source "carrier API", stamping `observed` with its own receipt time. The attempt's outcome is recorded in the same transaction, guarded so that only the first terminal outcome wins and so that a note observed later than this result is never overwritten by it:

```iql
.require ?attempt(S, G, T, Subj, Arg, Ep, Id, _, _, _), Id = "att-9f3",
         !attempt_done(Id, _, _, _, _), latest_note_at(Subj, At), At < 1791068685059
-carrier_note("S-77", W, R, At) <- carrier_note("S-77", W, R, At)
+carrier_note("S-77", "weather_delay", 2201, 1791068685059)
+attempt_done("att-9f3", "ok", "no", 0, "carrier reported weather delay at hub LEJ")
```

For a shipment with no note yet, the guard's last literal is `!carrier_note(Subj, _, _, _)` instead. `carrier_note` is a world fact keyed by the shipment with its own revision and observation time. It withdraws `work_intent` (the note now covers the current ETA) and derives the `carrier_reason` claim. Nothing in the result addresses "the user's question"; the rules decide whether any session still cares.

The same holds for a tool that changes the world. The reschedule API's response carries the new promise date, so the executor writes it as the order system's observation in the same transaction as the outcome, and the need withdraws itself at once instead of waiting for the order feed:

```iql
.require ?attempt(S, G, T, Subj, Arg, Ep, Id, _, _, _), Id = "att-b1", !attempt_done(Id, _, _, _, _)
+attempt_done("att-b1", "ok", "no", 0, "rescheduled")
-promised("ORD-4821", D, R) <- promised("ORD-4821", D, R)
+promised("ORD-4821", "2026-10-12", 1600)
```

When an attempt had been marked unknown, the terminal program that resolves it also deletes its `attempt_unknown` row, in the same transaction.

### 10.5 Late results, goal changes, cancellation

A late result is useful or obsolete depending on what it is keyed by. The observation is keyed by the shipment: it stays true and useful, and if the user's new goal `g-8` concerns the same shipment it supports `g-8`'s claims immediately. The attempt is keyed by its goal and episode: if `g-7` was replaced while the check ran, `attempt_done` still lands, the observation is kept, and nothing is spoken for `g-7` because its claims require a `goal` row that no longer exists. Observation acceptance depends on source identity, revision and observation time, not on which goal asked.

When `run_ok` is withdrawn the executor sees a `cancel` row, and distinguishes four states:

| State | Action |
|---|---|
| Claimed, `Create` not yet sent | finalize `not_started`; nothing happened |
| Running, cancellable (a read) | `DispatchCommand::Cancel { task_id, reason }` (target extension); on `DispatchEvent::Cancelled` finalize `cancelled`; a `Completion` that raced it is accepted instead, first terminal outcome wins, and its observation is kept |
| Running, irreversible (a write) | not cancelled; the effect completes and is recorded; if the goal changed, compensation is its own work intent with its own `tool_policy` row, consent mode included |
| Completed | nothing to cancel; the effect is a fact |

Because `cancel_due` is derived from `run_ok`, every reason to stop is covered by one rule: goal retracted, kill switch, policy disabled, consent withdrawn, policy conflict. The executor never interprets a message to learn that work is unwanted.

### 10.6 Failure, retry and reconciliation

| Event | Record | Consequence in the rules |
|---|---|---|
| `Failure` or `Rejected`, retryable | `attempt_done(Id, "failed", "yes", ready_at, …)` | the need is eligible again; the claim guard refuses it before `ready_at` by the engine clock; up to `max_attempts` failures |
| `Failure` or `Rejected`, permanent | `attempt_done(Id, "failed", "no", …)` | `exhausted`; the `action_failed` claim tells the user |
| timeout with no answer | nothing yet | `unresolved` stays; `reconcile` on the next owner; a status lookup by key decides |
| lookup says no task under the key | `attempt_done(Id, "not_started", …)` | not counted; the need is eligible again with the next ordinal |
| lookup inconclusive | `attempt_unknown(Id, revisit_at)` | `unresolved` and `run_ok` stay; a `reconcile` row stays until resolved; no new ordinal |
| lookup resolves an unknown attempt | the terminal program writes `attempt_done` and deletes `attempt_unknown` | the `reconcile` row leaves; the outcome counts like any other |
| success confirmed but no record returned | `attempt_done(Id, "ok", …)` without an observation | `satisfied` and `action_pending`; a `reconcile` row until the record arrives or the bound passes |
| confirmation bound passed | `attempt_unconfirmed(Id)` | `action_unconfirmed` replaces `action_pending`; the need stays satisfied, so no second effect |

**Crash after the effect, before the record.** The executor crashes after the carrier API returned and before `attempt_done` committed. On restart, and on every lease acquisition, the owner first reconciles every unresolved attempt it now owns: it asks the backend for the task under the attempt's key (the lookup by key is the fourth extension, an operation on the dispatch transport), learns the outcome, and writes it; adopting an attempt from an older epoch is a guarded reassignment of the `attempt` row. Only then does it allocate new ordinals, so a handover can never duplicate an unresolved effect and can never exhaust a need on an orphan: orphans are finalized, not counted.

Duplicate starts across a handover are therefore confined to one window, an old owner that called the backend and crashed before recording anything, and that window is closed by the backend's deduplication of the key. A suspended old owner that wakes later is fenced by its stale epoch at the backend and by its stale lease in every guard.

### 10.7 Parallelism without unbounded tasks

Work items are independent by key and run in parallel up to per-tool and per-backend concurrency limits held by the executor. Dependencies are rules: a work intent that needs another's result names that result's relation in its body and does not derive until it exists. Serialized access to one entity is a claim key. A burst of `start` rows arrives as one coalesced set, and the executor claims from it under its limits; nothing about the subscription obliges it to start everything at once. The speech lane is never blocked by any of this, because the executor shares nothing with it but the graph.

## 11. Rules as code

Rules are authored in `.iql` files, one pack per domain, reviewed in version control like any code. Regression tests are IQL scripts run against a real engine: for each scenario, load the pack, commit the facts, assert the derived rows, their `.why` proofs and the deltas a subscriber receives. **Registration is not validity**: a rule that violates range restriction registers and fails only when queried, so the pack tests execute every rule and every guard shape as a query. The engine ships a differential oracle that replays histories through independent evaluators and compares results as sets; the pack tests plug into the same harness.

Deployment is **one wire program**, sent over the API like any other write: the removals of the rules it redefines (`-claim`), **every clause** of each redefined rule (the example shows one of the thirteen `claim` clauses for brevity; dropping a rule drops all of its clauses, so a program that re-adds fewer than all of them changes the pack), any new schema declarations, and the replacement of `pack_version` guarded on the version it expects to replace. It commits as one transaction. The `.load` command is a client-side convenience that reads a file on the operator's machine, and its replace mode deletes the data of the relations a file declares; it is not how a pack reaches a tenant.

```iql
.require ?pack_version("delivery_support", "2026.10.3", _)
-claim
+claim(Sess, G, "eta", O, D) <- goal(Sess, G, "delivery_status", O), authorized(Sess, O), shipment(O, S, _), eta(S, D, _, _), !eta_conflict(S), topic_source("eta", Src), fresh(Src)
// … the other twelve claim clauses, verbatim …
-pack_version("delivery_support", V, H) <- pack_version("delivery_support", V, H)
+pack_version("delivery_support", "2026.10.4", "sha256:9a2e")
```

What the engine promises is **atomic visibility**: a subscriber sees either the old rules' result or the new rules' result at a revision, never a mixture; it may receive the change folded into one push with neighbouring commits, as coalescing allows. Every decision record carries the pack hash it was decided under (section 12).

A rule change does not touch running work by itself. An open attempt stays open until its outcome lands, because `attempt` is a fact. What a policy change does is withdraw `run_ok`, which is the designed path: the executor cancels what can be cancelled and lets irreversible effects complete and be recorded. A playback in flight is checked against the new view at the next chunk.

Versioning is application practice, not an engine feature: the pack's artifact, hash and version are kept immutable in the deployment record, and the migration tooling that ships with the Python SDK generates and applies numbered migrations for schema and rule changes. The guarantee relied upon is the transaction, not the tool.

## 12. Explainability and audit

`.why ?speech("s-42", G, "eta", "ORD-4821", V, "correction", P)` returns a proof tree: the rule clause that fired, its variable bindings, and the base facts beneath, down to `eta("S-77", "2026-10-10", 1804, …)` and the playback row that made the earlier value "heard". Over the WebSocket API the reply carries the result rows plus `proof_trees`: nodes of kind `fact` or `rule`, each rule node with the clause text as `rule_id`, its `bindings` and its `children`, and the `roots`. `.why_not eligible("s-42", "g-9", "reschedule_delivery", "ORD-4821", "2026-10-12", 9)` names the body predicate that failed.

**A decision and its proof are pinned to one snapshot.** `.why` explains the current state; it is not historical replay, and a proof read after the claim committed would explain a different state, one in which `eligible` is already withdrawn. So the claim program of section 10.3 and the reservation of section 9.3 include their `.why` in the same program, and the target contract is that queries and `.why` inside a write program evaluate at the program's snapshot, after its earlier statements, and that the reply to a write program reports the revision it committed. IQL has no statement that persists a query result as facts, so the client, not the engine, appends the proof to its decision record: an append-only audit log keyed by the attempt or playback id, holding the proof text, the committed revision, the pack hash and the policy rows read. An auditor then has what the decider had.

Two limits, stated so they are designed for rather than discovered: a proof shows a row follows from accepted facts and authored rules, and the `src_rev` and observation time in the base facts are how an audit walks from the graph back to the source record; and a proof of a derived row is not a proof of an LLM sentence, which is why best-effort language carries no claim and its receipt records the text that played.

## 13. Failure on the decision path, and production limits

### 13.1 The engine, the watchdog, or a lease fails

Every request to the engine carries a deadline. An engine that is unreachable, past its deadline, or read-only after an unknown write outcome (section 8.1) is the same case for every writer: the speech loop's behaviour degrades in three steps:

- **Admission stops.** No new playback is reserved, no new claim is started, no consent is accepted. All of these are guarded programs, and a program that cannot commit is a program that did not happen.
- **What is already in flight continues under its own rules.** The sentence being played finishes unless superseded. An external call already accepted by the backend completes, is reconciled when the engine returns, and is never "stopped by graph unavailability", because nothing can stop it.
- **Permitted speech is a fixed grammar.** While the view is unverified the realizer renders only the templates that assert nothing about the world: acknowledgements, "let me check that", clarifying questions already derived before the outage. The best-effort LLM path is suspended, because its snapshot would be stale and its sanitizer cannot tell. This is enforced by the realizer's mode, not by prompt instruction.

**If the watchdog dies**, status flips stop. The rules stay optimistic: a dead adapter's `source_health` remains `"ok"` and its firm claims remain derived. But the guards do not: the reservation guard for a source-dependent topic and the claim guard for a tool that requires the source both compare the health lease's expiry with the engine clock, so within one lease period no new firm sentence about that source is reservable and no such tool starts. Because the freshness check is its own `.require` statement, a `precondition_failed` names it by statement index, and the agenda treats that failure as "topic stale" and raises the alarm; the user hears the holding grammar for that topic rather than a confident stale estimate. A dead watchdog costs availability, not correctness, and the watchdog is redundant because its flips are idempotent compare-and-sets.

**If a lease holder stalls**, its lease expires by the engine clock; a successor takes over with the compare-and-set of section 8.2; the stalled owner's subscription empties on its next push, and if it is partitioned from the engine its own clock check stops it within one lease period. Queues are bounded channels with backpressure; the intent queue is unbounded by design and reports its depth; adapters resume from the cursor in the graph on reconnect. Recovery is reconnect with backoff, `.subscribe` again, rebuild the views from the new snapshots, reconcile open attempts, resume. No hard real-time guarantee is made anywhere; the deadlines are budgets the application enforces, and the engine's part is honouring `timeout_ms` and `cancel` and never interrupting a commit.

### 13.2 Tenancy and authority

The engine authorizes at the **knowledge-graph boundary**: users and API keys have `reader`, `writer` or `admin` on a graph, every request is checked, and a standing query re-checks its subscriber's credential on every re-evaluation, so revoking access stops deltas on live connections. One graph per tenant is the isolation unit. Inside a graph, rows are not isolated by the engine: session tagging is scoping, not isolation. The application enforces it at the write gate (every intent-path row carries the connection's session) and by binding every subscription to its session or its executor.

Authority to write **policy facts** belongs to the deployment credential. The runtime components hold `writer` credentials, and their write gates confine them to their relations; that confinement is an application guarantee backed by the engine's typed schemas, not a relation-level ACL, and this article does not pretend otherwise.

### 13.3 What scales, and what costs

- **Relation cardinality.** World relations are per tenant graph. A standing query bound by a session constant reaches what the bindings reach: for this pack that is one user's orders, their shipments and notes, and the policy rows.
- **Rule shape.** Joins and recursion over large relations cost what they cost; a bound root does not bound a reachable subgraph. Keep recursive relations small or sliced, and measure the pack's queries with the engine's performance gate, which measures writer-to-subscriber delta latency end to end over the real protocol.
- **Subscription evaluation.** Each affected subscription re-evaluates per coalesced change, and each subscriber connection holds its own view, so the cost per commit grows with the number of affected subscriptions. There is no clock relation in any closure, so time passing costs nothing; a health status flip re-evaluates the sessions that depend on that source, which is the intended cost of a feed going stale. Lease renewals touch `lease_until` and `speech_until`, which no subscription reads; takeovers touch `lease_owner` and `speech_owner`, which every `work` and `speech` query reads, and takeovers are rare.
- **Guard footprint.** A guard over a derived relation conflicts with every commit to the relations in its closure (section 8.2); the claim rate a tenant can sustain is bounded by that footprint and the eight re-stagings. Narrow guards and the tuple-level read set are the two levers.
- **Result limits.** A standing result over the configured row cap is reported as an error rather than delivered; an oversized snapshot or delta is streamed in chunks and applied only when complete; a single row larger than any frame resets the subscription. Session-bound queries keep results small by construction, and the recovery rule for an error or a reset is to resubscribe, with a narrower query if size was the cause.
- **Hot graphs.** One engine process owns a data directory, and its writes are serialized per graph. Scale is by graph, across engines; nothing here invents horizontal scaling of a single hot graph.
- **Model and tool capacity.** The speech lane's realizer and the background reasoner run on separate inference capacity; the executor bounds concurrency per tool.

Every bullet above is a design choice or a budget. The measured results are in the next section, and only those.

## 15. Tests, acceptance and the fault suite

Existing, in the engine and runtime, and relied upon:

- Standing queries over a real `/ws` connection: exact `inserted`/`retracted` rows for inserts, retractions through recursive rules, rule add and remove; contiguous `seq`; increasing `revision`; final view equal to a fresh query.
- The reactive end-to-end suite: 64 subscribers on one graph, reconnect and resubscribe, crash-restart, unrelated writes, write bursts, deltas arriving while the agent's own query runs, cancelling that query by id while keeping the subscription.
- The differential oracle: hand-written and random histories replayed through independent evaluators, including the subscription path, compared as sets.
- Atomic programs: a failed statement leaves data, schemas and rules unchanged and nothing in the WAL; a migration commits all three together.
- Deadlines and cancellation across the commit boundary: a cancelled or expired request never runs later; a blind retry leaves exactly one copy.
- WAL recovery and restart equivalence.
- Runtime: the causal flush keeps post-interrupt frames and durable frames; `recv_sys` reaches an interrupt past a backed-up data lane; the LM stage commits a turn only after its stream completes; the chunker and TTS stage cancel within one chunk.

Application tests this architecture requires, written against a real engine process and a fake backend:

**Acceptance.** Build the smallest loop first: the pack for `delivery_status` and `reschedule`, the carrier adapter with its cursor and health lease, the watchdog, the intent gate for those kinds, the agenda with template realization only, the pump with playback receipts, the executor for one auto-mode tool and one consent-mode tool against a fake backend. The demonstration shows each of the four pillars working, with `.why` on every decision:

- **Runtime data and workflows embedded in the agent**: inject the carrier revision while the first ETA is playing; the transcript shows the original claim, then one correction in the next floor-free window; the graph holds one `carrier_check` attempt and one `carrier_note`; `.why` on the correction names the new `eta` fact and its `src_rev`.
- **Tool calls and their policies modelled explicitly**: a consent-mode reschedule is refused by the gate before the confirm question has completed and accepted after it; `.why_not eligible` names the missing consent before, and `.why eligible` names it after.
- **Guardrails enforced with provenance**: a goal for another customer's order yields only "I can't find that order on your account"; an ETA conflict withdraws the firm claim; a kill switch cancels the running check and the agent says it cannot check right now; a sanitized best-effort answer never carries a date the snapshot did not hold.
- **Multitasking dispatch**: a carrier check starts and finishes while the agent is speaking, with no user turn, and its reason is spoken afterwards; a goal change cancels a running read, while an irreversible write already accepted completes and is recorded; the agent never says the same claim twice without a change.
- **The fault suite**: killing the speech owner during the first sentence leaves a `playing` row the successor marks `uncertain`, and the agent restates rather than repeats; killing the executor after the effect and before the record converges, by key, to one outcome; a zombie owner cannot block a failover.

A happy path proves the loop works; the fault suite proves the invariants, and the demo is not done without both.
