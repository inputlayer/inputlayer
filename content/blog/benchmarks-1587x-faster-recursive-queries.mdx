# Benchmarks: Recursive Queries in Milliseconds After the Graph Changes

If your compliance system takes 11 seconds to update after an ownership change, that's 11 seconds where a transaction can slip through against a sanctioned entity. If your recommendation engine takes 11 seconds to reflect a stockout, that's 11 seconds of customers clicking "buy" on products you can't ship. If your access control takes 11 seconds to propagate a role change, that's 11 seconds where a terminated employee's permissions are still active. That is the cost of recalculating everything from scratch in systems that need to reason over connected data.

Insert 100 edges into a 2,000-node graph with recursive reachability rules. Recomputing the full transitive closure takes 11.3 seconds. Asking InputLayer what one node can now reach takes 6.83 milliseconds.

The two numbers answer different questions. The full recompute rebuilds every reachable pair in the graph; the bound query returns only what node 1 can reach. The **1,652x** ratio measures demand-driven evaluation: InputLayer computes the part of the closure the question needs, and nothing else. That's what lets an agent react to a change within milliseconds instead of waiting for the next batch recompute.

## The benchmark setup

The graph is an Erdős–Rényi random graph (seed 42) with transitive reachability rules. It's the same shape of computation you'd need for authority chains in an organization, access control, supply chain risk propagation, or entity resolution across corporate structures: "A reaches B, B reaches C, so A reaches C."

```flow
2,000 nodes -> 4,000 edges -> about 1 million reachable pairs
```

```note
type: info
The test: insert 100 new edges, then ask what node 1 can reach. Compare that with recomputing every reachable pair from scratch.
```

All numbers are from a single machine (AMD Ryzen 9 9950X, release build). The full methodology and raw tables are in [BENCHMARKS.md](https://github.com/inputlayer/inputlayer/blob/main/BENCHMARKS.md).

## The results

| Approach | Time | What it does |
|---|---|---|
| Recompute the full closure | 11.3 s | Re-derives every reachable pair in the graph |
| InputLayer bound query | 6.83 ms | Answers "what can node 1 reach?", computing only what that question needs |

Recomputing the closure doesn't care that you only asked about one node. It treats the entire graph as dirty and rebuilds everything. InputLayer rewrites the recursive query so it starts from the node you asked about and follows only the paths that matter to the answer.

To put 6.83ms in perspective: that's fast enough to run inline with an API request, or to push an updated answer to an agent the moment the graph changes. You can check permissions, compute supply chain exposure, or resolve entity relationships when they're needed rather than pre-computing them in a batch process.

## What this means in practice

The practical takeaway here is about which architectural patterns become possible.

**Without incremental, demand-driven computation**, you're stuck with batch processing. Pre-compute permissions overnight. Rebuild recommendation indexes hourly. Re-run compliance checks on a schedule. And accept that between runs, your derived data is stale.

**With it**, you can do these things as the data changes:

| Use case | Batch approach | Streaming approach |
|---|---|---|
| Access control | Nightly permission rebuild | Live permission check at query time |
| Supply chain risk | Hourly risk recalculation | Risk update when a supplier status changes |
| Compliance screening | Daily sanctions check | Flag within milliseconds when ownership structure changes |
| Recommendations | Model retrain every few hours | Update when user behavior or inventory changes |

The speedup isn't about making a slow thing faster. It's about turning batch-only workloads into streaming ones. That's a qualitative difference in what you can build.

## The scaling story

The advantage grows with the graph, because the full closure grows roughly with the square of the node count while a bound query explores only the subgraph reachable from its seed.

| Graph | Full closure | Bound query | Speedup |
|---|---|---|---|
| 500 nodes, 1K edges | 578 ms | 2.01 ms | **288x** |
| 1,000 nodes, 2K edges | 2.40 s | 3.52 ms | **682x** |
| 2,000 nodes, 4K edges | 10.49 s | 6.61 ms | **1,587x** |

These are queries over the graph as generated, before any edges are inserted. The 1,652x figure above is the same comparison taken right after inserting 100 edges.

```steps
500 nodes: 578ms vs 2.0ms :: 288x [success]
1,000 nodes: 2.4s vs 3.5ms :: 682x [success]
2,000 nodes: 10.5s vs 6.6ms :: 1,587x [primary]
```

This scaling behavior is structural, not accidental. Recomputing everything has to process the entire graph regardless of what you asked. A bound query processes only the part of the graph its answer depends on, which stays relatively small even as the total graph grows.

## Why the numbers work this way

InputLayer is built on [Differential Dataflow](https://github.com/TimelyDataflow/differential-dataflow), a Rust library for incremental computation created by Frank McSherry. The core idea is simple: instead of storing derived results as static data, the engine tracks *what changed* and efficiently passes those changes along.

Here's how a fact change flows through the system:

```graph
Alice --authority-> Diana --manages-> Eve [primary]
Bob --authority-> Diana --manages-> Eve [primary]
Eve --manages-> Frank [success]
```

The engine didn't scan the entire graph. It didn't recompute relationships for nodes that weren't affected. It started from the change, followed the ripple effects, and stopped as soon as the ripple died out.

For recursive reasoning, like indirect authority where conclusions feed back into the computation, the engine runs a loop until it reaches a stable point where no new changes are produced. When something changes later, it re-enters that loop at the point of change and computes only the new changes.

InputLayer also uses an optimization that makes queries on-demand rather than exhaustive. When you ask "who does Alice have authority over?", the engine doesn't compute authority for every person in the organization. It starts from Alice and follows only the relevant paths. Query time becomes proportional to Alice's portion of the graph, not the entire organization.

## Correct retraction: the hard part

Adding facts is relatively straightforward to handle incrementally. Removing them is where things get genuinely hard.

Say Alice has authority over Charlie through two independent paths:

```graph
Alice --manages-> Bob --manages-> Charlie [primary]
Alice --manages-> Diana --manages-> Charlie [primary]
```

If you remove Bob's management of Charlie, Alice should still have authority over Charlie through Diana. But if you remove Diana's management of Charlie too, the authority should disappear entirely.

The engine tracks this through weighted differences. Each derived relationship has a weight based on the number of independent paths that support it. When a path is removed, the weight goes down. Only when it reaches zero does the conclusion go away.

```steps
Both paths: weight = 2 :: via Bob + Diana
Remove Bob path: weight = 1 :: survives [success]
Remove Diana path: weight = 0 :: retracted [highlight]
```

On a 500-node benchmark graph with the closure materialized, deleting 10 edges and re-querying takes about 600 ms, the same as a baseline query. Deleting 100 edges (10% of the graph) takes about 1.1 seconds; the extra cost is proportional to the cascade of derived rows that must be withdrawn.
