# Benchmarks: 1,652x Faster Recursive Queries with Magic Sets

```note
type: info
InputLayer is the live rules engine for AI agents. This post measures one thing: how fast the engine answers a bound recursive query after facts change, compared with recomputing the full closure. It is a recursive-query result, not an agent-latency figure, and it is not an incremental-maintenance result: InputLayer re-derives the answer on every query.
```

If your compliance system takes 11 seconds to answer after an ownership change, that's 11 seconds where a transaction can slip through against a sanctioned entity. If your recommendation engine takes 11 seconds to reflect a stockout, that's 11 seconds of customers clicking "buy" on products you can't ship. If your access control takes 11 seconds to propagate a role change, that's 11 seconds where a terminated employee's permissions are still active. These aren't hypotheticals. They're the cost of recalculating everything from scratch in systems that need to reason over connected data.

A knowledge graph with 400,000 derived relationships gets 100 new edges. Recomputing the full transitive closure: 11.3 seconds. InputLayer answering "what can node 1 reach?": 6.83 milliseconds.

That's a **1,652x** difference, and it comes from computing only what the question needs.

## The benchmark setup

We wanted to test something that reflects real-world usage, not a synthetic micro-benchmark. So we picked a common pattern: following chains of authority in an organizational graph. Think "Alice manages Bob, Bob manages Charlie, so Alice has indirect authority over Charlie." This is the same kind of computation you'd need for access control chains, supply chain risk propagation, or entity resolution across corporate structures.

```flow
2,000 nodes -> 4,000 edges -> 400,000 derived relationships
```

```note
type: info
The test: insert 100 new edges, then query. The bound query asks about one node; the full query asks for the whole closure.
```

The 400,000 derived relationships come from following chains of authority. If A manages B and B manages C, then A has indirect authority over C. Follow that logic through 2,000 nodes and the number of derived relationships grows fast.

## The results

| Query after +100 edges | Time | What it does |
|---|---|---|
| Full `?reach(X, Y)` | 11,300 ms | Derives all 400,000 relationships from the current facts |
| Bound `?reach(1, Y)` (Magic Sets) | 6.83 ms | Derives only the relationships reachable from node 1 |

Both queries are evaluated from the current facts; neither reuses a stored result. The difference is how much of the graph each one has to touch. The full query treats the entire graph as relevant. The bound query is rewritten by Magic Sets so the recursion starts from node 1 and explores only the subgraph that node 1 can reach.

To put 6.83ms in perspective: that's fast enough to run inline with an API request. You can check permissions, compute supply chain exposure, or resolve entity relationships at query time rather than pre-computing them in a batch process.

## What this means in practice

The practical takeaway here is about which architectural patterns become possible.

**With a precomputed table**, you're stuck with batch processing. Pre-compute permissions overnight. Rebuild recommendation indexes hourly. Re-run compliance checks on a schedule. And accept that between runs, your derived data is stale.

**With fast bound queries over current facts**, you can do these things live:

| Use case | Batch approach | Query-time approach |
|---|---|---|
| Access control | Nightly permission rebuild | Live permission check at query time |
| Supply chain risk | Hourly risk recalculation | Risk for one supplier computed when asked |
| Compliance screening | Daily sanctions check | Ownership chain checked at transaction time |
| Recommendations | Model retrain every few hours | Recommendations derived from current behavior and inventory |

The 1,652x figure is about making a bound question cheap enough to ask live. Questions that need the whole closure still pay for the whole closure on every read.

## How it scales, and where it doesn't

The bound query's cost is proportional to the part of the graph reachable from the seed, not to the total graph size. The full closure's cost grows with the whole graph, much faster than linearly: double the nodes and the time roughly quadruples.

| Graph | Full closure | Bound `?reach(1, Y)` | Speedup |
|---|---|---|---|
| 500 nodes, 1K edges | 578 ms | 2.01 ms | **288x** |
| 1,000 nodes, 2K edges | 2,400 ms | 3.52 ms | **682x** |
| 2,000 nodes, 4K edges | 10,490 ms | 6.61 ms | **1,587x** |

These are cold queries on random graphs (see [BENCHMARKS.md](https://github.com/inputlayer/inputlayer/blob/main/BENCHMARKS.md)); the 1,652x figure above is the same comparison after inserting 100 edges.

Two limits are worth knowing. Magic Sets helps only when the binding matches the recursion's direction; a bound read through a differently shaped rule can still cost the full closure. And because every read re-derives its answer, a subscription to a large recursive rule re-runs that query after every relevant commit. Keeping persistent rules as incrementally maintained views, so that a change is applied once instead of re-derived on every read, is planned work: [milestone 9](https://github.com/inputlayer/inputlayer/issues/305).

## Why the numbers work this way

InputLayer is built on [Differential Dataflow](https://github.com/TimelyDataflow/differential-dataflow), a Rust library for incremental computation created by Frank McSherry. InputLayer uses it as its execution engine: each query compiles its rules into a dataflow, streams in the current facts, collects the result and tears the dataflow down.

For recursive reasoning, like indirect authority where conclusions feed back into the computation, the dataflow runs a loop until it reaches a stable point where no new facts are produced.

Magic Sets is what makes the bound query cheap. When you ask "who does Alice have authority over?", the rules are rewritten so that the loop only ever considers people reachable from Alice. The engine doesn't compute authority for every person in the organization. Query time becomes proportional to Alice's portion of the graph, not the entire organization.

## Correct retraction: the hard part

Adding facts is relatively easy to get right. Removing them is where systems that store derived results get genuinely hard.

Say Alice has authority over Charlie through two independent paths:

```graph
Alice --manages-> Bob --manages-> Charlie [primary]
Alice --manages-> Diana --manages-> Charlie [primary]
```

If you remove Bob's management of Charlie, Alice should still have authority over Charlie through Diana. But if you remove Diana's management of Charlie too, the authority should disappear entirely.

InputLayer gets this right because the next query recomputes from the remaining facts: a conclusion appears exactly when some remaining path supports it. Inside each evaluation, Differential Dataflow tracks support as weights, and a conclusion only exists while its weight is positive.

```steps
Both paths: weight = 2 :: via Bob + Diana
Remove Bob path: weight = 1 :: survives [success]
Remove Diana path: weight = 0 :: gone [highlight]
```

On a 500-node graph with 1,000 edges, re-querying the full closure after deleting 10 edges takes about 600ms, and after deleting 100 edges about 1.1 seconds, because the re-query evaluates the recursive rules again over the changed graph.
